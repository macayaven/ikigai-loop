## Success Criteria

- **Code facts exist and are pure.** A new pure module in `framework/glimmer/` exposes `code_facts(as_of, winners, rollup)`. No model, no clock, no env, no I/O. Same `winners`/`rollup` in, byte-identical code facts out. At most 5 per cycle, one per family.
- **The rule cannot miss the largest change.** For each family, the largest absolute change between consecutive periods (earlier→prior, prior→last), across all members of the family, becomes a fact, subject to the pinned floor. The 2026-11-01 fixture below yields exactly the 5 statements pinned under Cases, including Media/Video 0→4.0.
- **Zero is citable.** `build_metric_snapshot` writes explicit `0.0` period keys for any category or tag that is non-zero in any of the three periods, so "from 0 in prior" cites a real snapshot key and a Wonder claim quoting it passes the gate instead of failing `L1B_UNKNOWN_METRIC`.
- **Templates cannot drift from the gate.** Every code-fact statement is generated by the pinned templates, and each fixture code fact wrapped in a claim with the correct metric refs passes `evaluate_briefing`; the same claim with the direction word swapped, and with a period word replaced by the third period, is rejected with the pinned codes.
- **Model facts cannot crowd out or repeat code facts.** Code facts come first in `FactResult.facts`, do not count against `MAX_FACTS`, and a model statement that repeats one drops with the new code `FACT_DUPLICATE_OF_CODE`.
- **Code facts are recognisable later.** The append-only store records whether each stored fact came from code or from the model, migrating an existing database file cleanly; a test opens a database created by the previous schema.
- **The model is optional.** If a model pass is unavailable, truncated or invalid, the code facts still come back. A cycle is a noop only when there are no facts at all. `extract_facts` gains `personal_pass: bool = True` and `feed_pass: bool = True`; the CLI gains `--no-personal-pass` and `--no-feed-pass` and prints how many code and model facts it kept.
- **A cited-row count backs a number only for feed rows.** In `check_fact`, the count of cited rows backs a number token only when every cited row is a `feed.item`; everywhere else the number needs snapshot backing or drops `FACT_NUMBER_UNBACKED` (D19). Code facts therefore rest on snapshot backing only, and the fixture's five still pass.
- **`other` and `system` never win the screen family, and `ai` prints as `AI`.** The screen family's member universe excludes `SCREEN_SKIPPED_CATEGORIES` by exact string; both categories stay in the rollup, the snapshot (zero keys included) and the model's reach. The screen template prints `SCREEN_DISPLAY_NAMES.get(category, category)` while `member` and `metric_ids` keep the raw category (D20).
- **Docs land with the code.** `CONTRIBUTIONS.md` entry, `docs/sessions/009b-code-facts.md`, and one line in `README.md` Status under the fact layer with the new test count.

### Key decisions (binding on the implementer)

- **D1 — Module, shapes, purity.** New file `framework/glimmer/code_facts.py`, pure and deterministic: no model, no clock, no env, no I/O, stdlib + existing repo imports only. It exposes:

```python
HOURS_FLOOR = 0.5  # hours; see D4
COUNT_FLOOR = 1.0
SCREEN_SKIPPED_CATEGORIES = frozenset({"other", "system"})  # D20
SCREEN_DISPLAY_NAMES = {"ai": "AI"}  # D20


@dataclass(frozen=True)
class CodeFact:
    family: Literal["screen_hours", "pushes", "prs", "tag_hours", "cancelled"]
    member: str  # screen category or tag verbatim; "" for pushes/prs
    from_period: str  # "earlier" | "prior"
    to_period: str  # "prior" | "last"; always the next period after from_period
    from_value: float
    to_value: float
    statement: str
    evidence: tuple[str, ...]  # real winning event ids, 1..8, D9 order
    tier: Tier
    metric_ids: tuple[str, str]  # (period.<from>.<rest>, period.<to>.<rest>)


def code_facts(
    as_of: datetime, winners: Sequence[Event], rollup: dict[str, dict[str, Any]]
) -> tuple[CodeFact, ...]: ...


def format_metric_value(value: float) -> str: ...  # D5
def is_duplicate_of_code(
    statement: str,
    evidence_ids: Sequence[str],
    code_facts: Sequence[CodeFact],
) -> CodeFact | None: ...  # D12
```

  Why a `CodeFact` record instead of returning `Fact` directly: the pinned signature `code_facts(as_of, winners, rollup)` has no `subject_id`, and `Fact` requires one ([framework/schemas/core.py:23](../../framework/schemas/core.py:23)-29), plus the fact-layer window. `extract_facts` mints the `Fact` from the `CodeFact` with the existing `_mint_id` ([framework/glimmer/facts.py:128](../../framework/glimmer/facts.py:128)-131), `subject_id`, and `FactWindow(window_start, as_of)`, so code and model facts share one ID rule and one stored shape. `code_facts` assumes `winners` are the window-filtered winners `extract_facts` already computed (subject, window, `collected_at <= as_of`, allowlist, logical-key winners): it does not re-filter. Reason: a second filter would be a second source of truth for supersession.

- **D2 — Families, members, order.** Five families, emitted in this order, which is also the order of `FactResult.facts` for code facts:

  | # | `family` | Members (universe) | Rollup source per period | Metric-id rest |
  |---|---|---|---|---|
  | 1 | `screen_hours` | union of categories in `screen_hours` over the 3 periods, excluding `SCREEN_SKIPPED_CATEGORIES` (`other`, `system`) by exact string (D20) | `rollup[p]["screen_hours"].get(cat, 0.0)` | `screen_hours.<category>` |
  | 2 | `pushes` | single member `""` | `float(rollup[p]["pushes"])` | `pushes` |
  | 3 | `prs` | single member `""` | `float(rollup[p]["prs"])` | `prs` |
  | 4 | `tag_hours` | union of tags in `calendar_hours_by_tag` over the 3 periods | `rollup[p]["calendar_hours_by_tag"].get(tag, 0.0)` | `tag_hours.<tag>` |
  | 5 | `cancelled` | union of tags in `cancelled_blocks_by_tag` over the 3 periods | `float(rollup[p]["cancelled_blocks_by_tag"].get(tag, 0))` | `cancelled.<tag>` |

  The exclusion at row 1 binds only this family's member universe (D20): `other` and `system` stay in the rollup and in the metric snapshot, with their D7 zero keys, and the model may still write about them. A member absent from a period counts as `0.0` in that period; `build_period_rollup` already leaves absent members out of its per-period dicts ([framework/glimmer/metrics.py:96](../../framework/glimmer/metrics.py:96)-140), so `code_facts` reads missing as zero and never mutates `rollup`. Screen and calendar are each **one** family across all their members (the largest change may be in any category or tag), while pushes and PRs are separate one-member families, matching the separate counters and metric families the gate already binds. At most one fact per family, so at most 5. A cancelled row with no tag contributes to no member (the rollup loop at [framework/glimmer/metrics.py:130](../../framework/glimmer/metrics.py:130)-131 iterates `data.tags`), so it can never create or win the cancelled family; a test pins this.


- **D3 — Largest change and the tie-break (pinned exactly).** For each family, build every candidate `(member, pair, from_value, to_value)` for the two consecutive pairs `(earlier, prior)` and `(prior, last)`, with `change = round(abs(to_value - from_value), 6)` — rounded to 6 places, about 3.6 ms of an hour, so only float noise is removed. Reason: `build_period_rollup` accumulates `minutes/60` row by row at [framework/glimmer/metrics.py:115](../../framework/glimmer/metrics.py:115)-116, so six 5-minute rows give `0.49999999999999994` and six 10-minute rows give `0.9999999999999999`, and the fixture's own rollup holds `4.749999999999999` and `3.4499999999999993`; with exact float comparison, the way minutes are split across hourly rows would decide whether a change passes the floor and which side of a tie wins, so the pinned tie-break would not hold on real row shapes. That rounded `change` is what the floor (D4) compares and what the sort key uses. Discard candidates under the floor (D4). Pick the winner by sorting on `(-change, -pair_rank, member)` and taking the first, where `pair_rank` is `1` for `(prior, last)` and `0` for `(earlier, prior)`: **the later pair of periods first, then the member name in ascending sorted (Python string) order**. Ties are exact equality of the rounded `change`; no other epsilon. This is deterministic because `member` names within a family are distinct, so the key is a total order. No surviving candidate means no fact for that family; in particular no change anywhere in a family gives no fact, and an all-empty window gives none (pushes/PRs read `0, 0, 0`; the other families have an empty member universe). `from_value`/`to_value` themselves stay full-precision rollup values everywhere else (statement printing via D5, evidence, snapshot); only the floor comparison and the sort key see the rounded `change`.
- **D4 — Floors (pinned, with the reason).** `HOURS_FLOOR = 0.5` hours for the two hour families (`screen_hours`, `tag_hours`): a candidate is kept iff the rounded `change` (D3) is `>= 0.5`. Counts (`pushes`, `prs`, `cancelled`) use `COUNT_FLOOR = 1.0`: kept iff the rounded `change >= 1`, i.e. no floor beyond a change of 1, as the brief pins. Reasons: one period is 24 hours, and a 3-minute wobble is `0.05` hours — ten times below the floor — while the changes this layer exists to surface are hour-scale (the missed live change was 4.0 hours; the smallest winning change in the pinned fixture is 1.0). A quarter-hour floor (`0.25`) was rejected: a routine 15–25 minute shift in one category over a day would become the family's headline fact on quiet days, which is the noise the floor exists to suppress, and calendar blocks are normally scheduled in 30-minute units, so a sub-30-minute largest change is rounding, not a change in the day. The floor compares the rounded change; boundary tests pin exactly `0.5` kept (including as six 5-minute rows and as one 30-minute row) and `0.49` (29.4 minutes in the higher period) dropped.
- **D5 — Number formatting (pinned, with the gate arithmetic).** The gate backs a number token against a cited value by rounding the **value** half-up to the token's decimal places and comparing absolute values: `_ref_backs_token` at [framework/briefing/gate.py:537](../../framework/briefing/gate.py:537)-540, and the same rule in the fact checks as `_backs` at [framework/glimmer/checks.py:45](../../framework/glimmer/checks.py:45)-51. Code-fact statements print each value with `format_metric_value`:

```python
def format_metric_value(value: float) -> str:
    quantised = Decimal(str(value)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
    text = format(quantised, "f")
    if "." in text:
        text = text.rstrip("0").rstrip(".")
    return "0" if text in ("", "-0") else text
```

  That is: round half-up to 2 places — the same precision the prompt already renders ([framework/glimmer/prompt.py:79](../../framework/glimmer/prompt.py:79)-84) — then strip trailing zeros, giving the fewest decimals at that precision. Searching for fewer places from 0 up was rejected: it collapses every value under `0.5` to `0`, which the gate would accept (a `0` token is backed by any value that rounds to `0` at 0 places) while the statement would say something false. Pinned round trips, each asserted against both the gate's `_ref_backs_token` ([framework/briefing/gate.py:537](../../framework/briefing/gate.py:537)-540) and the fact check's `_backs` ([framework/glimmer/checks.py:45](../../framework/glimmer/checks.py:45)-51) at the printed token's decimal places: `4.0 -> "4"`, `1.7500000001 -> "1.75"`, `0.3333 -> "0.33"`, `2.5 -> "2.5"`, `6.75 -> "6.75"`, `0.0 -> "0"`, `1.7333333333333332 -> "1.73"`, `3.4499999999999993 -> "3.45"`, `4.749999999999999 -> "4.75"`, `10.0 -> "10"`, `20.0 -> "20"`, `100.0 -> "100"`, `0.995 -> "1"`, `0.004 -> "0"`. Counts pass through the same function (`3.0 -> "3"`), so there is one formatter. Selection (D3) uses full-precision `from_value`/`to_value` except that the floor comparison and the sort key use the rounded `change` (D3); printing and statements still use the full-precision rollup values through `format_metric_value`, and a claim ref written by Wonder must still copy the **snapshot** value, never the printed token — the session record already shows a rounded ref failing `L1B_METRIC_VALUE_MISMATCH`.

- **D7 — Zero keys: densify the snapshot only, never the rollup.** In `build_metric_snapshot`, after `rollup = build_period_rollup(as_of, winners)` ([framework/glimmer/metrics.py:170](../../framework/glimmer/metrics.py:170)), compute the member universes from the rollup (union over the three periods, as at D2), and write every `period.<name>.screen_hours.<category>`, `period.<name>.tag_hours.<tag>` and `period.<name>.cancelled.<tag>` key for every universe member, using `0.0` where the period has no value. ## Risks

- **A code fact that fails its own check is silent by design, but now visible as one.** D11 drops it with a `CODE_`-prefixed code (for example `CODE_FACT_NUMBER_UNBACKED`) rather than crashing, because `DroppedFact` holds only a hash and a code. The fixture, template and gate tests are the guard; a reviewer should read any `CODE_*` code in a live cycle — and only that prefix marks a code statement, a bare `FACT_*` code is a model draft — as a bug report, not as noise.
- **The duplicate definition has stated edges.** D12 matches on member (gate labels only), a subset of the code fact's period words, and values backed by the two values or by the change size. Its limits are stated at D12: `one` before a non-unit word is not a token, a member word outside the gate's labels (`Commits`, `Media`, `YouTube`) is not matched, a compound statement carrying numbers the change size does not back is not matched, and a cited repo name holding a digit reads as an extra token. Such statements go to the normal checks and may be kept — that is the conservative side, since loosening the rule would drop true, different statements (the cancelled/calendar pair at D12 is the example).
- **Re-baselining 30 cases by hand can hide a mistake.** Step 3 derives each case's code facts from its rollup on paper, and AT5 must pass on the branch while the new tests fail on the base; the session note lists every changed assertion and expectation with its hand-derived value (D18), and a diff that changes a case's model expectations (`expected_personal`, `expected_feed`, dropped codes) beyond D18's list and the D12 duplicate and D19 number-backing effects is out of scope and stops the ticket.
- **Cycle ids move once.** D7+D16 change snapshots, prompt bytes and therefore `cycle_id`s for identical inputs versus Ticket 9. Old runs remain stored and readable; nothing is backfilled, and the session note must say this so a later diff is not mistaken for data loss.
- **Truth is still not checked for model facts.** Code facts are true by construction (the rollup is the data), but "largest change" is a rule, not a judgement: on a quiet cycle the largest change may still be uninteresting, and the floor is the only guard. The personal pass remains free to add nothing.
- **D19 removes one source of false backing, not the whole class.** A number still has no unit: "4 events" stays kept when a value of a cited family rounds to 4 at 0 places, because `_snapshot_backs` cannot tell hours from rows (C26 pins this as a known limit). The other side of the same rule: a true count with no snapshot metric now drops, for example "3 calendar blocks" (the snapshot has no block count). Fixing the unit blindness is out of this ticket.
- **Skipped screen categories stay visible everywhere except the code family.** `other` and `system` remain in the rollup, the snapshot (zero keys included) and the model's reach (D20), so a model statement about them can still be kept; only the code screen fact cannot be about them.

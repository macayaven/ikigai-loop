## Decisions (binding on the implementation session; each with its reason)

- **D1 — Scope: `framework/rater/pack.py` and `framework/rater/page.py` only.** No change to `framework/proposal/`, `framework/cycle/`, `framework/store/`, `framework/briefing/`, the scorer, the key format, or any schema. Reason: everything the new line needs is already stored — the source row's `snapshot`, the source briefing's `parent_briefing_id` inside `briefing_json`, and the parent row's `snapshot`. The rater is a read-only consumer of a store copy (Ticket 16 SD1/SD2); keeping the fix inside it cannot break the live card path.
- **D2 — "This card" and "the change" come from the AD3 source row.** This card's value for a cited metric is that metric's value in the `snapshot` stored with the claim's source result row — the earliest qualifying row AD3 already picks ([framework/rater/pack.py:413](../../framework/rater/pack.py)). The change is the claim's own metric ref value, which assembly filled from the delta table ([framework/proposal/assembly.py:81](../../framework/proposal/assembly.py)). Reason: the source row is the row that supplied the claim and its refs; any other row's snapshot would describe a different briefing than the one the rater is showing.
- **D3 — "The previous card" is found by briefing id, and only by briefing id.** The previous value is the cited metric's value in the `snapshot` of a stored result whose parsed `briefing_json` id equals the source briefing's `parent_briefing_id`. The lookup scans every `proposal_results` row on the copy with a parseable `briefing_json`; it applies **no** slot, profile, kind or delivered/run-slot filter. If several rows carry that id and they all hold the metric with the same value, that value is used; if they disagree on it, or any of them lacks it, the claim is unresolved. Reason: the briefing id is the identity assembly itself recorded ([framework/proposal/assembly.py:117](../../framework/proposal/assembly.py)); a slot/profile search (the `latest_proposal` shape) could silently pick a re-proposal or the wrong goal's parent. No filter also means a parent that is itself outside the pack's scope — the extra 11:30 card of Deviation 18 at [docs/PREREG.md:195](../PREREG.md), whose claims the pack excludes — can still supply previous values, because it is evidence here, not a rated claim. Rows with missing or unparseable `briefing_json` (fallbacks and noops store none, [framework/store/proposal_store.py:382-391](../../framework/store/proposal_store.py)) simply never match.
- **D4 — The three numbers must agree under `compute_deltas`' own arithmetic, exactly.** A cited metric resolves only when `Decimal(str(this_value)) - Decimal(str(previous_value)) == Decimal(str(ref.value))`, with all three read as stored JSON numbers. No float subtraction, no tolerance, no rounding to display first. Reason: that is the arithmetic that produced the ref value ([framework/proposal/prompt.py:67-70](../../framework/proposal/prompt.py)); display rounding would let a line through whose shown numbers do not add up, and float subtraction would both pass and fail cases the delta table itself treated differently. A snapshot value that is not a JSON number, a snapshot that is not a JSON object, and a metric absent from either snapshot all count as "lacks the metric".
- **D5 — The new line's exact shape.** Only the `since_last` branch of `_render_ref` changes. The line becomes, before the existing first-letter capitalisation at [framework/rater/pack.py:259](../../framework/rater/pack.py):

  `<what> <period phrase>: <previous><unit> on the previous card, <this><unit> on this card, <signed change><unit> since the previous card`

  `<what>` and `<period phrase>` are exactly today's ([framework/rater/pack.py:241-246](../../framework/rater/pack.py)); `<previous>` and `<this>` are `display_value` of the two snapshot values; `<signed change>` keeps today's three forms (`+x` rise, `-x` fall on the absolute value, `0` for no change, [framework/rater/pack.py:250-255](../../framework/rater/pack.py)); `<unit>` is today's `_unit` and is repeated after **each** of the three numbers. Worked forms the tests pin verbatim:

  - `Pull requests in the last period: 6 on the previous card, 9 on this card, +3 since the previous card`
  - `Programming screen time in the last period: 4 hours on the previous card, 2.5 hours on this card, -1.5 hours since the previous card`
  - `Feed items across the whole three-day window: 4 on the previous card, 4 on this card, 0 since the previous card`

  Reason: keeping the label, period phrase, unit and sign machinery untouched means the only new words are the two values and their card phrases, so the line still reads as the same evidence line the rater already knows; repeating the unit keeps each number readable on its own (the brief's plain-words example does this for a count family, which carries no unit word either way). This supersedes Ticket 16 AD6's `since_last` rendering only; AD6 stands for every other claim.
- **D6 — Failure leaves the whole claim out, counted once, on one new line.** While rendering a `since_last` claim's refs, the first ref that is unbound still counts the claim under the existing `metrics_unbound`; the first ref that fails D3/D4 (no parent id, no row carrying it, metric lacking in either snapshot, duplicate parent rows disagreeing, or arithmetic disagreeing) counts the claim once under a new counter, `claims_since_last_unresolved`, initialised in the counter dict at [framework/rater/pack.py:304-320](../../framework/rater/pack.py) so the line prints on every pack run, including `claims_since_last_unresolved=0`. The claim produces no atomics and no partial line. The existing order is kept: a missing cited fact still counts under `facts_missing` first ([framework/rater/pack.py:419-422](../../framework/rater/pack.py)), and a claim is never counted under both new and old metric counters. Reason: a half-shown line would hand the rater the change without its check — the exact failure this ticket exists to remove — and one counter with one meaning keeps the pack's stdout countable while every trigger stays testable through it. Because the scorer's unlabelled rerun uses the same `collect` ([framework/rater/score.py:144](../../framework/rater/score.py)), an unresolved claim is absent from that rerun too and is not double-reported as unlabelled; the pack stdout line is its count.
- **D7 — Per-claim, per-ref resolution; fact-only `since_last` claims are untouched.** The D3/D4 check runs for each cited metric ref of a `since_last` claim; every ref must resolve for the claim to render, and if the claim cites several metrics each line carries its own two values. A `since_last` claim citing no metrics renders exactly as today (its fact lines only). A metric cited by a non-`since_last` claim never triggers the lookup, even on a briefing that has a parent. Reason: the brief's requirement is about each cited metric's evidence line; inventing a failure for a claim with no metric line, or for a section the ticket does not touch, would shrink the denominator for no stated reason.
- **D8 — The start screen's new sentence, exact.** In [framework/rater/page.py:82](../../framework/rater/page.py), the last sentence of the periods paragraph ("A change since the previous card compares this card's number with the number on the card before.") is replaced by:

  `A line about a change since the previous card shows the number on the previous card and the number on this card, then the change. Each card counts its own three periods, so the same period name on two cards covers different hours.`

  The rest of the paragraph and page is unchanged. Reason: it says the two things the rater must know before judging such a sentence — that both values are shown, and that "the last period" on two cards is two different spans of hours, which is what makes the Deviation 17 sentence false rather than merely oddly worded. The existing page test's `"the card before"` assertion ([tests/test_rater_page.py:165](../../tests/test_rater_page.py)) names the old sentence and is updated to the new wording (D11); its other assertions (`three back-to-back 24-hour periods`, `most recent`, `all three together`) still hold.

Reason: the brief fixes the change at 3 but forbids Deviation 17's stored values (24 and 27, [docs/PREREG.md:189](../PREREG.md)); 6 and 9 are neither those nor the brief's illustrative 14 and 17, so no test can be mistaken for a replay of the real card.
- **D10 — No key, scorer or hash change.** The key file keeps its current fields; the changed evidence lines flow into `pack_hash` automatically because the hash covers the ordered `(item_id, text, evidence lines)` list ([framework/rater/pack.py:647-653](../../framework/rater/pack.py)). Reason: the hash's job is to prove the returned file belongs to this exact page; evidence that changed *should* change it, and the scorer's existing mismatch refusal already handles the rest.
- **D11 — Two existing tests are re-based, not weakened.** `test_since_last_signed_changes` ([tests/test_rater_pack.py:839-906](../../tests/test_rater_pack.py)) gains parent rows and snapshots so its three signed forms still render, and its assertions gain the full new lines alongside the existing signed-change substrings (which still appear verbatim at the end of each new line). `test_start_screen_explains_periods` ([tests/test_rater_page.py:159-165](../../tests/test_rater_page.py)) swaps the `"the card before"` assertion for fragments of the D8 sentence. No other existing test's assertions change; in particular `test_evidence_rendering_per_family` and `test_fact_only_claim_shows_fact_and_no_number` must pass untouched. Reason: both tests pin the exact behaviour this ticket replaces; leaving them as they are would leave the suite red, and loosening them would hide the change.
- **D12 — Implementation shape inside `pack.py`.** `_Candidate` gains the source row's parsed snapshot; `_candidates` adds `snapshot` to its `SELECT` ([framework/rater/pack.py:167-172](../../framework/rater/pack.py)). One lazily built parent index per `collect` call maps briefing id → list of parsed snapshots, built by scanning `proposal_results` (`rowid, briefing_json, snapshot`) on the copy in the `column_rows` style already used there, parsing each briefing with the same `Briefing.model_validate` the recovery path trusts.

def urllib_http_post(
    url: str, headers: dict[str, str], body: bytes

  (`data=body`, `method="POST"`; form bodies are built by callers with `urllib.parse.urlencode`.) Each poll/push constructor accepts the seams it uses — Spotify: `http_get: HttpGet = urllib_http_get`, `http_post: HttpPost = urllib_http_post`; ActivityWatch: `http_get` for AW reads and `http_post` for the ingest push — plus `now_fn: Callable[[], datetime]` defaulting to `lambda: datetime.now(UTC)`; `poll`/`collect` calls `now_fn` once and uses that instant as `collected_at` for every event in the batch. Missing required env raises `CollectorError("<collector>: <VAR> is not set")` — the message names the variable, never a value. Every collector raises `CollectorError` for bad statuses as `"<collector>: fetch failed (status <n>)"`, for the Spotify refresh as `"spotify: refresh failed (status <n>)"` (amendment A), and for unparseable bodies as `"<collector>: invalid response"`, always `from None`, never interpolating a URL, header value, secret, token, or body. Secrets and tokens (`SPOTIFY_CLIENT_SECRET`, `SPOTIFY_REFRESH_TOKEN`, the refreshed Spotify access token, `INGEST_TOKEN`) are held only in locals/headers and never appear in logs, cursors, stored data, pushed payloads beyond the bearer header, or exception text.
- **Event ids and emission order are deterministic.** Reuse `common.event_id(source, source_id)`. The Spotify poll sorts or preserves its pinned order before returning, because `run_collector` inserts in poll order and tests compare exact event lists. A fetch or parse failure raises out of `poll`/`collect`, so `run_collector` writes nothing and a push sends nothing — collectors do all fetching and parsing before returning/sending and never catch-and-return-partial on a fetch failure. Per-item skips for malformed entries inside an otherwise successful response are pinned per collector below; a skipped item is not a failed poll. The two push paths (health, `screen.hour`) are content-hash superseding instead: identical bytes re-delivered are store no-ops, changed content for the same logical slot mints a new `source_id` (Approach), and consumers resolve the slot by latest `collected_at` — stated in the `ingest.py` and `activitywatch.py` module docstrings.
- **Spotify (`spotify.py`, `SpotifyCollector`, `name="spotify"`, `version="spotify@0.1.0"`) — amendment A refresh flow.** There is no `SPOTIFY_ACCESS_TOKEN` env var, config key, or code path anywhere in this ticket.
  - Credentials (read at the start of `poll`, never at import/construction): `client_id = os.environ.get("SPOTIFY_CLIENT_ID")`, `client_secret = os.environ.get("SPOTIFY_CLIENT_SECRET")`, `refresh_token = os.environ.get("SPOTIFY_REFRESH_TOKEN")`; each missing/empty raises, in that check order, `CollectorError("spotify: SPOTIFY_CLIENT_ID is not set")` / `CollectorError("spotify: SPOTIFY_CLIENT_SECRET is not set")` / `CollectorError("spotify: SPOTIFY_REFRESH_TOKEN is not set")` — the message names only the variable.
  - Refresh first, on every poll: `auth = base64.b64encode(f"{client_id}:{client_secret}".encode()).decode()`; `form = urllib.parse.urlencode({"grant_type": "refresh_token", "refresh_token": refresh_token}).encode()`; `token_response = http_post("https://accounts.spotify.com/api/token", {"Authorization": f"Basic {auth}", "Content-Type": "application/x-www-form-urlencoded"}, form)`. `token_response.status != 200` → `CollectorError(f"spotify: refresh failed (status {token_response.status})") from None`. On `200` the body must decode as a JSON object with a non-empty string `access_token`, else `CollectorError("spotify: invalid response") from None`. Keep that access token in one local variable for this poll only: never stored on `self`, never put in the cursor, never logged, never formatted into any exception (always `from None`), and the class defines no `__repr__` carrying state. **Ignore any `refresh_token` field in the token response** (Spotify may rotate it; this ticket deliberately does not persist rotations — the operator's stored refresh token stays authoritative, and a rotation that invalidates it surfaces as a pinned refresh failure for the operator to re-run `ops/spotify-auth.md`). `client_secret` and `refresh_token` get the same local-only, never-logged, never-in-exception treatment.
  - Then fetch recently-played with the fresh token: URL is exactly `https://api.spotify.com/v1/me/player/recently-played?limit=50` plus `&after=<after_ms>` when the cursor holds one (below). Headers: `{"Authorization": f"Bearer {access_token}", "Accept": "application/json"}` via `http_get`. `status != 200` → `CollectorError(f"spotify: fetch failed (status {response.status})")`. Body must decode as a JSON object with an `items` list, else `CollectorError("spotify: invalid response") from None`.
  - Cursor: `{"after_ms": int | None}` (`None` cursor → `{"after_ms": None}`). Spotify's `after` is a Unix epoch **millisecond** cursor over `played_at`. On a `200`, the new `after_ms` is the maximum `played_at` epoch-ms among the items actually emitted this poll, or the previous `after_ms` when nothing is emitted, so a poll never moves the cursor backwards. The cursor holds no token material.
  - Mapping (API order is newest-first; the collector reverses to ascending before returning): skip silently any entry that is not a dict, lacks `track` dict, `track.id`, a non-empty `track.name`, or a parseable `played_at`. `track` name = `str(track["name"])`; `artist` = `str(track["artists"][0]["name"])` when a first artist with a name exists, else `""` is **not** allowed — skip the entry instead (an artist-less play has no signal and `MusicPlayData.artist` would carry an empty string). `played_at` parsed with `datetime.fromisoformat(value.replace("Z", "+00:00"))` (naive result → skip). Keep only plays whose epoch-ms is `> after_ms` when `after_ms` is not `None` (strictly newer; a play exactly at the cursor was already emitted). `source_id = f"{track_id}@{played_at_utc_iso}"` where `played_at_utc_iso` is `played_at.astimezone(UTC).isoformat()` — unique per play of that track, so a replayed track on another day is a new event and identical re-delivery under the same key is a store no-op. Envelope `time` = `played_at`, tier `"private"`, payload `MusicPlayData(track=…, artist=…, played_at=…)`. Track and artist names are the payload (PLAN §2.1 keeps them private-tier; §2.3 keeps them off the public tier, which `tier="private"` satisfies) — they are never printed by the CLI and never logged.

- **Ingest server (`ingest.py`, `source="health"` / `collector_version="health@0.1.0"` for health; amendment B rename, amendment E dating).** This is a push path, not a `Collector`: no `poll`, no cursor row. The module docstring states both supersede rules verbatim: health consumers take the latest `collected_at` per `(subject_id, date)` and `screen.hour` consumers take the latest `collected_at` per `(device, hour)` — because both `source_id`s are content-hashed, a correction is a new event, never an update and never a conflict.   - Health payload contract (what the Shortcut sends, documented in `ops/health-shortcut.md`): one JSON object `{"date": "YYYY-MM-DD", "sleep_h": …, "resting_hr": …, "hrv_ms": …, "steps": …, "exercise_min": …, "mindful_min": …, "daylight_min": …, "mood_valence": …}` where `date` is **yesterday in Europe/Madrid** at the 08:00 post (amendment E: the automation fires at 08:00 today and posts the just-completed day; `sleep` is the session that ended on the morning of `date`) and every metric is optional (omit or `null` when the device has no sample). Unknown keys are rejected (`extra="forbid"` via `HealthDailyData`), so a Shortcut drift fails loudly instead of silently storing a new field.
  - `parse_health_event(body: bytes, *, subject_id: str, now: datetime) -> Event`: decode UTF-8 JSON (failure → `CollectorError("health: invalid response") from None`); the top level must be an object with a `date` string parseable as `date.fromisoformat` (missing/malformed → same `CollectorError`); the remaining keys validate as `HealthDailyData` (a `ValidationError` → same `CollectorError`, with no field values interpolated). Build the event with: `time` = midnight Europe/Madrid on `date`, `data` = the validated `HealthDailyData`, `tier="sensitive"` (enforced by `Event` for `health.daily`), `collected_at = now`, and the amendment-E content-hash key: hash input is the canonical sorted JSON of the validated payload (`canonical_json(data.model_dump(mode="json"))`, the store's recipe — reuse `framework.store.store.canonical_json`, do not invent a second serialisation), `digest12 = hashlib.sha256(that_json.encode()).hexdigest()[:12]`, `source_id = f"health:{date_iso}:{digest12}"`, `id = event_id("health", source_id)`. Identical metrics for the same date therefore re-derive the identical `source_id` (store no-op); corrected metrics mint a new `source_id` for the same date (new event, no conflict, no `409`).
  - `ingest_health(store: EventStore, body: bytes, *, subject_id: str, now: datetime) -> bool`: parse, then `store.append_event(event)`; return `True` when inserted, `False` on identical re-delivery. Under the content-hash key a `ConflictingEvent` cannot occur for identical payload bytes, so it is not mapped to `409` anymore: if it ever propagates, the HTTP layer treats it as `400`. Ingest reads `subject_id` from `subject_id_from_env()` at call time in the CLI/handler wrappers, not inside `parse_health_event`.
  - `screen.hour` push contract (amendment B): `parse_screen_hour_events(body: bytes, *, now: datetime) -> list[Event]` decodes a JSON list (not a list, or any item failing below → `CollectorError("activitywatch: invalid response") from None`); each item must `Event.model_validate` **and** satisfy `type == "screen.hour"`, `source == "activitywatch"`, `tier == "private"` (any other `type`/`source`/`tier`, or a `ValidationError`, fails the whole batch). The validated events are returned as-is. `ingest_screen_hours(store: EventStore, body: bytes, *, now: datetime) -> tuple[int, int]` parses the whole batch first, then appends atomically (parsing completes before any append and any invalid item raises before the store is touched, so an invalid batch writes nothing); identical re-pushes count as not-inserted (store no-op). If a mid-batch store conflict raises, the whole batch rolls back per T4 semantics and the handler maps it to `400`.
  - HTTP layer (one server, two routes): `make_ingest_handler(store: EventStore, *, subject_id: str, now_fn: Callable[[], datetime], token: str) -> type[BaseHTTPRequestHandler]` (stdlib `http.server` only; no new dependency; `token` is a required `str`, not `str | None`) whose `do_POST` first requires the bearer header against `INGEST_TOKEN` (mismatch/missing → `401` with an empty body, before any routing or body read), then routes: `POST /health/daily` reads `Content-Length` bytes, calls `ingest_health`, answers `201` (inserted) / `200` (identical re-delivery) / `400` (`CollectorError`) with a counts-only body (never the payload); `POST /events/screen-hour` reads the body, calls `ingest_screen_hours`, answers `201`/`200` by the same inserted/no-op rule with a counts-only body, `400` on any invalid item with nothing written; any other path → `404` empty body. The handler never echoes a payload, a metric value, a window title, or the token, and its `log_message` is silenced. `serve_ingest(host: str, port: int, db_path: Path | None) -> None` reads `INGEST_TOKEN` from the environment at startup and **refuses to start without it** (missing/empty → raise `CollectorError("ingest: INGEST_TOKEN is not set")` before binding), then wires the handler to `ThreadingHTTPServer` for the store-host live step; the old name `serve-health` must not exist. Tests exercise the parse/ingest functions and the handler logic only through injected fakes or a `tmp_path` store, never by binding a socket. Binding beyond the serve call, TLS, and the timer are T13 ops, not this ticket.

The doc names no real host, port, token, or health value.
- **ActivityWatch (`activitywatch.py`, `ActivityWatchCollector`, `name="activitywatch"`, `version="activitywatch@0.1.0"`) — amendments B/C/D push path.** The module docstring states the supersede rule: consumers take the latest `collected_at` per `(device, hour)`; identical re-push is a no-op, late data mints a new event for that hour instead of a conflict. This collector does **not** implement the store `Collector` cursor protocol and is never run through `run_collector` against a local DB: it runs on the Mac (where AW listens on `127.0.0.1`) and the store lives on another host, so its output goes to `push` (below). Its testable core is `collect(now: datetime) -> list[Event]` (plus the `Collector`-shaped attributes `name`/`version` for version stamping); `poll(cursor)` must not exist — the window is stateless.
  - Fetch: `base = os.environ.get("AW_BASE_URL") or "http://127.0.0.1:5600"` (a local default, not a secret; the value never appears in exception text — errors use the pinned `activitywatch: …` messages). The collector first GETs `{base}/api/0/buckets/` — **trailing slash required** (without it AW answers `308`; the fake in tests asserts the slashed URL exactly) — headers `{}`; body must be a JSON object mapping bucket id → bucket object, else `CollectorError("activitywatch: invalid response") from None`; a non-`200` buckets response → `CollectorError(f"activitywatch: fetch failed (status {status})")`. It selects: window buckets whose id starts with `aw-watcher-window` (`device="mac"`), the AFK bucket whose id starts with `aw-watcher-afk` (amendment C), and Screen Time import buckets whose id contains `screentime` or `screen-time` or `iphone` (case-insensitive; `device="iphone"`) — decision 2's arrival path. **No window bucket → error**: raise `CollectorError("activitywatch: fetch failed (status 404)")`-shaped failure via the pinned fetch-failed form (AW not running is an operator-visible error on the Mac, not a silent no-op); **no Screen Time bucket → fine** (simply no `iphone` events this poll); a missing AFK bucket is treated as no `not-afk` intervals (Mac minutes all clip to zero for the affected hours — see clipping — rather than erroring, so an AFK-watcher gap degrades visibly in the data). For each selected bucket it GETs `{base}/api/0/buckets/{bucket_id}/events?start={start_iso}&end={end_iso}&limit=-1` over the window below; any non-`200` events call → `CollectorError(f"activitywatch: fetch failed (status {status})")` and the whole collect fails before anything is built or pushed.
  - Stateless rolling window (amendment B, no cursor): `now` from `now_fn`; `window_end` = the last complete hour boundary `<= now` in UTC; `window_start = window_end - 48h`. Every collect covers the last **48 complete UTC hours** `[window_start, window_end)`. There is no cursor value, no cursor row, and no `last_hour_end`: re-collecting the same 48 h re-derives the same events (identical minutes → identical `source_id` → server-side no-op), and hours that gain late data (Screen Time import arriving later, laptop off overnight then on) re-derive with different minutes → a new `source_id` for the same `(device, hour)` → a new event that supersedes by `collected_at`, never a conflict. Hours older than 48 h are never re-emitted.
  - AFK clipping (amendment C, Mac only): from the `aw-watcher-afk*` bucket events (each with `timestamp`, `duration` seconds, `data.status`), build the `not-afk` intervals `[timestamp, timestamp + duration)` keeping only `data.status == "not-afk"` (every other status, and malformed AFK events, contribute no interval). Each Mac window event's counted time is the total **overlap** of `[timestamp, timestamp + duration)` with the union of `not-afk` intervals, **split at UTC hour boundaries**: an overlapped span crossing an hour boundary contributes its minutes to each hour it touches. iPhone Screen Time events are counted **as-is** (already real usage; no AFK bucket applies, no clipping, but their durations are still split at UTC hour boundaries for the hourly roll-up — "as-is" governs the AFK rule, not the bucketing).
  - Aggregation (decision 3 — the privacy boundary; amendment D categories): each window/Screen Time bucket event is a dict with `timestamp` (ISO), `duration` (seconds, number), and `data` (dict). Only `data.app` (a string) is read, only to classify; `data.title`, `data.url`, and every other `data` key are never read into any variable that leaves the function, never stored, never pushed, never logged. Skip an event silently when `timestamp` is unparseable, `duration` is not a positive number, or `data.app` is missing/not a string. **Category table (amendment D)** — substring match on the **lower-cased app string only** (bundle-id style values such as `com.apple.MobileSMS` lower-case to `com.apple.mobilesms` and match by the same substrings; never match on a title or URL), **first match wins in exactly this order**:
    1. **skip (not counted at all)**: `sleeplockscreen`, `springboard`, `control-center`, `loginwindow`, `screensaver` — the event contributes zero minutes to every category (it is not `other`).
    2. `code`: `code`, `cursor`, `pycharm`, `xcode`, `iterm`, `terminal`, `ghostty`, `warp`, `vim`, `emacs`
    3. `comms`: `slack`, `discord`, `zoom`, `teams`, `mail`, `messages`, `mobilesms`, `mobilephone`, `facetime`, `incallservice`, `whatsapp`, `telegram`
    4. `feed`: `tweetie2`, `twitter`, `reddit`, `instagram`, `tiktok`, `linkedin`
    5. `browse`: `safari`, `chrome`, `firefox`, `microsoft edge`, `browser`
    6. `media`: `spotify`, `music`, `youtube`, `vlc`, `quicktime`, `podcast`, `netflix`
    7. `other`: everything else.
    Sum the counted (post-clipping, post-split) `seconds / 60` minutes per `(device, hour_start, category)`; drop zero totals and drop hours whose categories all total zero. One `Event` per remaining `(device, hour_start)`: payload `ScreenHourData(device=…, minutes_by_category={category: minutes, …})`, envelope `time` = `hour_start`, tier `"private"`, `subject_id` from `subject_id_from_env()` at collect time, `collected_at = now`. Content-hash key (amendment B): `sorted_minutes_json = json.dumps(minutes_by_category, sort_keys=True, separators=(",", ":"))` (keys sorted, the same compact recipe shape as the store's canonical JSON — state the literal recipe in code, do not import a second serialisation), `hash12 = hashlib.sha256(sorted_minutes_json.encode()).hexdigest()[:12]`, `source_id = f"{device}:{hour_start_utc_iso}:{hash12}"` where `hour_start_utc_iso` is `hour_start.astimezone(UTC).isoformat()`, `id = event_id("activitywatch", source_id)`. Events sorted by `(time, device)` before returning. Fixtures use bundle-id style apps too (e.g. `com.apple.MobileSMS`, `com.tweetie2` — invented/synthetic bundle ids only) and never a real device UUID anywhere (no UUID-shaped string appears in any fixture, bucket id, or `source_id`).
  - Push (amendment B): `push_events(events: list[Event], *, ingest_url: str, token: str, http_post: HttpPost) -> tuple[int, int]` POSTs `json.dumps([e.model_dump(mode="json") for e in events]).encode()` to `{ingest_url.rstrip("/")}/events/screen-hour` with headers `{"Authorization": f"Bearer {token}", "Content-Type": "application/json"}` via the injected `http_post`; any non-`2xx` → `CollectorError(f"activitywatch: fetch failed (status {status})") from None` (the pinned fetch-failed form; the URL and token never appear in the message). On `2xx` the body is a counts-only response; the CLI prints the local counts (below) and does not echo the body. An empty `events` list is still pushed (the server answers counts with zero inserted) so a quiet 48 h is distinguishable from a failed push only by the success status — or, equivalently, the CLI may skip the POST and print zero counts when there is nothing to push; pick the still-push behaviour so the server round-trip is exercised, and pin it in the test.

## Risks

- **Spotify secrets leaking, and rotation invalidating the stored refresh token (amendment A).** Three secrets now exist (`SPOTIFY_CLIENT_SECRET`, `SPOTIFY_REFRESH_TOKEN`, and the per-poll access token) plus the client id. Mitigated by construction: all held only in `poll` locals/headers, every raise uses `from None` with a secret-free pinned message (`spotify: refresh failed (status <n>)` / `spotify: fetch failed (status <n>)` / variable-name-only missing-env errors), nothing logs in `framework/collectors/`, the cursor holds only `after_ms`, and AT3/AT4 assert no credential or token string appears in events, cursor, exception text, or `caplog`, and that a refresh failure issues no recently-played call and writes nothing. Rotation: Spotify may return a new `refresh_token`; this ticket **ignores** it by decision, so if Spotify invalidates the old token on rotation, polls start failing with the pinned refresh error and the operator re-runs the one-time flow in `ops/spotify-auth.md` (which is why that doc exists and contains no values). Persisting rotations would need a writable secret store outside the repo — deliberately not built.
- **`http_post` widening the leak surface (amendment A).** A shared POST seam that echoed URLs, headers, or bodies on error would leak the token endpoint's Basic header and the ingest bearer. Mitigated by giving `urllib_http_post` the identical discipline as `urllib_http_get` (HTTPError → response for caller handling, network errors → bare `CollectorError("network error") from None`), by pinning every caller's error messages, and by the fake-`http_post` tests asserting request shape without ever logging values. Gitleaks covers the committed tree; fixture secrets are `synthetic-*` strings.
- **Spotify `after` cursor missing plays at the same millisecond.** The strictly-newer filter (`> after_ms`) can drop a second play sharing the newest millisecond. Accepted for wave 2: plays at identical ms are rare, the store's `(source, source_id)` dedupe already makes exact re-delivery safe, and widening to `>=` would re-emit the boundary play every poll (still correct via store no-op, but noisier). Noted here so review sees the trade.
- **Health corrected re-post superseding (amendment E) vs append-only history.** The content-hash key means a correction does not overwrite — it adds a second `health.daily` event for the same date, and "the value for that date" is defined as the latest `collected_at`. A consumer that naively takes the first event (or sums both) reads stale or doubled health data. Mitigated by stating the latest-`collected_at`-per-date rule in the `ingest.py` docstring, in `ops/health-shortcut.md`, and in Success Criteria, and by AT7 resolving the date that way. This replaces the earlier `409` design: a `409` made a Shortcut correction an operator incident, while health aggregates are exactly the data that gets corrected when the phone finishes syncing.
- **Ingest endpoint exposure (amendment B).** One server now accepts health data **and** `screen.hour` events from two different producers (phone Shortcut, Mac push). Mitigated in this ticket: `INGEST_TOKEN` is **required** — `serve-ingest` refuses to start without it (it is no longer an optional check), every request is bearer-checked before routing, the `screen-hour` route validates the whole batch before writing anything (any invalid item → `400`, zero writes), responses are counts only, `log_message` is silenced, and no payload/title/metric is ever echoed or logged. The server is a manual store-host step (binding/TLS/firewall are T13 ops); the docs use placeholder endpoints so no real host, port, or token is committed. Review must confirm no fixture or doc contains a real token or health value (step 7 sweep + gitleaks).
- **ActivityWatch bucket/API shape drifting, including the trailing slash (amendment B).** Bucket ids (`aw-watcher-window_<host>`, `aw-watcher-afk_<host>`, Screen Time import ids) and the events response shape vary by AW version and host, and the bucket-list endpoint `308`-redirects without the trailing slash (a redirect the stdlib client may not follow for this API, surfacing as a spurious failure). Mitigated by discovery (prefix/contains matching, never an exact host-suffixed id), by pinning `{base}/api/0/buckets/` with the slash in code and asserting it in AT11's fake, and by the injected `http_get` seam pinning both request URLs in tests. The live shape is confirmed by Carlos's post-merge push; a mismatch is a plan amendment, not a silent fixture change.
- **No window bucket is now an error, not a no-op (amendment B).** If ActivityWatch is not running on the Mac, `push activitywatch` fails loudly instead of silently succeeding — deliberate, so a dead AW on the Oct 30 timer is visible the same night rather than as a week of missing screen data. The cost is a failed push job on nights the Mac is asleep/off; that failure is the signal. No Screen Time bucket stays a success (the import is a Could).
- **AFK clipping understating or overstating Mac minutes (amendment C).** If the AFK watcher lags, is missing, or reports long `not-afk` spans across sleep, clipped minutes skew. Mitigated by construction: only positive overlaps with `not-afk` count, a missing AFK bucket yields zero (visible as empty hours, not silently unclipped totals), splitting is exact interval arithmetic pinned in AT9, and iPhone minutes are never AFK-adjusted. An operator who runs without the AFK watcher gets no Mac screen signal until it is enabled — accepted, because unclipped window time (locked screen, away) is the worse error for this signal.
- **Category mapping misclassifying or skipping real usage (amendment D).** The pinned substring table will misfile some app, first-match order decides deliberate collisions, and the skip list (`loginwindow`, `springboard`, …) drops events that might occasionally wrap real usage. Accepted for wave 2: the signal is per-category minutes for attention patterns, not an audit; the table (including the skip list and the new `feed` category) is pinned in one place in `activitywatch.py`, covered exhaustively in AT10 (including bundle-id forms and a two-category collision), and widened only by amendment. Matching on the lower-cased `app` only (never title/URL) is the privacy rule (decision 3), not an accuracy choice — a title-based classifier is rejected outright.
- **Stateless 48 h re-push and latest-wins resolution (amendment B).** Every `push` re-sends up to 48 hours of events; identical hours no-op on the server, changed hours supersede. A consumer that reads all `screen.hour` events without resolving latest `collected_at` per `(device, hour)` double-counts corrected hours. Mitigated by the content-hash `source_id` (a changed hour is visibly a *different* event for the same hour, not a store conflict that would hide it), by stating the rule in the `activitywatch.py` and `ingest.py` docstrings and Success Criteria, and by AT11 exercising the re-derivation. The 48 h bound means data older than 48 h when the Mac first comes back (a long weekend off) never arrives — accepted; lengthening the window is a one-constant amendment if the stream shows gaps.
- **iPhone Screen Time import not actually present (decision 2).** SPEC moves Screen Time to Could on the strength of AW's import; if the operator's AW has no such bucket, the collector simply emits no `iphone` events (AT11 success case) and the Could stays unexercised — no failure, no fake data. The SPEC wording says "arrives via" the import, which this collector implements; whether the import is enabled is an operator step recorded in the evidence note, not code.
- **`daylight_min` export touching more than two schema files.** Regenerating after a one-field change should diff only `HealthDailyData.json` and the embedding `Event.json`. Step 2 stops and reports if any other `schemas/*.json` changes (that would mean unrelated model drift), rather than committing a wide regeneration. The drift test (AT1) then guards the field permanently.
- **Decision-5 caches landing outside the repo.** Running `uv`/`pre-commit` without the prefix would populate the operator's global caches and could pick up a foreign pre-commit home. Mitigated by pinning `PRE_COMMIT_HOME="$PWD/.git/pre-commit-home" UV_CACHE_DIR="$PWD/.git/uv-cache"` on every `uv` invocation in Steps and on the commit itself (step 9, AT13), with `.gitignore` already covering the resulting dirs. The evidence note records the exact command as run.

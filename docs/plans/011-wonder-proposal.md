## Success Criteria

- **Pure core, one edge client.** New `framework/proposal/`: a pure core with no wall clock, no env read, and no network except through an injected client, mirroring [framework/glimmer/facts.py:1-6](../../framework/glimmer/facts.py); an edge client in `framework/proposal/client.py` is read only at the CLI/`run_proposals` seam. HTTP is stdlib `urllib` only; no new dependency in `pyproject.toml`/`uv.lock`.
- **The hour is code's job.** `pick_hour` is pure, stays inside the slot's local day (A7/D3), returns the first free hour-long block at a quarter hour at or after the slot inside the allowed window, or `None`. It is picked once per slot, shared by both profiles. No free hour means kind `noop` with its own reason and zero model calls.
- **Future busy intervals.** Busy intervals come from `future_busy_intervals` (A6/D4): winners first, then cancelled/non-busy/zero-length dropped, then overlap with `[min(as_of, slot), max(as_of, slot) + 24h)`, unclipped, over rows loaded `as_of - 31 days` to `as_of + 31 days` on event `time`.
- **Narrow draft, per-call schema.** `ProposalDraft` carries only `commitment_id` and `ClaimDraft{text, fact_ids, metric_refs}` (metric refs are id strings, A2) lists for `overall_state`, `working`, `not_working`, `since_last`. Frozen, extra-forbid, every field required recursively in the exported JSON schema (tested). The per-call response schema is hand-built inline by `build_response_schema` (A1/D7): no `$defs`, no `title`, never `enum: []`, never `maxItems: 0`; an empty id list means the property is left out and code inserts `[]` before validation.
- **Assembly in code.** `assemble_briefing` is pure and fills briefing id, profile, subject, slot, parent id, claim ids, and the action's kind, text, dimension, `commitment_id`, start, and end from the commitment and the picked hour. Each ref's `value` comes from the snapshot (or the offered current-minus-parent delta in `since_last`) at full precision, never from the model. It dedupes `fact_ids`/`metric_refs` within a claim, keeping order (A2). An unknown commitment id reaches the gate as `L1_ACTION_NOT_COMMITTED`, not an exception (D9).
- **Evolution since the last card.** With a parent, code offers only gate-acceptable deltas (A3/D12), requires at least one `since_last` claim citing one, and the prompt/schema carry `since_last`. With no parent — or a parent with no offerable delta, run as no-parent with `PARENT_WITHOUT_DELTAS` (A3) — `since_last` is absent from the schema, the assembled briefing omits the section, and `parent_briefing_id` is `None`.
- **Prompt.** Pure `build_prompt` with the exact template printed in D13 and exact rendered outputs for the frozen fixture in both shapes: purpose paragraph, rules checked against the merged gate, facts by id and statement only, metrics as one JSON line each with gate labels, deltas if any, eligible commitments by id/title/kind/dimension, an opaque policy string defaulting to `""`, the profile name, and the hour. Every data block sits between delimiters and is declared data. No private profile text, no evidence ids, no raw events.
- **One guarded client.** Every Meta request goes through one class that scans the full outbound text before sending (A4/D18: allowlisted codes only; the repo check runs on eligible titles in `propose`, not on the whole prompt) and owns the only network calls to Meta in `framework/proposal/` (local `_open_no_redirect` opener; source-scan test). A failed scan sends nothing, logs the attempt as blocked with codes only, and returns a noop with no retry. Private terms unavailable blocks too. Any model id containing `contributor` is refused at the client and, in the CLI, before anything else (A17).
- **Models are parameters.** First-attempt and retry model/effort travel in one frozen `ModelParams` (A10/D26), defaults `muse-wonder-1.0` at `high` for both, read at the CLI edge. `MetaClient` has no `model` constructor argument; each request names its model (A17). Nothing else in the package assumes Wonder. `max_tokens` is 32768.
- **Retry, then fallback.** Exactly one retry via `repair_loop` in `framework/verify/repair.py` (A5/D24: Ticket 17a's `Attempt`/`FailedValidation`/`RepairResult` shape), with violation codes, locations, and messages that never echo matched content, plus the D25/A13 claim-id line. No eligible commitment, no hour, a slot outside allowed hours, or no evidence (`FALLBACK_NO_EVIDENCE`, A1) means noop or the A1 fallback as pinned in D15/D8, never a wasted call. `ProposalResult.kind` is one of `"proposal"`, `"fallback"`, `"noop"`.
- **Persistence, append-only.** A sibling store `framework/store/proposal_store.py` in the same database file records every attempt and every result (D23), keyed by subject as well as profile (A16). `first_draft_report()` (A15) computes the R1 first-draft failure report from SQL in a named constant. Raw text and prompts stay local and never print.

"Delivered" is Ticket 13's knowledge through the `parents` argument; the CLI treats the latest stored proposal as delivered (stated plainly in D12 and "What Ticket 13 calls").

## Approach

### Key decisions (binding on the implementer; each with its reason)

- **D1, layout mirrors Glimmer.** `framework/proposal/` holds `schemas.py` (draft, fallback, per-call schema, parsing), `hour.py` (`pick_hour`, `future_busy_intervals`, `allowed_windows`, fallback window check), `prompt.py` (`build_prompt`, `compute_deltas`, `Delta`), `assembly.py` (`assemble_briefing`), `core.py` (`propose`, `ProposalResult`, client protocol, error types), `client.py` (edge `MetaClient`, config loader), and `__init__.py` re-exports. Reason: [framework/glimmer/facts.py:3-5](../../framework/glimmer/facts.py) already proves the pure-core-plus-injected-client split in this repo, and the brief requires the same shape, so reviewers get one pattern, not two. The store is `framework/store/proposal_store.py`, a sibling of [framework/store/fact_store.py](../../framework/store/fact_store.py), in the same database file. The seam `run_proposals` joins `run_cycle` in [framework/cycle/__init__.py](../../framework/cycle/__init__.py) (D14/A10), and the CLI subcommand joins `facts` in [framework/cycle/__main__.py](../../framework/cycle/__main__.py), which today registers exactly one required subparser ([framework/cycle/__main__.py:43-50](../../framework/cycle/__main__.py)); `propose` is added beside it and the `facts` line format does not change.
- **D2, tiers: `public` and `private` facts are sent as statements; `sensitive` facts are never sent and never citable.** Reason: `Fact.tier` is `Literal["public", "private", "sensitive"]` ([framework/schemas/base.py:6](../../framework/schemas/base.py), carried on [framework/schemas/core.py:29](../../framework/schemas/core.py)), and Wonder is an external API while raw rows stay local; Glimmer's own checks already keep private free text out of statements (kept-row leak check, [framework/glimmer/checks.py:227](../../framework/glimmer/checks.py)), so a `private` statement is the designed abstraction boundary, while a `sensitive` statement has no such need. Mechanism: `run_proposals` filters fetched facts to `tier in ("public", "private")` before the core sees them; the fact-id `enum`, the prompt fact list, and `GateContext.facts` all contain only those facts, so a claim citing a withheld fact fails `L1B_UNKNOWN_FACT` at [framework/briefing/gate.py:741-751](../../framework/briefing/gate.py) instead of leaking. Note for the implementer: on today's code a `sensitive` fact should not exist, because `extract_facts` only mints facts from allowlisted event types ([framework/glimmer/facts.py:39-51](../../framework/glimmer/facts.py) excludes `health.daily` and `app.journal`, the two sensitive types at [framework/schemas/events.py:212](../../framework/schemas/events.py)), and tier is the highest evidence tier ([framework/glimmer/checks.py:33-34](../../framework/glimmer/checks.py)). The exclusion is defence in depth for rows written by any other producer, and a test pins it.
- **D3, `pick_hour(slot, busy_intervals, limits) -> TimeInterval | None` is pure, in `hour.py`, and stays inside the slot's local day (A7).** Same signature as before. Algorithm: the candidate starts at the slot rounded up to the next quarter hour **in the local zone** (`limits.timezone`); a slot already on a quarter hour starts at itself; seconds count, so 15:15:01 starts at 15:30. The candidate block is `[start, start + 1h)` computed **in UTC**, so a DST change cannot make a block longer or shorter than an hour. A block is accepted iff it lies fully inside **the slot's local day's** `[allowed_start, allowed_end)` window (ending exactly at `allowed_end` is inside, half-open) and overlaps no busy interval under the gate's own overlap test `start < busy.end and busy.start < end` ([framework/briefing/gate.py:196](../../framework/briefing/gate.py)); otherwise the candidate advances 15 minutes. There is **no next-day jump**: a candidate past the slot's day's `allowed_end` ends the search and the function returns `None`. Reason (A7): a 22:30 card proposing tomorrow's 13:00 is not "the next free hour", and the next day's 13:30 card covers it, so `None` is the honest answer when today's window has no free hour; this also removes the old D3/D4 horizon mismatch (the search no longer runs to `slot + 24h` while busy data stops earlier). A test crosses 2026-10-25 (the Europe/Madrid DST fall-back) in `tests/test_proposal_hour.py`. New public `allowed_windows(slot, limits) -> tuple[TimeInterval, ...]` in `hour.py` returns the slot's local day's allowed window as UTC intervals and supplies the gate's `free_intervals` (D5), so `pick_hour`, the gate, and the fallback check read one construction. The hour is picked once per slot in `run_proposals` and the same `TimeInterval` is passed to both profiles' `propose` calls, because both goals compete for that same hour. With `None`, each profile's result is `noop` with reason `NOOP_NO_FREE_HOUR` and the client is never called (case P8).
- **D4, future busy intervals: winners first, then filter, then overlap (A6).** Pure function in `hour.py`: `future_busy_intervals(events, *, as_of, slot) -> tuple[TimeInterval, ...]`, steps in this exact order: (1) keep `collected_at <= as_of`; (2) `select_winners` ([framework/glimmer/metrics.py:49-60](../../framework/glimmer/metrics.py), greatest `collected_at`, then greatest `id`), imported, never forked; (3) drop cancelled, non-busy, and zero-length winners — zero-length must be dropped here because `CalendarEventData` allows `end == start` ([framework/schemas/events.py:22-26](../../framework/schemas/events.py)) while `TimeInterval` raises on it ([framework/briefing/context.py:29-31](../../framework/briefing/context.py)); (4) keep what overlaps `[min(as_of, slot), max(as_of, slot) + 24h)`, **unclipped**. The old D4 order (overlap before winners) is wrong: filtering on overlap before picking winners lets a stale row win. The query in `run_proposals` is `events_between(subject_id, as_of - 31 days, as_of + 31 days, types=("calendar.event.created", "calendar.event.updated", "calendar.event.cancelled"))` ([framework/store/store.py:280-305](../../framework/store/store.py) filters on event `time` in `[start, end)` only). The wide query is required because a recurring override keeps its logical key while its `time` moves ([framework/collectors/calendar_ics.py:186-189](../../framework/collectors/calendar_ics.py) for the key `f"{uid}@{rid}"`, [framework/collectors/calendar_ics.py:36-37](../../framework/collectors/calendar_ics.py) for the collector's −2/+14 day collect window): the row that moved an event out of the window sits past `as_of + 24h` and must load, or the old row wins and blocks a free hour. Tests in `tests/test_proposal_hour.py`, each failing under the old order: moved out of the window, moved into it, cancelled, updated (counted once), collected after `as_of`, zero-length, running since before `as_of`, ending exactly at `as_of`. Gate context `free_intervals` are `allowed_windows(slot, limits)` (D3) and `busy_intervals` are these intervals; busy takes precedence in the gate at [framework/briefing/gate.py:196-202](../../framework/briefing/gate.py).
- **D5, gate context construction is pinned, fail-closed on all four availability inputs.** Per profile, `run_proposals` builds `GateContext` with: `facts` keyed by `Fact.id` (the validator at [framework/briefing/context.py:95-101](../../framework/briefing/context.py) rejects any other keying) containing only the D2-eligible facts; `metrics` from the cycle's snapshot (`MetricSnapshot(values=...)` over `fetch_cycle(...)["snapshot"]`); `parent_briefing` and `parent_metrics` both set from the parent (D12) or both `None` — the pair validator at [framework/briefing/context.py:103-109](../../framework/briefing/context.py) raises on a half-set pair, and both are forced `None` in the `PARENT_WITHOUT_DELTAS` arm (D12); `free_intervals`/`busy_intervals` from D4/D3; `limits` from D28; `private_terms` plus `private_terms_available` from `load_private_terms` ([framework/briefing/context.py:129-171](../../framework/briefing/context.py)); `forbidden_raw_literals` from D17; `commitments` holding **the eligible commitments for this profile only** (A9), not the whole registry, with `commitments_available=True`, so a draft picking a commitment that exists but is not eligible fails `L1_ACTION_NOT_COMMITTED` (case P35). Both availability flags matter because their defaults fail closed: `private_terms_available` defaults `False` at [framework/briefing/context.py:89](../../framework/briefing/context.py) and the gate then emits `L1_PRIVATE_TERMS_UNAVAILABLE` at [framework/briefing/gate.py:418-426](../../framework/briefing/gate.py); `commitments_available` defaults `False` at [framework/briefing/context.py:93](../../framework/briefing/context.py) and the gate emits `L1_COMMITMENTS_UNAVAILABLE` and skips per-action checks at [framework/briefing/gate.py:442-451](../../framework/briefing/gate.py). Leaving either unset makes every card fail, which is the Ticket 10 review finding this ticket designs for.
- **D6, `load_commitments` is always called with `private_terms` passed in.** The loader's signature is `load_commitments(environ, *, private_terms=(), forbidden_raw_literals=())` ([framework/briefing/commitments.py:45-50](../../framework/briefing/commitments.py)) and it validates every title through `text_check_codes` plus `action_targets_repo` at [framework/briefing/commitments.py:91-99](../../framework/briefing/commitments.py), rejecting the whole file as `title_failed` on any hit. The CLI therefore loads private terms first and passes them (and the D17 literals from `forbidden_literals_for`) into `load_commitments`. Reason: with the default empty `private_terms`, a title carrying a private term loads fine and then fails every card at the gate with `L1_PRIVATE_TERM`; loading with the terms turns that into one loud `title_failed` at startup, surfaced by the CLI as exit 2 with `error: commitments unavailable: <closed reason>` and no path (A17/D29). If private terms are unavailable, the terms tuple is empty at load and the outbound scan blocks before any send anyway (D18), so nothing reaches Meta on a guess. Note the second lock in A4/D18: even a title that loads, `propose` re-checks eligible titles for the repo and blocks before the first send, for library callers who did not load through this loader.
- **D7, the narrow draft, the per-call response schema, and parsing (A1, A2).** In `framework/proposal/schemas.py` on `SchemaModel` (frozen, extra-forbid, [framework/schemas/base.py:11-12](../../framework/schemas/base.py)):

```python
class ClaimDraft(SchemaModel):
    text: NonEmptyStr
    fact_ids: list[NonEmptyStr]
    metric_refs: list[NonEmptyStr]  # metric id strings only; code fills the value (D9)


class ProposalDraft(SchemaModel):
    commitment_id: NonEmptyStr
    overall_state: list[ClaimDraft]
    working: list[ClaimDraft]
    not_working: list[ClaimDraft]
    since_last: list[ClaimDraft]
```

  There is no `MetricRefDraft` (A2: metric refs are id strings). No field carries a default, so Pydantic puts every property in `required`; a test walks `ProposalDraft.model_json_schema()` recursively (including `$defs`) and asserts `set(properties) <= set(required)` at every object level — the exported models keep this all-required recursive test, which is the exact property whose absence broke the `Briefing.json` response schema. Only three draft/fallback models join `EXPORTED_MODELS` ([framework/schemas/export_schemas.py](../../framework/schemas/export_schemas.py)): `ProposalDraft`, `ClaimDraft`, `FallbackProposal` — three generated schema files, not four — and their `schemas/*.json` are generated, never hand-edited. The model never returns a metric value, a claim id, an action field, or a slot.
  The per-call response schema is **hand-built inline** by `build_response_schema(*, commitment_ids, fact_ids, snapshot_metric_ids, delta_metric_ids, has_facts, has_metrics, has_parent) -> dict` in `schemas.py`: a plain `dict`, no `$defs`, no `title` anywhere, sent as `response_format` with name `proposal_draft`. It never sends `enum: []` or `maxItems: 0` — the measured table shows both are unsafe (`enum: []` reads as a server error; `maxItems: 0` ran away once in five and produced garbage text in three of five on a string array) — and a test asserts neither shape (`"enum": []`, `"maxItems": 0`, and the bare tokens `enum.*\[\]`/`maxItems: 0` as they would serialise) can appear in the serialised schema for any input, including all-empty inputs. When a list of ids is empty the property is **left out of that schema** (measured: 8 of 8 fine, the property absent from the answer) and code inserts `[]` before validating against `ProposalDraft`: no parent ⇒ `since_last` absent; no facts ⇒ `fact_ids` absent from every claim; no metrics ⇒ `metric_refs` absent from the non-`since_last` claims; no facts **and** no metrics ⇒ no claim could carry evidence, so **no model call is made** and the result is a fallback with `FALLBACK_NO_EVIDENCE` (D15, case P36). With no cycle at all for the subject (and no `--cycle-id`), `run_proposals` records per profile a noop with `cycle_id` `"no-cycle"`, run 0, code `NO_CYCLE` (A16) and the CLI prints the per-profile noop lines and exits 0, because a scheduled step must not crash the loop for missing data — the orchestrator (T13) reads the printed codes.
- **D28, profile limits are CLI parameters; markdown is never parsed.** `GateContext.limits` needs a typed `ProfileLimits`, and the gate never parses markdown ([framework/briefing/context.py:53-54](../../framework/briefing/context.py)), and this repo has no typed per-profile limits source. The CLI therefore builds one `ProfileLimits` from `--timezone` (default `Europe/Madrid`), `--allowed-start` (default `13:00`), `--allowed-end` (default `23:30`), `max_actions=3`, matching the fixture limits at [evals/briefing_cases.py:109-115](../../evals/briefing_cases.py), and passes the same limits to both profiles and to the single shared `pick_hour` call. Per-profile windows are Ticket 13's job (see "What Ticket 13 calls": one set of limits for both profiles, so Disconnect's own evening limits and which profile runs at which slot are its job). The same limits object feeds the gate's slot check (via `slot_window_codes`, D18), `pick_hour`, and the fallback window check, so the three can never disagree.
- **D29, CLI line and exit codes (A17).** `python -m framework.cycle propose` is a thin wrapper over `run_proposals` (D14). It prints exactly one line per requested profile, in the order the `--profile` flags were given (defaults `builder`, `disconnect`): `profile=<id> kind=<proposal|fallback|noop> attempts=<n> codes=<comma-joined sorted unique codes or -> seconds=<sum of attempt latencies, one decimal>s tokens=<sum of completion tokens, 0 when unreported> stale=<cycle_age_s as integer seconds or ->`. Codes are the result's `reason_codes` plus every attempt's codes, de-duplicated and sorted, so a blocked, stale, or fallback outcome is visible from codes alone. Nothing else is printed on stdout; claim text, commitment titles, fact statements, prompts, raw responses, and cycle ids beyond what the line carries never appear (a test asserts fixture marker strings are absent). Exit codes: **2** for operator errors — a model id containing `contributor`, refused first of all through `refuse_contributor_model` (D19); an unset `META_API_KEY`, `HIDDEN_CRITERIA_DIR`, or `IKIGAI_COMMITMENTS_FILE`, each naming only the variable; a naive or unparsable `--as-of`/`--slot`; a missing subject — `--subject-id` or `IKIGAI_SUBJECT_ID` is required, following [framework/cycle/__main__.py:51-65](../../framework/cycle/__main__.py); a bad `--timezone` or an `--allowed-start` not before `--allowed-end`, each printing one fixed line naming the flag from the module-level `parse_proposal_limits` (no nested imports, no `SystemExit`, pydantic text never reaches stderr); an unknown `--cycle-id`, including a named cycle that belongs to another subject, which raises `UnknownCycleError` in `run_proposals` exactly like an unknown cycle; `load_commitments` returning `available=False`, printed as `error: commitments unavailable: <closed reason>` with no path; a model id containing `contributor`, before anything else, through `refuse_contributor_model` (D19); and a `MetaConfigError` from `load_meta_config`, caught in `main`, printed to stderr naming only the variable, `return 2`. **Not an exit:** `HIDDEN_CRITERIA_DIR` set but its terms unavailable — the run goes on to blocked noops, because that is the fail-closed path the brief pins (D18). **1** only for unexpected exceptions: the existing `error: <TypeName>` line, exit 1, as at [framework/cycle/__main__.py:71-73](../../framework/cycle/__main__.py); no traceback, because pydantic's messages echo inputs and titles and statements must never print. **0** otherwise, including all-noop runs. Env is read only in `main`: `META_API_KEY` via `load_meta_config`, `IKIGAI_COMMITMENTS_FILE` and `HIDDEN_CRITERIA_DIR` via their existing loaders, `IKIGAI_SUBJECT_ID` as in the facts CLI. Ordering inside `main` is fixed: refuse contributor models first of all, before the environment checks; check the three variables; resolve subject and instants; parse the limits before any store opens; load private terms; load commitments with those terms (D6), exiting 2 if unavailable; build the client; then call `run_proposals`, recording inside it, and print one line per returned result.
- **D30, the live acceptance test sets its own world (A21, A22).** `tests/test_proposal_live.py` holds one test, marked with `pytest.mark.skipif` on the env var `IKIGAI_PROPOSAL_LIVE` not equal to `1`, so `make check` skips it by default. When enabled it **builds synthetic deny terms in `tmp_path` and uses [profiles/commitments.example.json](../../profiles/commitments.example.json) through an explicit environ mapping, reads no key: the login is Muse Code's, and never reads a real `HIDDEN_CRITERIA_DIR`, even if it's set in the shell**. It builds a synthetic cycle in a `tmp_path` database through `EventStore` and `FactStore` (synthetic facts and snapshot written directly as store rows) and makes one real `propose` call per profile against `muse-wonder-1.0` at `high` through the real `MuseExecClient`. It prints only kind, attempts, codes, seconds, and tokens per profile. **It fails if a kind is noop or an exception escapes; a fallback prints its codes and fails too, with those codes in the message**, because that is what the reviewer needs to see. It is run by the reviewer outside the sandbox, **before the commit** (A22, Steps), and its printed lines go into the evidence note before the single commit is made. Inside the sandbox it must remain skipped, never made to pass by mocking.
- **D31, the Muse Code transport.** Product calls run through `MuseExecClient` in `framework/proposal/muse_client.py`, which shells to the headless `muse` binary on my subscription instead of the Model API. The CLI edge takes `--transport muse|api` with `muse` as the default; `MetaClient` in `framework/proposal/client.py` stays as is for anyone with their own key, with its fakes and its request shape unchanged. The exact argv, in order: `muse exec --json --no-session-log --preset empty --model <model> --reasoning-effort <effort> --contributor-mode off --approval-mode never --trust-workspace --workspace <dir> --no-foreign-personal-context --disable-web-tools --disable-request-user-input --disable-reminders --disable-shell --disable-write --max-model-steps 3 --output-schema <file> --prompt-file <file>`. Why each load-bearing flag is there: `--preset empty` because the default preset hands the model `read_file` and `search`, which read outside the workspace by absolute path even under `--disable-shell --disable-write` (measured Nov 1); injected prompt text could then read a file and send it to the model after the outbound scan has passed, while the empty preset has no tools at all. `--trust-workspace` and `--approval-mode never` let the headless run start and finish with nobody at the keyboard to answer prompts. `--contributor-mode off` keeps traces off shared models. `--disable-shell` and `--disable-write` leave the workspace as read-only input. `--disable-web-tools` stops fetches of injected links. `--disable-request-user-input` and `--disable-reminders` fit a run nobody can interrupt. `--no-foreign-personal-context` keeps other personal context out of the prompt. `--no-session-log` keeps the prompt and the response off disk, with usage still reported on the event stream (measured). `--json` gives one event object per line. `--max-model-steps 3` bounds the turn. `--workspace` points at a fresh empty temp dir. `--output-schema` and `--prompt-file` carry the per-call schema and the prompt as files. The refused-contributor rule and the outbound scan run first, in the same order as `MetaClient`. Temperature and max_tokens cannot be set on this transport, and nothing pretends otherwise. The harness adds its own instructions, the real date, the temp workspace path, and a catalog of skill names, about 16,000 input tokens per call with the empty preset, so `prompt_tokens` on these rows is not comparable with the Model API's. Exit 0 means only that the turn ended, so every draft is still validated. Each attempt row holds the transport and the `muse --version` line, read once per process. On the transport choice this decision supersedes D20, D29, and D30; their other content stands. `--no-foreign-personal-context` covers rules from other tools and not my own file, and a host with `~/.config/muse/AGENTS.md`, or that path under `XDG_CONFIG_HOME`, sends that file too. Each attempt therefore records `harness_rules_file`, presence only. Two more closed failure reasons exist: `contributor model`, when a run's events report a contributor id, and `temp files`, for any `OSError` creating, writing or removing temp files. `muse-wonder-full-1.0` is a parameter like any other model and isn't on the Model API. `--no-session-log` was checked with a positive control, and on the Spark a tool call under the empty preset comes back as an unknown tool. A reply over `MAX_DRAFT_CHARS` (64,000) takes the unparseable path before the gate, because the gate's text scan is quadratic on one unbroken run and the timeout can't reach it.

## Risks

- **Latency and cost are per profile.** Two profiles, up to two attempts each, at the measured 13.5–19.4 s per Wonder high call: a bad day is four calls and over a minute, plus the A14 worst case (a truncated first attempt that runs to 32768 tokens, about 50 s, then a retry) at about 100 s for one profile. Accepted: the retry exists because a first draft that breaks a taught rule is a wasted call, and the fallback bounds the outcome.
- **The prompt teaches rules; it cannot teach judgement.** The gate proves provenance, number backing, label binding, and non-leakage — not that the chosen commitment or comparison is the one that matters. That is the same limit Ticket 9 states for facts, carried forward unchanged.
- **Truth of fact statements is not checked.** Ticket 9's statements are model phrasing; the gate lets swapped period labels through (disclosed at [framework/briefing/numbers.py:8-21](../../framework/briefing/numbers.py)). This ticket sends those statements as data and gates only what the new draft claims on top of them; it does not upgrade their truth.
- **A metric at zero is listed only when Ticket 9b's snapshot gives it a key.** Ticket 9b has landed, so a family active in any period carries explicit zero keys and the metric table lists them. A metric with no key stays unlisted, and the prompt forbids claiming it fell to 0.
- **Some honest deltas cannot be offered (A3).** A current-minus-parent difference that does not survive `float()` exactly (about a third of minutes/60-shaped values) is never offered, so `since_last` stays silent about it rather than failing the gate on a correct value. This is a stated limit in the evidence note, not a gate change; the gate's comparison is never touched.
- **Metrics with a digit in a label are invisible (A12).** A category or tag whose label holds a number token (the `3D` case, [framework/briefing/numbers.py:18-20](../../framework/briefing/numbers.py)) is dropped from the table and the enum, because any sentence naming it would fail. The drop is pinned by tests so it is a known silence, not a surprise.
- **The fallback is deliberately thin.** It carries a commitment and a window, no factual prose, so a fallback card can only say which commitment and when. That is the design: code may schedule, but may not invent evidence.
- **The 31-day busy query has a stated edge.** A single event whose winning row sits more than 31 days from `as_of` on event `time` is missed by both the proposer and the gate together (D4); they agree with each other, and the card would double-book that block. Widening further was rejected for load reasons.
- **`proposal_attempts.raw_response` holds raw model content locally.** Content only, never printed, never the prompt, covered by the repo sweep; it exists so the first-draft failure report and any future replay have the actual bytes, the same reason Ticket 9 persists raw contents.

- **The outbound allowlist can drift from the gate (A4).** A future gate text code that should block sends will not block until it is added to the allowlist in D18. That is the chosen direction: a new prose code must not silently start blocking sends.

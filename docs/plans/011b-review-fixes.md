That mapping carries the subject, the slot, the parent id, every section in order with each claim's text, fact ids and metric refs with their values, and the action with its commitment, kind, text, dimension and window, because all of it is in the model the function already built. It is deterministic — keys are sorted, list order is the draft's order, datetimes and floats render through the model's JSON form — so byte-identical inputs give the same id, which is correct: a byte-identical replay is one briefing. Any change in content, including a different metric value behind identical claim text, gives a different digest. - **D13, item 12 — one 4 MiB cap, one constant, per call.** The constant is `MAX_RESPONSE_BYTES = 4 * 1024 * 1024` in [framework/proposal/client.py](../../framework/proposal/client.py), and the Muse transport imports it with the names it already takes from that module. The reasons, recorded as the brief gives them: it is 93 times the largest real stream measured, at 45,036 bytes; it is well above the most a legal draft can reach given `MAX_DRAFT_CHARS = 64_000` at [framework/proposal/schemas.py](../../framework/proposal/schemas.py):23, even echoed and escaped; and it is below the 5 MB garbage reply the review used. Each call is its own child process or its own request, so the cap is per call and no shared budget is needed. The closed reason on both transports is the new string `output too large`, raised as a `MetaUnavailableError` so the core's existing unavailable path records the attempt and falls back.
- **D14, item 12 — `_default_runner` reads incrementally against one deadline and never holds the stream.** Today `_default_runner` at [framework/proposal/muse_client.py](../../framework/proposal/muse_client.py):89 calls `proc.communicate(timeout=timeout_s)`, which reads stdout to end of stream and holds all of it; that is the three-times-the-reply memory measured. The rewrite keeps the `Popen` otherwise as it is — same argv handling, `stdin` from `/dev/null`, `start_new_session=True` so the child leads its own process group — with stderr going to the anonymous temporary file Ticket 13 added, read at most its first 8 KiB only on a non-zero exit — and replaces the read with a bounded loop over the stdout pipe in fixed 64 KiB reads, appending to a bytearray and checking its length after every read, so memory never exceeds the cap plus one read's worth. The bounded read uses what works on pipes on both Linux and macOS, with no platform branch. One monotonic deadline, `start + timeout_s`, governs both reading and waiting for exit, as `timeout_s` bounds the whole call today. Three exits. On passing the cap: I kill the process group at once through the existing `_kill_group` at [framework/proposal/muse_client.py](../../framework/proposal/muse_client.py):82, reap the direct child with a bounded wait, close the pipe without reading it to end of stream — a process that escaped the group could keep writing, and reading on would hand it the clock — and return `RunResult(None, b"", False, oversized=True)`, no output and no exit code. On the deadline expiring, whether the child is still writing, has closed stdout and stayed alive, or has exited while a background process still holds the pipe: I kill the group, reap the direct child the same bounded way, and return `RunResult(None, b"", True)` as a timeout does today. On any `BaseException`: I kill the group and re-raise, as the current handler at [framework/proposal/muse_client.py](../../framework/proposal/muse_client.py):115 does. The wait after pipe end-of-stream uses whatever of the deadline is left, so a child that closes stdout and sleeps cannot hang the call, and a child that exits while a background holder keeps the pipe open is bounded by the same deadline rather than by the holder's lifetime. On every path the runner closes the pipe and has reaped the direct child or given up after the bounded wait, so a normal run leaves no zombie and no open pipe, and no resource warning. `RunResult` at [framework/proposal/muse_client.py](../../framework/proposal/muse_client.py):58 gains one last keyword-only field, `oversized: bool = False`, so every existing three-positional-argument construction in the tests and in this module keeps working untouched, and a caller that does not know the field still fails closed, because the exit code is `None`, which is what a timed-out run already returns. The field is keyword-only, so a positional field added by another ticket can't collide with it. The `Runner` protocol at [framework/proposal/muse_client.py](../../framework/proposal/muse_client.py):65 keeps its signature. The version probe keeps working unchanged: it calls the same runner and reads the first line through `_first_version_line` at [framework/proposal/muse_client.py](../../framework/proposal/muse_client.py):138, and an oversized probe result carries empty stdout and a `None` return code, so the probe reports no version instead of failing.
- **D15, item 12 — both `complete` methods enforce the cap before parsing, whatever produced the bytes.** In `MuseExecClient.complete`, a runner result with `oversized` set fails with `output too large`, and the same length check runs on whatever any runner returned — `len(outcome.stdout) > MAX_RESPONSE_BYTES` — before `_parse_stdout` is called, so an injected runner that ignores the cap gets the same result as the real one. The check sits ahead of the exit-code branch, because bytes nobody will parse should not be parsed. In `MetaClient`, the default transport returns a small wrapper around the real response whose `read` takes no argument — the shape the fake at [tests/test_proposal_client.py](../../tests/test_proposal_client.py):95 has and keeps — and internally reads at most `MAX_RESPONSE_BYTES + 1` bytes, so nothing past one byte over the cap enters memory whether the server sends a `Content-Length` or chunks. After any read returns, in `_send`'s caller and before `json.loads`, a body longer than the cap fails with `output too large`, raised outside any handler so an injected transport that hands back a whole body gets the same result. The resend-once path for dropped connections is unchanged; the cap is checked once, on the body that survived. No test fake changes for any of this.

## Risks

- **A test that cannot fail is the standing risk in this ticket, and three shapes of it are easy to write by accident.** A contributor test that puts the marker only in a configured event or a usage row passes on `main`, because that is exactly what the shipped check reads; AT8 therefore leads with the provider detail and the earlier-event arms, which are the ones that fail today. A cap test that only asserts a body is refused also passes on any code that truncates, so AT12 and AT13 pair every refusal with the exactly-the-cap boundary and with the group-death assertion. And a same-slot store test whose ids happen to sort in recording order passes on the old `(as_of, run, id)` key, so AT1 runs both recording orders and AT2 separates `run` from recording order on purpose. AT16 exists to catch any of these that slip through: a new test that passes on the base measures nothing.
- **Item 7 reads a rowid that SQLite does not promise to keep stable across a `VACUUM`.** Nothing in the repo vacuums this file, rows are never deleted, and a rowid only has to order rows within one file's recording history, which insertion order gives. If a future ticket adds a purge or a vacuum to the cycle table, this rule needs revisiting in that ticket, not silently.
- **Item 6 groups slots by parsed instant, so a stored row with a naive slot would now raise where the old filter may have skipped it.** A4 covers why no writer produces one. The failure, if a hand-edited file ever held one, is a loud exception at read time rather than a quietly wrong parent, which I prefer.
- **Item 8 fails closed on a harness change I cannot see from here.** If a future `muse` build moves the provider's model out of a `kind: provider` mapping, every clean run becomes a labelled fallback with `no model evidence`. That is the intended failure shape — visible, counted, with the requested model and argv unchanged — and the orchestrator in Ticket 13 sets the no-auto-update variable for its runs, so an upgrade is a deliberate act, which is when the stream gets measured again. The reverse risk is a structured field I have not imagined carrying a sentence under a `model` key; the walk would fail that run closed too, and I accept that, because the alternative is reading fewer fields and missing a real Contributor run again.
- **The iterative walk still pays for the size of the stream it walks.** Item 12 caps the bytes before `_parse_stdout` sees them, so the walk's cost is bounded by 4 MiB of JSON per call; without the cap this item would have made the memory finding worse before it made it better. The two items land together for that reason, and Steps orders them so the helpers exist before the walk ships.
- **Item 12's runner is the only place this ticket leaves a process behind on purpose.** When a writer has escaped the process group and still holds the pipe, I return on the deadline and leave it running, because I have no proven pid for it and killing by guess could kill another session's work. It holds a pipe with no reader and dies on its next write. The tests cover the group I do own, and I do not claim the escaped one.
- **Item 11 makes briefing ids longer, and anything outside this repo that assumed eight hex characters would break.** I checked `framework/` and `tests/` and found no parser; stored ids stay readable as opaque strings, and traces exported before this ticket keep their shorter ids. Two briefings that differ only in a metric value that renders identically in JSON — for values the model itself cannot distinguish — would share an id, but `MetricRef` rejects non-finite values, and two floats that dumps renders the same are the same value for every reader downstream.
- **Item 4's noop could surprise a caller who passes a mixed list and reads only the kind.** They get a noop with an explained code instead of a fallback for the wrong goal, which is the point of the fix; the code is one the watchdog already knows, so nothing new needs explaining downstream. The residual risk is a caller who built a mixed list deliberately to offer both goals from one call — none exists in the repo, since the seam filters per profile before calling.
- **Item 10 closes the draft cap but leaves the claim text unbounded in the local model.** That is deliberate: the 64,000-character reply cap and the core's claim-length findings already bound what reaches the gate, and adding a text cap to `ProposalDraft` would invent a limit the sent schema does not declare, the same mistake this item fixes in the other direction. Reference lists stay uncapped for the reason in D11.
- **What the brief left out, recorded so the implementer does not have to rediscover it.** The version probe runs through the same `_default_runner`, so it inherits the bounded read and needs the `oversized` handling in D14 to keep reporting no version rather than raising. `MetaClient`'s resend-once path reads a body twice on a dropped connection, so the cap must be checked on the surviving body, not inside `_send`. And the Muse transport's usage rows name the cached field `cached_tokens` in the row itself, while the Model API nests it under `prompt_tokens_details`; D10's one rule covers both shapes because it judges values, not locations.
- **Timing tests on a loaded machine.** AT12 and AT13 assert that a capped or timed-out call returns well inside a generous bound and that its group is dead; they never assert it returns fast in absolute terms. A loaded box can still slow process startup, so the bounds are set against the call's own timeout, not against the wall clock's best case.

## Approach

### What a domain pack is

A domain pack is a thin config layer. It declares one goal, the commitments I allow, the signals I read and the metrics I check, for one domain. It runs public data with answers known apart from my code through the same proposal and checker path my live loop uses. The pack holds no code of its own in this ticket. The later code reads the pack, builds one reference per window, asks the model for one commitment with reasons, and checks the answer with `check_claims` from `framework/verify/hardened.py` plus one plain rule check on the commitment.

I say three things plainly here and in the later docs. Planted errors are not natural model failures. Historical public data is not a user. The checker checks numbers, sources, labels, units, periods and direction against declared records, not whether a sentence is true. The commitment rule check is a separate plain check, not something the checker does.

### Schema (`framework/domains/schema.py`)

Pydantic models, every one with `extra="forbid"`:

- `SourceFile`: `path: str` (relative to the pack folder), `sha256: str` (64 lowercase hex), `date_column: str`.
- `WindowSpec`: `days: int` (1 to 31), `starts_on` one of monday to sunday as a `Literal`, `period_phrase: str` (must hold `{start}`).
- `DailyMetric`: `prefix: str` (pattern `^[a-z][a-z0-9_]*$`), `source: str`, `column: str`, `op: Literal["sum", "count_above"]`, `above: int | None = None` (I require it when op is `count_above`, I forbid it otherwise), `labels: list[str]`, `unit: UnitName` imported from `framework.verify.hardened`.
- `WindowMetric`: `id: str` (same pattern), `op: Literal["sum", "count_above", "max"]`, `of: str` (a declared daily prefix), `above: int | None = None` (same rule), `labels: list[str]`, `unit: UnitName`.
- `Identity`: `kind: Literal["columns_sum", "daily_matches"]`, `source: str`, `parts: list[str] | None = None`, `total: str | None = None`, `metric: str | None = None`, `column: str | None = None`. `columns_sum` needs source, parts and total. `daily_matches` needs metric (a daily prefix), source (another source) and column.
- `Rule`: `metric: str` (a window metric id), `op: Literal[">=", ">", "==", "<=", "<"]`, `value: int`.
- `CommitmentRule`: `id: str` (pattern `^[a-z][a-z0-9-]*$`), `text: str`, `when: Rule`.
- `Goal`: `id: str`, `text: str`.
- `DomainPack`: `pack_id`, `title`, `note`, `goal: Goal`, `sources: dict[str, SourceFile]`, `window: WindowSpec`, `daily_metrics: list[DailyMetric]` (at least 1), `window_metrics: list[WindowMetric]`, `identities: list[Identity]`, `commitments: list[CommitmentRule]` (at least 2, unique ids), `facts: dict[str, str]`.
- Cross checks: every metric id and prefix is unique; every daily metric source is declared; `of` names a declared prefix; every rule names a window metric; label lists hold 1 to 10 entries and every entry is one lowercase word with no spaces, because the checker naming check compares single words; units are only the checker units.
- `load_pack(path: str | Path) -> DomainPack`. Every failure (missing file, bad JSON, schema error) raises `PackError(ValueError)` with a short safe message.

### Adapter (`framework/domains/csv_adapter.py`)

- Exceptions: `SourceHashMismatch(ValueError)`, `IdentityError(ValueError)`, `WindowError(ValueError)`.
- `load_sources(pack, pack_dir) -> dict[str, list[dict[str, str]]]`: I read each source with `csv.DictReader` after I check the file sha256 on its bytes. A mismatch raises `SourceHashMismatch` naming the source key.
- `window_starts(pack, pack_dir) -> list[str]`: every ISO date that falls on `starts_on` and has all `days` dates present in every daily metric source, in order. For the bikes pack this is 104 dates, from 2011-01-03 to 2012-12-24.
- `build_reference(pack, pack_dir, window_start: str) -> WindowReference`. A start not in `window_starts` raises `WindowError`.
- Metric ids: daily metrics are `f"{prefix}.{date}"` for each ISO date in the window. Window metrics use their `id`. Values are ints. Daily op `sum` adds the column over that date rows. `count_above` counts that date rows whose column is strictly greater than `above`. Window op `sum` adds the daily values. `count_above` counts the window dates whose daily value is strictly greater than `above`. `max` is the largest daily value.
- Labels and units come from the pack. Periods: a daily metric period is its ISO date. A window metric period is `window.period_phrase` with `{start}` replaced by the window start. Order: one series per daily prefix, the window dates in order. Facts: the pack facts.
- Identities run on every build, over the window dates, and any failure raises `IdentityError` naming the identity kind and the first failing date. `columns_sum`: for every row of the source in the window, the sum of the parts columns equals the total column. `daily_matches`: for every date, the daily metric value equals the sum of `column` over that date rows in the other source.
- `WindowReference` is a frozen dataclass: `pack_id`, `window_start`, `dates: tuple[str, ...]`, `metrics: dict[str, int]`, `labels: dict[str, list[str]]`, `units: dict[str, str]`, `periods: dict[str, str]`, `order: list[list[str]]`, `facts: dict[str, str]`, `identities: tuple[IdentityResult, ...]`. `IdentityResult` is a frozen dataclass with `kind: str`, `dates_checked: int`, `held: bool`. Method `check_input(claims: list[dict[str, Any]]) -> dict[str, Any]` returns the full dict `check_claims` accepts: claims plus facts, metrics, labels, units, periods and order.

### Runner (`framework/domains/runner.py`)

- `expected_commitment(pack, ref) -> str`: the id of the one commitment whose rule holds on `ref.metrics`. Zero or several raise `ValueError`.
- `build_prompt(pack, ref, feedback: str | None = None) -> str`: plain words. It states the pack note, the goal, the decision to make, every commitment id with its text and its rule in words, one line per metric with id, value, label words, unit and period phrase, every fact id with its text, and these writing rules: I choose exactly one commitment whose rule holds; I write 1 to 3 claims giving the reasons, each one plain sentence of at most 25 words; every number in a sentence is the exact listed value of a metric the claim cites, written in digits; a claim that cites a metric writes all its label words and its period phrase as listed; I cite one metric per claim, or two metrics from the same daily series when I compare two dates, writing each value next to its own date; I never write the threshold number (a claim about the threshold cites the `busy_rule` fact and states no number); no other numbers, no other units, no negations. With feedback, it adds the feedback lines and asks for a complete new draft.
- `response_schema(pack, ref) -> dict[str, Any]`: a JSON schema for `{"commitment_id": str, "claims": [{"id": str, "text": str, "metric_refs": [{"metric_id": str, "value": int}], "fact_ids": [str]}]}` with `commitment_id` held to the pack commitment ids (enum), `metric_id` held to the window metric ids (enum), `fact_ids` items held to the pack fact ids (enum), 1 to 3 claims, and `additionalProperties: false` on every object.
- `DomainValidation`: frozen dataclass `passed: bool`, `codes: tuple[tuple[str, str], ...]` (code, claim id or `-`), `commitment_id: str | None`, `check_complete: bool | None`. Method `feedback() -> str` with one `CODE claim_id: message` line per finding. It meets the `Validation` protocol in `framework/verify/repair.py`.
- `validate_proposal(pack, ref, text: str) -> DomainValidation`. Codes, in this order: `DOMAIN_UNPARSEABLE` (not JSON or wrong shape; then nothing else runs), `DOMAIN_UNKNOWN_COMMITMENT`, `DOMAIN_COMMITMENT_RULE` (the chosen commitment rule does not hold on the window metrics), `DOMAIN_CHECK_INPUT` (`check_claims` raised `VerifyInputError`), then every violation code `check_claims` reports, with its claim id. Passed means no codes at all.
- `run_window(pack, ref, client, *, model, effort, max_retries=1) -> WindowRun` uses `repair_loop` from `framework.verify.repair` with `max_retries=1`. The generator builds a `WonderRequest(prompt=..., model=..., effort=..., response_schema=..., schema_name="domain_proposal")`, calls `client.complete`, and returns the response. The validator runs `validate_proposal` on its text. I catch `MetaUnavailableError` and `OutboundBlocked` from the client: the run records `transport_error` (the exception class name and its closed reason) and does not raise. I do not use `verify_and_repair`; it runs the older, narrower checker.
- `WindowRun`: frozen dataclass with `pack_id`, `window_start`, `model`, `effort`, `expected_commitment`, `attempts: tuple[AttemptRecord, ...]`, `first_pass_accepted: bool`, `repaired: bool` (first attempt failed and the second passed), `final_passed: bool`, `transport_error: str | None`, `latency_ms_total: int`, and `to_json() -> dict[str, Any]`. `AttemptRecord`: `number`, `latency_ms`, `model_reported`, `prompt_sha256`, `raw_text`, `passed`, `codes`, `commitment_id`, `commitment_matches_expected: bool | None`, `check_complete`.

### Command line (`python -m framework.domains`)

- `check --pack PATH --window START --claims FILE`: FILE is a JSON list of claims. It prints `format_check_report` from `framework.verify.hardened`. Exit 0 on pass, 1 on fail, 2 on bad input.

## Key decisions

- K1, pinned: the bikes pack declares no threshold metric. A labelled threshold metric makes the natural sentence "total rentals were 7,100 on a date, above the threshold" fail twice over: citing both metrics gives `L1B_TOO_MANY_METRICS`, and naming "threshold" while citing only the daily metric gives `L1B_METRIC_LABEL_MISSING`. So the threshold lives in the `busy_days` definition and the `busy_rule` fact, and the prompt says never to write the threshold number.
- K2, my call: `client_factory` takes no arguments and returns a client. The `propose` command builds `MuseExecClient(private_terms=(), private_terms_available=True)` inside the default factory, so a test factory never needs model or effort values. Reason: one shape serves the command line and the tests.
- K3, my call: the oracle result shape in Approach (assumption A2) uses a `days` dict keyed by date. Reason: a test can name one date without counting list positions.
- K4, my call: `WindowReference.metrics` and the other maps use plain dicts, and `identities` uses a tuple. Reason: `check_input` can pass the dicts straight to `check_claims`.
- K5, my call: the mini fixture uses threshold 100, first week busy days 2, second week busy days 0, with the values in `tests/fixtures/domains/mini/`. Reason: the runner test needs both commitment outcomes from the two mini weeks alone.
- Known limits I foresee before any run: the unit check knows only time, percent and magnitude words, so a unit like kilometres passes. The planted unit list uses words the checker knows, and the docs must say so. Label words match as whole words, so "1 busy day" fails against the label "days". I expect that as a first-pass failure the repair can fix.

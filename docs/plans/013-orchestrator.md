## Decisions

Each decision is binding on the implementer. I give the reason with each one.

- **D1 — Modules, thin dispatch.** New modules, one line of reason each: `framework/cycle/orchestrator.py` keeps `SLOT_TIMES`, `slot_profiles`, `EligibilityState`, `eligible_commitments`, `run_slot`, `check_slot` (Ticket 14 plans against those names in that module); `framework/cycle/slot_ledger.py` holds the tables, writes and state reading (one place owns the append-only record and its lock retries); `framework/cycle/card_build.py` holds statements, since line, chart data and the card (pure card assembly, apart from the run); `framework/cycle/trace.py` holds the trace command (read-only, its own `SELECT`s, D35); `framework/cycle/rehearse.py` holds the rehearsal and its seed (a hand path that shares `run_slot` and nothing else). `framework/cycle/__main__.py` stays thin dispatch: subparsers that build the seams and call into these modules. Reason for the split: rebases are coming, Ticket 11 owns `__main__.py`, and a small dispatch keeps that conflict to a few lines. No change under `framework/briefing/`, `framework/schemas/` or `framework/verify/`, so `make verify-page` is not owed. If that changes in implementation, I rerun it or a stale-bundle test fails.
- **D2 — One process tree, facts as a child, pinned model constants.** `run-slot` does the whole slot in one process tree because a hand run must work with no timer. In-process first it writes a code-only cycle (no client, milliseconds, the `--no-personal-pass --no-feed-pass` path at [framework/cycle/__main__.py:317-322](../../framework/cycle/__main__.py)), so a card can always go out. `orchestrator.py` defines its own never-called stub for that in-process code cycle, because importing the one in `__main__` would be circular. Then it runs the model cycle as a child, `sys.executable -m framework.cycle facts --as-of <iso> --subject-id <id> --db <path>`, in its own session (`start_new_session=True`, the pattern at [framework/proposal/muse_client.py:88-109](../../framework/proposal/muse_client.py)), and at the deadline kills the process group. The child's stderr goes to `DEVNULL` and is never captured. Its stdout is parsed for `cycle=` and `run=` only and is never echoed; unparseable stdout on exit 0 gives `facts_model` outcome `FACTS_UNPARSED` and the code cycle carries the slot. A non-zero exit gives `MODEL_DOWN` and the code cycle. A `BaseException` in the parent kills the process group before it propagates. No thread, because a blocked `urllib` call cannot be stopped. No separate facts timer, because a hand run would lose it. A kill mid-write loses nothing: `record_cycle` is one `BEGIN IMMEDIATE` transaction ([framework/store/fact_store.py:200-267](../../framework/store/fact_store.py)). Models are constants with no CLI flag on `run-slot`: `ModelParams("muse-wonder-1.0", "high", "muse-wonder-1.0", "high")`, stale limit 12 h, `ProfileLimits(timezone="Europe/Madrid", allowed_start=13:00, allowed_end=23:30, max_actions=3)`, the same values as the `propose` CLI defaults ([framework/cycle/__main__.py:273-281](../../framework/cycle/__main__.py)).
- **D3 — Lead 25 minutes, facts deadline pinned.** Default `--lead-minutes` is 25. The model's time ends a fixed reserve before the slot: `FACTS_SLOT_RESERVE` of four minutes. The facts deadline is `min(slot - 4 min, run start + lead + 10 min)`: the second bound stays, so a slot instant in the future cannot give the model hours. On a 13:05 timer the model has until 13:26, 21 minutes against the two measured full runs of 851 s and 974 s. At the deadline I stop waiting for the local model, kill the facts child's process group, and go on with the code-only cycle. A run that starts past that deadline (a hand run started after slot minus four minutes) skips the child and goes straight to code facts, recording `FACTS_DEADLINE`. A hung model pass can block up to `MODEL_TIMEOUT_S=1800` ([framework/glimmer/llm.py:27](../../framework/glimmer/llm.py)), and nothing stores until both passes finish, so the child-process kill is the only bound that holds.
- **D4 — The card goes at the slot.** If everything is ready early, `run-slot` waits until the slot instant, checks the kill file again, then sends. `--no-wait` turns the wait off for hand runs and the rehearsal. Reason: a card for 15:30 that lands at 15:12 asks me to rule on an hour that has not started.
- **D5 — Slots as pinned constants.** `SLOT_TIMES = (13:30, 15:30, 18:00, 20:30, 22:30)` in Europe/Madrid, and `slot_profiles(slot) -> tuple[str, ...]` maps a slot to its allowed profiles. The limits are the constant `SLOT_LIMITS` from D2. Builder runs at every slot. Disconnect runs at 15:30, 20:30 and 22:30 only. Any other Madrid time is refused, exit 2, code `SLOT_NOT_PINNED`, unless `--force-slot` is passed; a forced run is recorded in the ledger with `forced=1`. A forced run at an unpinned time keeps both profiles until 23:00 and counts toward the cap; pinned 13:30 and 18:00 stay Builder only. A slot string with no offset, or an offset that is not Madrid on that date, is refused exit 2. Reason: the function is the one place a later ticket changes hours, and a forced hand run must stay visible in the record.
- **D6 — Eligibility is one pure function, and the hour comes before proposals.** `eligible_commitments(commitments, *, profile_id, slot_local, state) -> tuple[Commitment, ...]` in `orchestrator.py`, where `state` is a frozen `EligibilityState(disconnect_sent_today: int, now_local: datetime, hour_start_local: datetime | None)`. The function's signature stays; the state gains the one field. It takes the commitment state as an argument so Ticket 14 can add skip, defer, drop and done without changing call sites. Today it applies only the fixed rules: profile match in file order; from 21:00 Madrid, Disconnect keeps only kinds `music` or `rest` (`ActionKind` at [framework/briefing/schemas.py:23-36](../../framework/briefing/schemas.py)); after 23:00 Disconnect returns nothing. The 21:00 rule reads the time the proposal is for: `hour_start_local` when an hour was picked, else `slot_local`. Reason: `pick_hour` walks forward to the first free block ([framework/proposal/hour.py:53-88](../../framework/proposal/hour.py)), so a 20:30 slot can propose 21:15, and PREREG says that after 21:00 Disconnect offers only music or rest. Otherwise it returns all of the profile's commitments. The commitments file never changes. This needs the hour before proposals, so the `hour` step really runs before `propose`: the orchestrator computes it with the same public calls as [framework/cycle/__init__.py:150-156](../../framework/cycle/__init__.py) (`busy_query_span`, `events_between` on the busy types, `future_busy_intervals`, `pick_hour`), and a test pins that it equals `result.hour`. `run_proposals` still picks its own, unchanged; it is pure over the same inputs. Tests: one per rule, plus "returns all otherwise", plus the new one: 20:30 slot, busy until 21:15, Disconnect keeps only `music`/`rest`.

The last pinned slot is 22:30, so this binds forced runs. Add the send-time lock: right before the send, a card carrying Disconnect does not go out at or after 23:00 Madrid by the clock. Outcome `DISCONNECT_AFTER_CUTOFF`, nothing sent, explained to the watchdog. Reason: the slot-time rule cannot see a forced 22:50 run whose send lands at 23:05. The rehearsal is exempt, because it is a labelled test a person starts by hand (D24). Tests at 23:00 and 23:30, and: forced 22:50, clock 23:05.
- **D9 — Proposal parents come only from delivered cards, one reading only.** Smallest fix, and it touches Ticket 11's function: in `run_proposals`, when `parents` is not `None`, a profile missing from the dict means no parent. One reading only; the old fall-through to the store is gone for that case. Today the fall-through sits at [framework/cycle/__init__.py:161-170](../../framework/cycle/__init__.py): `if parents is not None and profile_id in parents` else `proposal_store.latest_proposal(...)` ([framework/store/proposal_store.py:357-380](../../framework/store/proposal_store.py)), which reads delivered and undelivered rows alike, so a proposal from a killed or failed slot would become a parent. The annotation is `dict[str, tuple[Briefing, MetricSnapshot]]`, as `run_proposals` already declares it. I build each entry from the latest delivered slot whose `slot_cards` row for that profile has kind `proposal`, then `proposal_store.latest_proposal(subject, profile, before_slot=<that slot> + 1 microsecond)`. The side read is the delivered card's, not any card's at that slot. A profile with no such slot is simply absent from the dict. One test in `tests/test_cycle_orchestrator.py` pins the new reading; the `parents=None` default keeps the CLI behaviour.
- **D10 — No blind retry on a send whose delivery is unknown, run side.** An independent review of my repo by GPT Sol 6.1, run through Codex, reproduced this: at [framework/telegram/client.py:208](../../framework/telegram/client.py) and [:308](../../framework/telegram/client.py), when `sendPhoto` is accepted and the response is lost, the client retries and delivers two photo messages with one ledger row. The coordinator's ruling, which I take: no blind retry when delivery is unknown; record the outcome as delivery unknown so the run's counts stay true; retrying is still fine when the request never connected. The slot ledger (D13) is the record. The send step, in `orchestrator.py`: `send_card` writes the card ledger before the request, so a `sqlite3.Error` it raises means nothing went out: outcome `SEND_NOT_SENT`, retried on the same 30, 60, 120 s schedule. Any other unexpected exception in the send step is recorded as `DELIVERY_UNKNOWN`, by class name only, because I cannot prove the request did not go. Catch in this order: `TelegramDeliveryUnknown`, then `TelegramRateLimited` and plain `TelegramTransportError`, then `TelegramAuthError`, `TelegramConfigError` and other `TelegramApiError`, then `sqlite3.Error`, then `Exception`. Write a `send_intent` row, call `send_card`, write one outcome row. Outcomes: `delivered` with the message id; `DELIVERY_UNKNOWN` on `TelegramDeliveryUnknown`; `SEND_NOT_SENT` on plain `TelegramTransportError` or `TelegramRateLimited`; `SEND_REFUSED` on `TelegramAuthError`, `TelegramConfigError` or any other `TelegramApiError`. After `SEND_NOT_SENT` the run waits 30, then 60, then 120 s and tries again, each attempt with its own `send_intent` and outcome row, and the kill file and D15 stale check run again before each. Nothing else is retried. If all fail, the slot ends `SEND_NOT_SENT`, exit 1. A re-run reads the last send rows. A `send_intent` with no outcome row after it means a crash mid-send: record `DELIVERY_UNKNOWN`, send nothing, exit 1. Last outcome `DELIVERY_UNKNOWN`: send nothing, exit 1, unless the hand flag `--resend-unknown` is passed. `SEND_NOT_SENT` or `SEND_REFUSED`: a re-run sends the stored card again. `delivered`: never sends. `--resend-unknown` is for me after I look at my phone and see no card. It sends the stored card once more, records `resend_unknown=1`, is refused with `RESEND_NOT_UNKNOWN` exit 2 on any other state, and still obeys D15. It is checked before `ALREADY_DONE`: on a delivered slot it refuses `RESEND_NOT_UNKNOWN` exit 2. On `intent_open` it first writes the `DELIVERY_UNKNOWN` row, then sends. Once a `card` row exists, a re-run skips the pipeline and resumes at the send stage with the stored payload and sides. That is not a blind retry, because a person looked. The brief asked what a crash between Telegram accepting and the ledger recording does; my answer: it leaves `send_intent` with no outcome; the next run records `DELIVERY_UNKNOWN`, sends nothing, and the watchdog alerts so I look at my phone. No duplicate arises on its own. The only way to get one is `--resend-unknown` after a wrong look: two photo messages with the same caption and chart, two message ids, one card id, and taps dedupe on `card_id:target` ([framework/telegram/service.py:444-456](../../framework/telegram/service.py)), first ruling stands. The failure I pick is a possibly lost card, because it is rare (the window is one request), it shows in the counts as unknown, and a look at the phone can restore it, while a silent duplicate inflates the counts I publish. A tap on an unknown card proves delivery: replay feeds it to the learner like any other, and `trace` prints it. Resume reuse: before any Wonder call for a profile, read `results_for_slot`; a stored result for this slot and profile is reused and its ledger row written with `reused=1`, even if the crash came before the ledger row. No second model call. `--fresh` restarts from `facts_code`, both facts and proposals, under the same deadlines, because the brief says reusing stored facts and proposals unless `--fresh`. It is refused with `FRESH_REFUSED` exit 2 when the slot has a `delivered` row or an unresolved or `DELIVERY_UNKNOWN` send. A slot that already has a `done` row and no `--fresh` prints `code=ALREADY_DONE`, exit 0, and writes nothing.
- **D11 — No blind retry, client side.** In `framework/telegram/client.py`: `_request_once` splits its broad failure. `urllib.error.URLError` that is not `HTTPError` means the request never got to Telegram in full: stdlib `AbstractHTTPHandler.do_open` wraps only `OSError` raised by `h.request(...)` (connect, TLS, writing the body) into `URLError`, and lets errors from `h.getresponse()` and the body read through raw. Kind `not_sent`. Any other exception there is kind `unknown`. New `TelegramDeliveryUnknown(TelegramTransportError)`. `send_photo` retries with the existing 1, 2, 4 s backoff only on `not_sent`, and on 429 as today, because a 429 is a refusal. It raises `TelegramDeliveryUnknown` at once, with no retry, on kind `unknown`, on any 5xx, and on an unusable 2xx body. `send_photo` keeps its signature with no `attempts` parameter, and four failed `not_sent` attempts raise plain `TelegramTransportError`. `call()` and every non-photo method keep their behaviour. A repeated Why? reply is harmless, and `sendMessage` is not a card. `send_card` passes `timeout_s=60.0`, because a timeout now costs a card, and a usable 2xx with no integer `message_id` raises `TelegramDeliveryUnknown` instead of plain transport error, because Telegram accepted something. No method follows a redirect, on either path in `_open_url` (a 3xx on a POST would otherwise become a GET, and a failed GET would read as `not_sent` although the POST already arrived); a 3xx comes back as a plain status, and on a photo send `_classified` turns it into `TelegramDeliveryUnknown`, while other methods treat it like any other refused status. Ticket 12 tests that pin the old blind photo retry change to the new rule; `tests/telegram_fake.py` gains an outcome `connect-refused` that raises `urllib.error.URLError(ConnectionRefusedError())`.
- **D12 — The delivered row must land, and the hole is named.** A database locked for 30 s cannot record `LEDGER_WRITE_BLOCKED` in itself. So the `delivered` write, once Telegram has accepted, holds the message id in memory and keeps retrying with short sleeps until the D15 stale limit. Only then does it print `code=LEDGER_WRITE_BLOCKED message=<id>` to stdout and exit 1, leaving `send_intent` with no outcome, so a later `check-slot` reports `DELIVERY_UNKNOWN`. Other ledger writes that hit the 30 s limit print the same code and exit 1. It never claims a row it could not write. The same database file is written by the poller, the collector timer, the ingest server and the facts child, so the slot ledger opens its own connection per write with `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=30000` and `synchronous=FULL`, and retries a `database is locked` write with short sleeps. Sqlite's default busy timeout is 5 s and [framework/telegram/ledger.py:30-34](../../framework/telegram/ledger.py) sets none, so this is new work, not a reuse. The test covers a lock held past the first 30 s and released before the stale limit: the delivered row lands. This test needs a real child process, which the sandbox allows; it binds no port.
- **D13 — `as_of` is pinned, `done` is earned, ledger shape is fixed.** `as_of = slot - lead_minutes` is computed once and written in the `start` row. Every later step and every re-run reads it back from the ledger: the facts child's `--as-of`, the code cycle, the since line's `C`, `slot_cards.as_of`, and `trace`. A re-run with a different `--lead-minutes` or at a different wall time cannot rebuild a different card. Only `--fresh` may write a new `start` row with a new `as_of`, and the latest `start` row wins. A `done` row is written only after `delivered`, an explained noop on both sides, `STALE_CARD`, or `DISCONNECT_AFTER_CUTOFF`. It is not written after `killed`, `DELIVERY_UNKNOWN`, `SEND_NOT_SENT`, `SEND_REFUSED`, any `PREFLIGHT_*` code, `COMMITMENTS_UNAVAILABLE`, `TERMS_UNAVAILABLE`, `CHART_FAILED`, or an unexpected failure, so those re-run through the send-state rules in D10, and `ALREADY_DONE` never hides them. Ledger shape, fixed: `slot_cards` has one row per side, so the key is `(card_id, letter)`, and it must carry everything replay needs: `card_id, letter, slot, subject_id, as_of, bucket, profile_id, commitment_id, kind, policy_pick, policy_alternative`, with `bucket` and `policy_pick` nullable (see D22). New table `slot_card_payloads(card_id PRIMARY KEY, card_json, chart_json)`, written at the `card` step. A resume or a resend loads the card and the chart from it, so the same bytes go out and no recomputation can change the card id. The other two tables are `slot_ledger` and `learner_states(id INTEGER PRIMARY KEY, slot, state_json)` (D21). All four tables are append-only with `BEFORE UPDATE` and `BEFORE DELETE` triggers in the existing store pattern ([framework/store/fact_store.py:62-80](../../framework/store/fact_store.py)), and a test asserts both raise. `slot_ledger` keeps `slot TEXT, step TEXT, outcome TEXT, seconds REAL, card_id TEXT, detail TEXT` plus a rowid; `detail` holds only closed codes and counts as `key=value` pairs (for example `forced=1`, `transport=muse`, `tokens=1234`, `cycle=<id>`), never text. Steps, in order: `start, preflight, commitments, facts_code, facts_model, hour, learner, propose_builder, propose_disconnect, card, send_intent, <send outcome>, done`. `killed` writes no `done`, so a re-run after removing the kill file resumes. A fifth table `local_start_retries(slot, profile, try, reason, latency_ms, exit_code, stderr)` holds one row per retried local start failure with the same append-only triggers; its stderr is masked, and a propose row's `detail` carries only the `local_retries=<n>` count.
- **D14 — Two run-slots for one slot cannot both send.** I take an OS lock, `fcntl.flock` on `<db path>.run-slot.lock`, non-blocking, held for the whole run. The OS releases it on a crash, so no row can go stale. A second run that cannot take it records nothing, prints `slot=<iso> code=ALREADY_RUNNING` and exits 3. Test: two real processes race one slot against fakes; exactly one `sendPhoto` happens.
- **D15 — A stale card never sends.** A send is allowed until slot+30 minutes. Past that, `run-slot` records `STALE_CARD` and sends nothing, exit 0, because the slot is explained. `--force-slot` lifts the pinned-time refusal (D5) and does not lift this limit; a hand re-run hours later must not send a card whose hour has gone. `--no-wait` does not lift it either. The rehearsal never meets it because of the D24 slot rule: its slot is the next 15:30 Madrid at or after now, so the send is never past that slot plus 30 minutes.
- **D16 — Dry run and `--skip-local-model`.** A dry run never contacts Telegram, no client is built, and `TELEGRAM_*` is not required; a test asserts the fake transport saw no call. It copies the database file to a temp file with sqlite's backup API, runs the whole slot against the copy, prints the usual counts and codes plus `dry=1` and `card=<id>` for what it would have sent, and deletes the copy. It takes no lock on the real file, and it removes the copy's `-wal` and `-shm` files when it deletes the copy. It never opens the real file for writing. Reason: `ProposalStore.latest_proposal` and `last_offered_by_commitment` read every stored row ([framework/store/proposal_store.py:357-417](../../framework/store/proposal_store.py)), and the ledger drives exactly-once and the Disconnect count, so a dry run on the real file would change later cards. A missing database file gets a fresh empty copy. It runs the facts child and Wonder for real unless `--skip-local-model` is passed. `run-slot` gains `--skip-local-model`: it skips the child and records `facts_model` outcome `SKIPPED`. Preflight (D34) still applies to dry runs. Test: dry run on a seeded file, then a real run at the same slot sends, and the real file holds no dry-run rows.
- **D17 — Two cycles at one `as_of` are named, never guessed.** The cycle id carries `prompt_hash[:8]` at [framework/glimmer/facts.py:488-503](../../framework/glimmer/facts.py), and a skipped pass has an empty prompt, so my code-only cycle and the model cycle at the same `as_of` get different ids and both are run 1. `fetch_latest_cycle` ties on `(as_of, run, id)` and picks by string order ([framework/store/fact_store.py:316-339](../../framework/store/fact_store.py)), which can pick the code-only cycle over a finished model cycle. So `run-slot` never calls `fetch_latest_cycle`: it records the code cycle's id from `run_cycle`'s return, parses the model cycle's id from the facts child's stdout line, and passes the chosen id to `run_proposals(cycle_id=...)` ([framework/cycle/__init__.py:113-123](../../framework/cycle/__init__.py)). A test seeds both cycles at one `as_of` and asserts the model cycle's facts are the ones proposed from, by id.

The winners the trace hands in come from the same reconciliation as `run_cycle` and `extract_facts`: calendar rows load whole (no time filter before `select_winners`, so a block crossing the window's start still explains `calendar.busy_hours`), other rows load from the floored window's start, the collected guard sits at the raw `as_of`, then `select_winners`. `_print_since` keeps calling `since_counts`, with its event load and its row count on the same floored bounds. Code fact evidence is capped at 8 ids by Ticket 9b, so the fact line can undercount and the metric line gives the full number; I say so in `--help`.

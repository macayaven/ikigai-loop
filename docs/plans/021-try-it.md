## Success Criteria

- **One command, no setup.** `try-ikigai` is a console script in `pyproject.toml` next to `verify-claims`. `uvx --from git+https://github.com/macayaven/ikigai-loop try-ikigai` works for a stranger with `uv` and `git` (plus a network connection the first time; uv fetches Python itself if needed): no key, no model, no phone, no account, no environment variable read. `make try` runs the same command from a clone without pulling the dev and app groups into a fresh clone. `--help` prints what the command does and its flags, exits 0 and runs no replay.
- **Five sections, in order, the first four labelled synthetic.** The output is: a synthetic banner; an opening naming Ikigai Loop with two or three plain first-person sentences saying what it is (Decision 23); (1) the card — the two goals in plain words (Builder is my work, Disconnect is family time with screens off), the real `render_card_text` text, the real `render_chart_png` image described by pixel size with the period words explained where the chart is described (three bars per row are earlier, prior and last; the counts under it are my earlier choices), and the `build_keyboard` buttons shown as the choice a person makes; (2) the choice — the simulated tap (A by default, `--pick B` or `--pick neither`), the real `toast_recorded` wording, the `build_ruled_keyboard` keyboard, the one `app.tap` row that would be stored (nothing is stored), and the earlier-choice count for the picked side moving by one, plus how to choose differently; (3) a wrong number, stopped — the planted sentence (which says pushes reached 5 in last while the records hold 4), every gate code from the real first attempt each followed by a plain sentence saying what it means, the number the sentence said and the number the records hold, the one retry, and the corrected sentence that reached the card; (4) where a number comes from — the real `why_reply_pieces` reply, then one corrected claim traced to the fact it cites (with that fact's statement — `Pushes rose from 2 in prior to 4 in last.`), the metrics it cites with their snapshot values, and the six made-up rows those numbers were counted from, listed so a person can count them; (5) `Check your own agent` (no synthetic label) — opening with the Decision 23 first line, then the same two commands and the browser link the README gives, two or three lines on what the real loop needs, and a pointer to the README.
- **Plain language.** No output line uses the word "ruling", and none of the banned words (thrilled, delighted, leverage, delve, tapestry, robust, seamless, coach, wellness, wellbeing, mental, recovery) appears in the output or the recording. Internal names a stranger cannot know (Glimmer, Wonder, L1B, briefing, gate layers) are either absent or explained in plain words where they appear; each error code is explained in the sentence right after it; "earlier", "prior" and "last" are explained in section 1, where the chart is described, as the three most recent 24-hour periods. A model is named only with what it is. The text says plainly that the proposal wording is written by hand in the shape the model returns and that no model ran, and that the "Something's wrong" button asks for a voice note in the real app and that path is not in the replay. Nothing reads as health advice. The whole output fits the length limit in Decision 22.
- **Real code, in memory.** The replay runs `extract_facts` with both model passes off, builds a `GateContext` directly the way `run_proposals` does, picks the hour with `pick_hour`/`allowed_windows`, and runs `propose` once per goal against a recorded client. The printed card text, chart bytes and button labels are the real functions' outputs on the replay's own objects. If the gate is replaced by one that passes everything, the command exits 1 and prints no story.
- **Deterministic and buffered.** Two runs give byte-identical stdout and byte-identical image bytes, independent of the clock, the machine's time zone and the working directory. Nothing is printed until the replay has finished and checked its own story, so a failure never leaves half a story. Exit codes: 0 when the replay went as recorded, 1 with a one-line reason on stderr when it did not, 2 for usage errors and an unwritable `--save`. A closed pipe and a non-UTF-8 terminal produce no traceback. No sleeps.
- **No writes by default.** With no `--save` the command writes no file anywhere, the temp folder included; it renders the image in memory and says the image was made in memory and how to keep it. `--save PATH` writes the chart image to exactly that path and says where it went, the path as typed; the output carries no absolute path unless the person typed one. Onto an existing path that is not a regular file, or a regular file holding different bytes, it writes nothing and exits 2 with a one-line message; a regular file already holding the same bytes is left untouched and succeeds, so running the published command twice works. It never hangs: a named pipe, directory or symlink is refused without opening it.
- **Isolation.** The new package imports and calls none of the forbidden names (Decision 19), reads no environment, opens no socket, no database and no subprocess, and never reads stdin. It still exits 0 in-process with sockets blocked the way `tests/telegram_fake.py` blocks them and `sqlite3.connect` set to raise, and in a subprocess whose HOME, working directory and decoy environment point at a decoy database file that stays byte-unchanged.
- **Packaging.** `pillow`, `icalendar` and `recurring-ical-events` move from the `app` group into `[project].dependencies` with their version floors unchanged, `uv.lock` is refreshed with no version changes, and CI gains one step that runs the command through `uvx` from the checkout, proving the built wheel and the declared dependencies. `framework.verify`'s import closure is unchanged, so `docs/verify/bundle.json` needs no rebuild.
- **Docs.** The README gains a short `## Try it` section right after the opening paragraph and before `## Check your own agent`, with the published command (with `--save card.png`), what the reader needs (`uv` and `git`, network the first time), what the command writes (only the file they named), what it does and does not do, and a clearly marked placeholder for the measured time that the owner fills in at commit time. ## Approach

### Numbered decisions

Every assumption this plan makes is one of these decisions, with its reason. Approval of this plan accepts them.

1. **Package: a new `framework/tryit/` package, entry point `framework.tryit.__main__:main`.** Reason: `verify-claims` is exposed as `framework.verify.__main__:main` at `pyproject.toml:10-11`, and the wheel ships only `framework/` (`pyproject.toml:32-33`), so a package inside `framework/` is the only shape that both mirrors the checker and reaches a `uvx` stranger.
2. **The recording lives at `framework/tryit/recording.json`, beside the modules, with no subfolder, and parses through Pydantic models on `SchemaModel` in the new package (`framework/tryit/models.py`).** Reason: `AGENTS.md` wants typed manifests only and `make check` runs pyright strict on `framework/`, so the recording is a typed manifest, not loose JSON; the file must not sit under a folder named `data/` or `out/` because `.gitignore:21,24` ignores those names at any depth and hatchling honours that, which would silently drop the recording from the wheel and from git. One JSON file holds the fixed instants (including the previous card's instant, Decision 20), the subject id, the event rows, the earlier taps, the two commitments and the reply templates, plus a typed top-level note saying everything in the file is made up, so a reader audits the whole made-up world in one place.
3. **The subject id is `synthetic-subject-021` and every packaged instant is well before 2026-11-02.** Reason: the id says synthetic on its face, and dates before the live run mean nobody can mistake the replay's rows for a real run. The fixed `as_of` is a whole hour on 2026-10-24 in Europe/Madrid, well before 2026-11-02.
4. **The packaged story: pushes of 1, 2, 4 across the three periods, so the fact reads `Pushes rose from 2 in prior to 4 in last.`; code screen hours rose too and stay the largest change, with a second screen category, feed, also present so the chart shows more than one screen row.** Screen rows stay sparse — there is no need for all 72 hours — every screen row's minutes are multiples of 15, code and feed alike, so hour sums stay exact in binary floating point, and no screen row holds more than 60 minutes (longer hours are split into rows). Tiers match the real collectors (github.push public; screen.hour and calendar private). Feed values read cleanly as halves and quarters and differ across periods, so the chart's feed row is not three equal bars. One busy calendar block sits on the first candidate hour. The trace in section 4 lists the six rows behind those two metrics (the pushes pair's rows and the code pair's rows). The planted Builder sentence lies about that same last-period number: it says pushes reached 5 in last while the records hold 4. Reason: pushes and screen hours are two of the families the rule-made facts report on (`framework/glimmer/code_facts.py:29`), the 1/2/4 story draws three bars while the consecutive-period comparison plus the later-pair tie-break picks the prior-to-last pair, the feed row makes the chart look like a real one without changing which family wins, and the busy block proves the free hour is picked, not simply the slot: `pick_hour` (`framework/proposal/hour.py:53-88`) must skip the blocked hour.
5. **Facts come from `extract_facts` with `personal_pass=False, feed_pass=False` and an LLM stand-in whose `complete` raises if called.** Reason: `framework/glimmer/facts.py:432-435,490-491` shows a switched-off pass builds no prompt and never calls the model, so what remains is exactly the real rule-made facts, their evidence ids and the metric snapshot — and if a future change calls the model anyway, the replay fails loudly instead of silently needing one.
6. **The `GateContext` is built directly, copying the inputs `run_proposals` passes at `framework/cycle/__init__.py:203-216`, but from the recording instead of stores.** That means facts keyed by `Fact.id`, the snapshot from `extract_facts`, no parent briefing or parent metrics, free intervals from `allowed_windows`, busy intervals from `future_busy_intervals` over the packaged calendar rows, the real profile limits below, forbidden raw literals from `private_free_text_values` (`framework/glimmer/checks.py`, the function `framework/cycle/__init__.py:14,92-102` builds them with) over the packaged rows plus the internal-only labels, one `GateContext` per goal, each holding only that goal's eligible commitments the way `run_proposals` builds each profile's context (`commitments=eligible`), both with `commitments_available=True`. Nothing is imported from `framework.cycle` (Decision 19). Reason: the gate must see the same shape of reference data the real run gives it, or the replay proves nothing about the real gate.
7. **`private_terms_available=True` with `private_terms=()`.** Reason: `framework/briefing/gate.py:418-426` shows false is a fail-closed violation (`L1_PRIVATE_TERMS_UNAVAILABLE`), so a false here would reject every draft for a reason that has nothing to do with the story. The output says in one line that the real run also checks a private word list and this replay's list is empty because nothing here is private. `load_private_terms` is never called (Decision 19), so the replay never goes near the real list.
8. **The limits are the real slot limits: `ProfileLimits(timezone="Europe/Madrid", allowed_start=13:00, allowed_end=23:30)`.** Reason: these are the defaults the real propose command uses (`framework/cycle/__main__.py:403-405`), and `pick_hour`/`allowed_windows` take them as arguments, so the replay's hour is picked under the same rules as the real card's.
9. **The hour comes from `pick_hour(slot, busy, limits)` and the free intervals from `allowed_windows(slot, limits)`, called once and shared by both goals.** Reason: that is what `run_proposals` does (`framework/cycle/__init__.py:188-189`), the hour is an input to `propose`, and sharing it is why both card sides offer the same hour.
10. **Proposals come from `propose` in `framework/proposal/core.py`, once per goal, against a recorded client that implements the `WonderClient` protocol (`framework/proposal/core.py:80-87`) and returns canned replies in order.** Builder gets two replies (the planted one, then the corrected one), Disconnect gets one. The client reports fixed transport strings and zero latencies. Reason: this runs the real parse (`parse_draft`), assembly (`assemble_briefing`), gate (`evaluate_briefing`) and one-retry path (`framework/proposal/core.py:493-494`), so section 3 shows the product's actual retry, not a re-enactment. The output names no model for this client; it says the wording is written by hand in the shape the model returns and no model ran.
11. **On current main the planted Builder draft is rejected with `L1B_NUMBER_WITHOUT_METRIC_REF`, and the plan does not pin the exact code list.** Reason: `assemble_briefing` fills metric values from the snapshot (`framework/proposal/assembly.py:41-44`), and the draft carries metric ids only (`framework/proposal/schemas.py:26-31`), so the records' value on the claim is always right and the lie can only live in the sentence's number, which then has no backing ref. That mechanism — not the checker's `L1B_METRIC_VALUE_MISMATCH`, where the supplied ref itself disagrees with the records — is what the plain sentence after the code describes. A gate change landing soon adds `L1B_VALUE_PERIOD_MISMATCH` to this draft, so the tests pin only: first attempt has at least one code, second attempt has none.
12. **Every printed error code is followed by its plain sentence from a small map in the new package, with a generic sentence for a code the map does not know.** The map covers at least `L1B_NUMBER_WITHOUT_METRIC_REF` (the sentence says a number no cited record backs, and code fills the cited values from the records, so the false number lives in the words), `L1B_METRIC_VALUE_MISMATCH` (a cited value differs from the records) and `L1B_VALUE_PERIOD_MISMATCH` (a number is tied to the wrong one of the three periods). Reason: a stranger must understand each code where it appears, and an unknown future code must degrade to a true generic sentence, never fail the replay or print a bare code.
13. **Reply templates name a fact by what it covers, never by id; the replay fills the real id in before handing the reply to `propose`.** A template carries a marker naming the code-fact family and member (for example the pushes pair), the replay finds that fact among the `extract_facts` results, and substitutes its minted id (`framework/glimmer/facts.py:143-146`). Reason: fact ids are a hash of statement and evidence, so hard-coding one would let a rewording in the fact layer silently break the recording; naming by coverage fails loudly instead, as a drift check (Decision 17).
14. **The two commitments come from the recording, in the wording style of `profiles/commitments.example.json`: "Build the synthetic parser sketch" for Builder and "Call the synthetic family line" for Disconnect**, with ids, kinds, dimensions and evidence kinds copied from that file's matching entries (`profiles/commitments.example.json:2-9,107-115`). Reason: `propose` only offers commitments it is given, the example file is not in the wheel, and these two titles are already the repo's published synthetic pair, so the card reads like the real product's card.

The replay imports these from `framework.telegram.models` and `framework.telegram.chart` directly, never through `framework.telegram.service` (Decision 19). Reason: those functions are pure and already pinned by the telegram tests; reimplementing any of them would make the replay prove something about a copy.

The chart's series come from the snapshot's period values (Decision 20), so what the bars show is what the facts were counted from.

Reason: the recording is data a future edit can break; the command must notice and say so in one line instead of printing a story that no longer happened.

Reason: on a phone the person taps; in a terminal nobody is waiting, so the choice is an argument with a default, and showing the would-be row and the count moving is the honest picture of what a tap does.

## Steps

## Risks

- **The corrected draft failing a gate rule nobody aimed at.** The gate also checks metric labels, period words and direction (`framework/briefing/gate.py` binding checks), so a hand-written corrected sentence can fail for a second reason and turn the story into a fallback. Mitigated by shaping the corrected sentence on the code facts' own statement shape (`framework/glimmer/code_facts.py:78-112`: label, both period words, both numbers, one direction), by the story checks failing loudly at exit 1, and by Step 7's rule: fix the template wording, never the gate.
- **`uv run --no-default-groups` pruning an existing environment.** If the installed `uv` removes dev/app packages when groups are excluded, `make check` right after `make try` would fail. Mitigated by Decision 27's before/after package-list check and AT5; if it prunes, the implementer stops and amends the plan rather than shipping a `make try` that breaks the clone.
- **The dependency move slowing the checker's clean install.** Moving three packages into `[project].dependencies` makes every `verify-claims` install carry them (measured at about 0.4 seconds and 30 MB of cache).

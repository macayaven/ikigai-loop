Ticket 14c — a voice-corrected card keeps its `slot_cards` rows on the live path. ## Success Criteria

- **Live corrected cards carry rows.** With no explicit store path and `IKIGAI_DATA_DIR` pointing at the live store folder, a corrected card gets its `slot_cards` rows before it is sent: the unchanged side copied with the new card id and letter, the changed side from its new result, with the handling instant as its `as_of`.
- **Live matching uses the rows.** With no explicit path, the card matching in `_answer_correction`, in the fact-dispute path and in `build_corrected_card` reads the stored rows keyed by letter, as the existing tests already do with an explicit path, instead of falling back to the display-string comparison.
- **Live retries are recorded.** A retried local start failure during a re-proposal writes its `local_start_retries` row with no explicit path, as it does with one.
- **Explicit path unchanged.** Every existing voice and telegram test passes unedited. A run with an explicit path writes exactly the rows it writes today.
- **Backfill.** `python -m framework.voice backfill-slot-rows` rebuilds, from stored rows only, exactly the rows the fixed worker writes for the same note. It is a dry run by default, writes only with `--apply`, writes each card's rows in one transaction, never touches a card that already has rows, and skips a card it cannot rebuild exactly, with a closed reason code and nothing written for it. It never calls a model or the network, never writes events, and never touches `telegram_cards` or `voice_notes`. Its printed output holds counts and ids only.
- **Gate green.** No file in the gate closure changes. The full gate, `make check` and `make eval`, passes under the environment prefix in Acceptance Tests; the coordinator runs that gate herself, capped, outside the implementation session.

### Key decisions (binding on the implementer)

- **D1 — The three functions resolve the path the way the rest of the worker does, then carry on.** In `_slot_rows`, `_save_corrected_rows` and `_record_local_retries`, I pass `resolve_db_path(deps.db_path)` (and `resolve_db_path(ctx.deps.db_path)`) to `SlotLedger` instead of returning early. `resolve_db_path` is already exported from `framework.store` at [framework/store/__init__.py:4](../../framework/store/__init__.py:4), and the worker already imports from that package at [framework/voice/worker.py:62](../../framework/voice/worker.py:62), so the fix adds one name to an existing import and removes three guards. With an explicit path `resolve_db_path` returns it unchanged, so nothing moves for any existing test or run. In `_record_local_retries` the `ctx.slot is None` arm stays: that arm is not a store-path skip, `_repropose` asserts the slot is set at [framework/voice/worker.py:1070](../../framework/voice/worker.py:1070), and removing it would change a guard that is not part of this fault.
- **D2 — There is no fourth place, and I checked the whole of both packages.** I read every `db_path` use in `framework/voice/` and `framework/telegram/`. Each one either hands the value to a store or ledger whose constructor resolves `None` (the lines under Approach), or already holds a resolved path: `_latest_sent_card` is called with `card_ledger.db_path`, which `CardLedger` resolved at construction, at [framework/voice/worker.py:397](../../framework/voice/worker.py:397); `_event_recorded` resolves before connecting at [framework/voice/worker.py:2095](../../framework/voice/worker.py:2095); `show_chain` opens the two ledgers and lets them resolve. The three guards in D1 are the only places in either package that skip work when the store path is `None`. If the implementer's own search finds a fourth, it gets the same one-line fix and a line in the session note; the plan does not expect one.
- **D3 — What changes on the live path, said plainly.** A corrected card sent on the live path now carries its `slot_cards` rows, so a tap on it is counted by `rebuild_state` instead of skipped. The matching in `_answer_correction`, in the fact-dispute path and in `build_corrected_card` now uses the stored rows keyed by letter, which is the path the existing tests already run with an explicit path; the display-string fallback still serves cards sent before slot rows existed, exactly as its comments say. Retried local start failures during a re-proposal are recorded on the live path. Nothing else on the live path changes: no card text, no outcome code, no send order.
- **D4 — One shared row builder, used by the worker and by the backfill.** I take the row-building core out of `_save_corrected_rows` into one pure function in [framework/voice/worker.py](../../framework/voice/worker.py), `_corrected_rows(old_rows, card, changed, offers, *, as_of)`, where `offers` maps a profile id to its `(commitment_id, kind)` pair or to `None`. It returns the rows `_save_corrected_rows` writes today: an unchanged side copies its old row with the new card id and letter; a changed side with an offer takes that commitment and kind, with slot, subject, bucket, pick and alternative from its old row and `as_of` from the argument; a changed side with no offer writes no row. `_save_corrected_rows` keeps its signature, builds `offers` from the fresh results through `_result_commitment` against the commitments file exactly as today, passes `as_of=ctx.now`, and keeps its key-hit swallow, so the worker's behaviour is the same line for line. The backfill builds `changed` and `offers` from stored rows (D6) and passes the note's applied instant. No second copy of the row rules exists anywhere.
- **D5 — The backfill command sits next to `show-chain`, with the same store argument.** In [framework/voice/__main__.py](../../framework/voice/__main__.py) I add one subcommand, `backfill-slot-rows`, with `--db` resolved exactly as `show-chain` resolves it at [framework/voice/__main__.py:30](../../framework/voice/__main__.py:30), and one flag, `--apply`. Without `--apply` it writes nothing. The work lives in `framework/voice/worker.py` beside `show_chain`, as one function that returns the text to print, so the CLI stays a thin edge and tests call both the function and the CLI. It reads only `telegram_cards`, `voice_notes`, `slot_cards` and `proposal_results`; it writes only `slot_cards`, only under `--apply`; it never writes events and never touches `telegram_cards` or `voice_notes`.
- **D6 — How the backfill decides changed from unchanged, from stored rows only.** For one corrected card: the voice note that names it as `new_card_id` gives the replaced card as its `matched_card_id` and the handling instant as its `applied_at`; the replaced card's `slot_cards` rows tie each replaced side to a profile, keyed by letter as `_profile_id_for_side` does; the corrected card and the replaced card both come from `telegram_cards`. A corrected side ties to the replaced side for the same profile by that profile's display string, so a lone side relettered to A still ties to its own old row. A side whose kind, title, start and end all equal the replaced card's side for the same profile is unchanged. Any other side is changed, and its commitment and kind come from the stored results for that profile and slot whose kind and hour match the side: for a proposal result the hour is its stored hour and the commitment is its briefing's first action; for a fallback result the hour is its fallback window and the commitment is its fallback commitment. Stored results means every `proposal_results` row for that subject and slot, not only the latest per profile: `results_for_slot` keeps the latest row per profile at [framework/store/proposal_store.py:482](../../framework/store/proposal_store.py:482), which would hide two rows naming different commitments, and hiding them is guessing. So `ProposalStore` gains one additive read that returns every stored row for a subject and slot in row order, sharing the one row-to-`StoredResult` build with `results_for_slot`, whose behaviour does not change. Before counting distinct commitments, the backfill drops any candidate that would rebuild the replaced side itself: a candidate whose commitment equals the commitment in the replaced side's slot row and whose kind and hour equal the replaced side's kind and hour. Such a result cannot be the source of a side that differs from the replaced side; the regular card's own stored result sits next to the re-proposal's at the same kind and hour, naming the commitment the replaced side offered, and counting it would turn every such card into a false `AMBIGUOUS_RESULT`. Only then does more than one distinct commitment mean `AMBIGUOUS_RESULT`. The worker checks a changed side's commitment against the commitments file when it builds the card; a card that was really sent passed that check then, so the backfill reads no commitments file and checks nothing against it.
- **D7 — Skips are closed, whole-card, and write nothing.** A card is skipped, with nothing written for it, under exactly these reason codes: `INCOMPLETE_LINK` when the corrected card, its note link, the matched card id or the applied instant is missing, or a corrected side ties to no replaced profile; `NO_REPLACED_ROWS` when the replaced card has no `slot_cards` rows; `MISSING_RESULT` when a changed side matches no stored result for its profile, slot, kind and hour; `AMBIGUOUS_RESULT` when the matching stored results name more than one distinct commitment. A profile that stood on the replaced card but has no side on the corrected card was dropped by its new result and writes no row, as the worker writes none; that is not a skip. Each card's rows are written in one transaction through `SlotLedger.save_slot_cards`, which already commits its rows together at [framework/cycle/slot_ledger.py:445](../../framework/cycle/slot_ledger.py:445), so a failed card leaves no half-written side behind, and a write error stops the command with a non-zero exit after the cards already written, each of them whole.
- **D8 — Output is counts and ids only, and the totals are pinned.** For each card the dry run and the `--apply` run print the same lines: one `write card_id=<id> message_id=<id> letter=<letter> profile_id=<id> commitment_id=<id> kind=<kind>` per row it writes or would write, one `skip card_id=<id> message_id=<id> reason=<code>` per skipped card, and one `already_present card_id=<id> message_id=<id>` per card that already has rows. Then the totals: `seen=<n>`, `to_write_cards=<n>`, `to_write_rows=<n>`, and one `skipped_<reason>=<n>` line per reason that occurred. No title and no transcript text appears anywhere in the output; the only values printed are card ids, the voice note's message id, letters, profile ids, commitment ids, kinds, reason codes and counts. A card that already has rows is never touched, so a second `--apply` prints `to_write_cards=0` and `to_write_rows=0` and writes nothing.
- **D9 — No file in the gate closure changes.** The files this ticket modifies are [framework/voice/worker.py](../../framework/voice/worker.py), [framework/voice/__main__.py](../../framework/voice/__main__.py), [framework/store/proposal_store.py](../../framework/store/proposal_store.py) and the two test files. None of them is in the 47-file closure I listed under Approach. The one new import (D1) names `framework/store/__init__.py` and `framework/store/store.py`, which are inside the closure, but it changes neither: importing a name from them is fine, editing them is not. `framework/store/proposal_store.py` itself is outside the closure. The implementer re-runs `closure_files` and checks the diff against it (AT6); a touched closure file is a stop-and-report, not a fix-up.

### What the brief left out (checked against the code)

- **D10 — Two notes can name the same corrected card, and the smaller message id wins.** A resumed note and its first pass share one `new_card_id`, and nothing in the schema stops two rows naming the same new card. The backfill takes the note with the smallest message id for that card, because message ids rise in send order and the first note is the one that built the card. The choice is deterministic, so a dry run and its `--apply` agree.
- **D11 — A corrected card with no voice note is out of the backfill's reach, and I leave it out.** The handling instant and the replaced card both come from the note. A card in `telegram_cards` whose `replaces_card_id` is set but which no note names has no stored handling instant to write as `as_of`, so inventing one would be guessing. Such a card is not counted in `seen`. If one exists on the live store, it needs its own ticket; this command does not go looking for it.
- **D12 — `save_slot_cards` is already one transaction, so D7 needs no new transaction code.** Its insert loop and commit sit in one `_write` call at [framework/cycle/slot_ledger.py:450](../../framework/cycle/slot_ledger.py:450). The backfill re-checks that the card still has no rows immediately before saving; a key hit then means a row landed in between, the save raises, that card writes nothing, and the command counts it as `already_present` instead of failing, mirroring the worker's own key-hit rule.

## Risks

- **The resolver reads the environment at call time, so a test can pass against the wrong file.** A no-explicit-path test that sets `IKIGAI_DATA_DIR` after a store has already resolved, or that seeds one file and resolves another, would pass or fail for the wrong reason. A3 pins the shape — folder first, file inside it, environment set before the note runs — and B2 reads the rows back through the same resolver the worker used, so a split-brain test cannot go green quietly.
- **The shared builder drifts from the worker's rows.** The whole backfill rests on D4: one builder, two callers. If the extraction reorders a field or drops the key-hit rule, the worker's explicit-path behaviour moves and the backfill inherits the move. The existing row tests pin the worker's rows field by field, K1 pins the two paths equal, and both must be green before anything else counts.
- **The backfill writes a wrong row to a real store.** It runs on stored rows only and skips the whole card whenever the stored rows do not name exactly one commitment per changed side (D7), so its failure shape is a skipped card with a code, never a guessed row. It is still a write to an append-only table: `slot_cards` refuses updates and deletes, so a wrong row cannot be edited away. That is why applying it to any real store is the coordinator's call (Step 9), why the dry run prints every row it would write first, and why this ticket never runs it outside made-up stores.
- **A corrected card whose note is missing stays row-less.** D11 leaves it out on purpose: without the note there is no handling instant to write. The risk is reading a clean backfill report as "every corrected card now has rows". The totals say what was seen, and `seen` counts only cards a note names (A4), so the report never claims the note-less card. If the live store holds one, it surfaces as a tap still skipped, and it gets its own ticket.
- **Two results at one slot name the same commitment twice, or the old one once.** Re-proposals at a slot write further `proposal_results` rows under suffixed keys, so the all-rows read in D6 can see the same commitment from two runs. That is one distinct commitment, not `AMBIGUOUS_RESULT`: the code compares distinct commitments, never row counts. And the regular card's own stored result sits next to the re-proposal's at the same kind and hour, naming the commitment the replaced side offered — that candidate is dropped before the count (D6), so it never turns a clean re-proposal into a false `AMBIGUOUS_RESULT`. K6's ambiguous case names two different commitments, neither of them the replaced side's, and K10 pins the dropped-candidate case, so a row-count check would fail both loudly.
- **The gate closure grows into this ticket's files.** The closure follows imports from the gate files; today it reaches none of the touched files (D9). A new import from a gate file into the voice or store code would change that without any edit here. AT6 re-runs the closure on the branch and reads the diff against it, so the drift is caught before the gate, not by it.

- Cards corrected before slot rows existed, and corrected cards no voice note names (D11). The backfill rebuilds only what stored rows can prove, for cards a note names.

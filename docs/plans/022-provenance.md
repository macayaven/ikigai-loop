## Success Criteria

- **Isolation.** All new code lives in `framework/provenance/`. No file in `framework/cycle/orchestrator.py`, `framework/cycle/__main__.py`, `framework/cycle/__init__.py`, `framework/cycle/card_build.py`, `framework/cycle/slot_ledger.py`, `framework/cycle/trace.py`, the stores, the Glimmer modules or the proposal modules changes at all, not even a dispatch line. No module outside `framework/provenance/` imports it. The new modules may import existing modules read-only.
- **Export.** `python -m framework.provenance.export --db <path> [--out <file>]` prints or writes one JSON object per line, one line per slot that has ledger rows, sorted by slot instant. Same database, same bytes: no export time, reading order with `slot` first (never sorted keys; bytes stay stable because the model fixes the field order), ASCII only. Regenerating the whole log after each card is the update path. With `--out`, write to a temp file beside the target and rename into place, and the final file keeps normal permissions for a tracked file, not a temp file's. If the existing `--out` file holds a slot the new export lacks, or can't be parsed line by line, refuse with a closed code, leave the file untouched and exit 2. Without `--out`, print to stdout. Stderr gets one line of counts only: slots, cards, delivered, cited facts by origin.
- **Read-only.** The export opens the database read-only by URI, never uses the `SlotLedger`, `FactStore`, `ProposalStore` or `EventStore` constructors because they run DDL and migrations (the same choice [framework/cycle/trace.py](framework/cycle/trace.py:3) explains), and runs all SELECTs in one read transaction. Main file bytes and `sqlite_master` are unchanged after a run.
- **Honest counts.** `facts_cited` by origin (`code`, `model`, `unknown`) counts only facts cited by claims that reached the card. A true zero prints as `0`. Any missing value prints the word `unknown`, never zero and never null, except the pinned real zeros on a no-card line and a `no-cycle` side. A missing `facts` table, a missing `origin` column or an unparseable briefing makes the affected counts `unknown`.
- **Closed strings.** Every emitted string passes through a Pydantic model on `SchemaModel` with Literals and constrained strings, validated before anything is written. If a line fails, write nothing and exit 1 with a closed code. Model ids leave only as a safe basename, and a test proves it.
- **Glimmer proof.** `make glimmer-proof` runs `framework/provenance/glimmer_proof.py`. It refuses inside a real slot's Glimmer window before reading the environment or touching the network, proves the front door without loading anything, runs one synthetic label, then reads the served weights. Its output holds no private address, path or key on any path, including failures.
- **Docs.** `docs/MODELS.md` (at most 340 words, first person, one table, then how to check each claim, then two or three plain sentences) names which model does which job, where it runs, what crosses to the network, and the check commands. An empty `docs/provenance.jsonl` is in the file list so the link resolves, and a test validates every line of that file against the same schema. One sentence goes into `docs/PRIVACY.md`, one Status bullet into `README.md`, and one line each into the `AGENTS.md` Layout and Commands sections. Nothing else in those files changes.
- **Gate.** `make check` is green. No test uses the network beyond loopback, and tests use made-up data only. Canary strings in tests stay low-entropy plain words, so gitleaks has nothing to flag, and no key-shaped strings appear anywhere.

## Approach

### Binding decisions

- **Package layout.** New package `framework/provenance/` with exactly `__init__.py`, `export.py` (CLI plus line builder), `schemas.py` (closed line models), `glimmer_proof.py`, and `__main__.py` only if needed for `python -m framework.provenance.export` dispatch; I keep `export.py` as the module so `python -m framework.provenance.export` works without a package `__main__`. No other package imports it. Stdlib plus pydantic only; `pyproject.toml` and `uv.lock` stay untouched. A perceived need for a new dependency stops the ticket for amendment.
- **What a card is.** I follow `latest_card_id` in [framework/cycle/slot_ledger.py](framework/cycle/slot_ledger.py:620): the slot's last `card` step row decides, including a trailing `card` row with a NULL id. A `--fresh` run that ends in such a row means no card: the line says `no_card` with no sides, the older built id counts as superseded, and the noop sits in `not_on_card`. `--fresh` can also leave an older card id at a slot, which by the orchestrator's refusal rule at [framework/cycle/orchestrator.py](framework/cycle/orchestrator.py:835) never reached me as delivered; I print how many were superseded as a count (`superseded_cards`), never the id. A card built but not delivered still gets its line, with its send outcome, because hiding failed sends would make the log a highlight reel. A slot whose run produced no card also gets a line, marked plainly as no card. A delivered card whose side rows are gone (or whose `slot_cards` table is missing) prints the word `unknown` for `facts_cited` and `cycle_origin`, since a zero would not be real; a real no-card slot keeps `none` and real zeros. I state this here as a decision so review cannot read it as an oversight.
- **Slot identity.** `slot_ledger.slot` and `slot_cards.slot` hold UTC text ([framework/cycle/slot_ledger.py](framework/cycle/slot_ledger.py:193)); `proposal_results.slot` holds the offset as given ([framework/store/proposal_store.py](framework/store/proposal_store.py:335)). I compare as instants, never as text. The latest row per profile at the instant wins, matching `results_for_slot` at [framework/store/proposal_store.py](framework/store/proposal_store.py:426). The line's `slot` is the slot instant in Madrid local time with offset, and it is the only timestamp in the line.
- **Allowlist, and nothing else.** Each line holds only: `slot`; `delivery` (exactly `delivered`, `DELIVERY_UNKNOWN`, `SEND_NOT_SENT`, `SEND_REFUSED`, `intent_open` — an intent row with no outcome after it for that card, so delivery can't be ruled out — `not_sent` — a card with no send rows at all — `no_card`, or `unknown`, read from that card id's own `send` and `send_intent` rows, never the slot's; the word `none` from `send_state` never prints); `final_code` (every line, replacing any no-card code: the outcome of the slot's last ledger row ignoring `watchdog` rows, which `check-slot` appends after `done`, through the closed-code rule plus the lower-case words `delivered` and `killed`; a last row that says `ok` or `none`, or no row, prints `unknown`); `facts_model_step` (once per line, not per side: the slot's last `facts_model` outcome from the closed set `ok`, `SKIPPED`, `FACTS_DEADLINE`, `MODEL_DOWN`, `FACTS_UNPARSED`, `killed` that the orchestrator writes for that step; an exception class name prints the placeholder; no such row prints `unknown`); `forced` (true if any of the slot's `start` rows, written at [framework/cycle/orchestrator.py](framework/cycle/orchestrator.py:849), says so, false if a start row exists and none does, `unknown` if there is no `start` row); `superseded_cards`; `cycle_origin` for the card as a whole (`model`, `code`, `none`, `mixed` or `unknown`); `facts_cited` for the card as a whole, distinct cited facts by origin (`code`, `model`, `unknown`); `not_on_card`, one compact entry per profile whose latest result at the slot has no side on the card (a noop, or a proposal dropped by `COMMITMENT_GONE`), each with only `profile`, `kind`, `reason_codes`, and nothing in it counts toward `facts_cited` — this explains a one-sided card and a no-card slot; `sides`, one entry per card side in letter order, each with `letter`, `profile` and `kind` from their closed sets, `reason_codes`, `local_retries` (a count), `timeout_retries` (a count, summed over every `propose_<profile>` row of the side at the slot: a row with no such key adds nothing, a value that is not a non-negative whole number makes the side's count the word `unknown`, and a side with no such row at all prints `unknown`), `facts_cited` for that side, `metrics_cited` (a count of distinct metric ids on the side's shown claims, which are always computed by code), `cycle`, and `attempts`; `attempts`, one entry per stored Wonder attempt in order with `model_requested`, `model_reported`, `transport`, `muse_version`, `effort`, `latency_ms`, `prompt_tokens`, `completion_tokens`, `reasoning_tokens`, `cached_tokens`, `parsed_ok`, `blocked`, `gate_codes` (codes only, never locations); and `cycle` per side with `origin`, `facts_available` by origin (counting only the tiers `_rebuild_facts` in [framework/cycle/__init__.py](framework/cycle/__init__.py:104) passes to Wonder, that is `public` and `private` at line 120), `dropped_codes`, and `passes`, one per stored Glimmer pass with `name`, `attempts`, `model_reported`, `latency_ms`, `completion_tokens`, `finish_reason`, `kept`, `noop_reason`. A side with a stored result and a present attempts table and no attempts has an empty list, which is itself the statement that no model wrote that side.
- **Never selected.** I never select statements, titles, claim text, raw responses, prompts, prompt hashes, snapshots, hours, `as_of`, windows, evidence, event rows, subject ids, card ids, cycle ids, proposal keys, commitment ids, policy picks, bucket, message ids, stderr, card and chart payloads, learner state, or gate-code locations. I use explicit column lists everywhere, and I never select `seconds`, `as_of` or `subject_id` either: nothing needs them. The file holds one subject, so I apply no subject filter; join keys are read and never printed, which is the one allowance. `briefing_json` is the one exception: I parse it in memory only to walk fact ids and metric ids, and nothing from it but counts leaves. The `Attempt` shape carries no `finish_reason`: it is not on the allowlist.
- **Cited means on the card.** `build_statements` in [framework/cycle/card_build.py](framework/cycle/card_build.py:58) keeps at most 3 claims per proposal side, first `overall_state` claim first, while the draft schema allows more. A fact cited only by a claim that never reached the card is not load-bearing and must not count. The export has its own selection, since `card_build.py` cannot change, and a test feeds one briefing to both and asserts the export selects exactly the claims whose texts `build_statements` returns, so a later change there fails loudly.
- **Distinct and joins.** A fact cited twice on a side counts once per side; at card level distinct means distinct on `(cycle_id, run, fact_id)`, so the same fact id in another cycle counts again. Both sides of a card usually share one cycle. Facts join on `(cycle_id, run)` from the side's own `proposal_results` row, as the trace does at [framework/cycle/trace.py](framework/cycle/trace.py:380). A cited id with no row in that cycle counts as `unknown`. Card-level counts print the word `unknown` if any side's count is the word `unknown`.
- **Cycle origin.** I take it from the stored `passes` of the side's own `(cycle_id, run)`: any pass with attempts above zero means `model`; `code` only if the list holds entries and every one has a real zero; anything else (missing numbers, non-dict entries, an empty list, no row, unparseable) means `unknown`; `no-cycle` means `none`. A pass missing `attempts`, `latency_ms` or `kept` prints the word `unknown` for those fields, never 0, and the same goes for an attempt's unreadable `latency_ms`, `parsed_ok` and `blocked`. A stored JSON null `noop_reason` is a real value meaning no noop happened, so it prints `none`; a missing key prints `unknown`. It does not come from the ledger's `facts_model` step, because that step says `ok` when both passes were unavailable, and it does not come from comparing cycle ids, because with nothing to send the model the two ids can be equal. `facts_model_step` still prints once on the line beside it. Unparseable or missing `reason_codes`, `dropped_codes` or `passes` print the word `unknown`, never an empty list and never a one-item placeholder list; an empty list only ever means a real empty list, and a side on `no-cycle` keeps real empty lists. A missing `local_start_retries` table prints `local_retries` as `unknown`, never 0. Deep JSON counts as unparseable, and `main` maps any other exception to its class name as a closed code, exit 1, never a traceback. Card-level `cycle_origin` is `mixed` when the two sides disagree and neither is `unknown`, `unknown` when any side needed for the card is `unknown`, else the shared value. I pin this aggregation here because the brief names the card-level field without defining the mix rule.
- **Facts available and edge rows.** I count facts stored for the side's `(cycle_id, run)` whose tier is in (`public`, `private`), grouped by stored `origin`, because those are the facts Wonder could cite. If the `facts` table or its `origin` column is missing, or the stored cycle row cannot be read, available counts are `unknown`. A fallback side has no claims, so its cited counts are real zeros. A no-card line has empty `sides`, `facts_cited` real zeros and `cycle_origin` `none`. A side whose `proposal_results` row is missing, or a missing attempts table, has `attempts` as the word `unknown`, never an empty list; a missing `proposal_results` row also prints `reason_codes` as the word `unknown`, never an empty list. A side on `no-cycle` has origin `none`, `facts_available` real zeros and `passes` empty.
- **Read transaction and path.** All SELECTs run in one read transaction, so a slot writing at the same moment cannot give a line that mixes two states. I build the read-only URI with proper encoding (`pathlib.Path.as_uri()` or `urllib.parse.quote`), so a space or a hash in the path works. Errors print one closed code and never a path: no database, not a database, unreadable. A file with no ledger tables is exit 0 with zero lines, not an error.

### Closed shapes and code families

I build each line through Pydantic models on `SchemaModel` ([framework/schemas/base.py](framework/schemas/base.py:11)) with Literals and constrained strings, so a line cannot hold free text by construction, and I validate before writing anything.

- Profile, kind, letter, transport, effort, delivery, pass name are closed sets. Anything else prints `unknown`. Profiles are `builder` and `disconnect` ([framework/cycle/card_build.py](framework/cycle/card_build.py:300)); kinds are `proposal`, `fallback`, `noop` ([framework/proposal/core.py](framework/proposal/core.py:144)); letters are `A`, `B` ([framework/cycle/card_build.py](framework/cycle/card_build.py:41)); transports are `muse` ([framework/proposal/muse_client.py](framework/proposal/muse_client.py:263)), `api` ([framework/proposal/client.py](framework/proposal/client.py:103)) and `unknown` ([framework/proposal/core.py](framework/proposal/core.py:137)); efforts are `minimal`, `low`, `medium`, `high` ([framework/proposal/client.py](framework/proposal/client.py:34)); delivery is exactly the eight words pinned in the allowlist, read per card id from [framework/cycle/slot_ledger.py](framework/cycle/slot_ledger.py:122); pass names are `personal`, `feed` ([framework/glimmer/facts.py](framework/glimmer/facts.py:101)).
- Codes match upper-case letters, digits and underscores, and start with one of the families the source actually uses, which I grepped again for this amendment: `L0_` / `L1_` / `L1B_` from the gate ([framework/briefing/gate.py](framework/briefing/gate.py:142)), `NOOP_` from the fact passes ([framework/glimmer/facts.py](framework/glimmer/facts.py:221)), `FACT_` from dropped facts ([framework/glimmer/facts.py](framework/glimmer/facts.py:359)) and `CODE_` wrapping a check failure ([framework/glimmer/facts.py](framework/glimmer/facts.py:408)), `FALLBACK_`, `MODEL_`, `PROPOSAL_`, `DRAFT_` and `PARENT_` from the proposal core and its neighbours ([framework/proposal/core.py](framework/proposal/core.py:266)), `CYCLE_` from staleness ([framework/proposal/core.py](framework/proposal/core.py:194)), the whole code `NO_CYCLE` from the no-cycle result ([framework/cycle/__init__.py](framework/cycle/__init__.py:169)), and the orchestrator families `SLOT_`, `SEND_`, `DELIVERY_`, `CHART_`, `PREFLIGHT_`, `TERMS_`, `STALE_`, `COMMITMENT_`, `COMMITMENTS_`, `FACTS_`, `DISCONNECT_`, `LEARNER_`, `CALENDAR_` and `BUCKET_` ([framework/cycle/orchestrator.py](framework/cycle/orchestrator.py:612)). I also allow `CORRECTION_` and `CONTRIBUTOR_`; I assume an in-flight voice ticket uses them, so they survive when it lands. A value that fails prints one fixed placeholder word (`CODE_UNKNOWN` is not allowed because it would invent a family; I use the single word `unknown` in the code slot only where the field itself allows it, else the fixed placeholder `OTHER_CODE`) and still counts, so a new family on `main` later loses detail and leaks nothing. Exception class names, which the ledger also stores as outcomes, print as that placeholder. I pin the placeholder as `OTHER_CODE` here; it starts with no listed family on purpose, so tests can assert it.
- `slot` is exactly a Madrid instant with offset (`+01:00` or `+02:00`), enforced in the model too. Code fields enforce the family rule in the model too, not just the builder. `final_code` is a valid code, `OTHER_CODE`, `delivered`, `killed` or `unknown`. `finish_reason` is a closed set of the real values (`stop`, `length`, `completed`, `tool_calls`, `content_filter`, `cancelled`) or `unknown`, so a private lower-case word gets through neither the builder nor the model. `muse_version` is only the version number pulled from the stored first line of `muse --version` (stored via `transport_version` from [framework/proposal/muse_client.py](framework/proposal/muse_client.py:286)); for example from `Muse Code 1.4.14 (1.4.14-R7309.1)` it prints `1.4.14`. No number found prints `unknown`.
- Model ids: only a basename ever gets out, and a test must prove it. A trailing separator means a directory, so `unknown`. A last component directly under a parent named `home` or `Users`, or `/root` itself, is `unknown` whoever runs the export, on a plain path and on a URL's path alike. For a URL the basename comes from its path only, and no path means `unknown`. A basename with no letter in it, such as a bare port number from `host:port`, is `unknown`. A name ending in a domain suffix such as `.net`, `.com`, `.org`, `.local`, `.lan`, `.internal` or `.home` looks like a host, so `unknown`. The runtime username, the home directory's name and the hostname, read at runtime, refuse as a whole name bounded by non-alphanumerics or the string's ends (so a hyphenated hostname still matches inside a name), except that a name shorter than 3 characters is ignored. A test builds the runtime-username string from the runtime username, never a literal. `unreported` and empty print `unknown`. I cover forward slashes, backslashes, a trailing slash and backslash, URL forms with and without a path, URL paths under `home` or `Users`, a bare `host:port` and other letter-less basenames, a query string, an scp-style path, a dotted version id, whitespace and an at-sign form in tests.

### Glimmer proof: binding order

`framework/provenance/glimmer_proof.py`, run by a new Makefile target `glimmer-proof`. Its output carries the served weights' basename, the endpoint's shape and one synthetic result with its timing. No private address, path or key appears on any path through the code, including failures. The order is binding:

1. **Refuse inside a real slot's Glimmer window, first, before reading the environment or touching the network.** The window is slot minus 25 minutes to slot minus 4 minutes, both ends inclusive, for all five `SLOT_TIMES` ([framework/cycle/orchestrator.py](framework/cycle/orchestrator.py:108)) on any day, in Madrid time whatever the machine's zone. I import `SLOT_TIMES` and `FACTS_SLOT_RESERVE` ([framework/cycle/orchestrator.py](framework/cycle/orchestrator.py:476), 4 minutes) from the orchestrator; a test pins the 25 against `inspect`'s view of `run_slot`'s default (`lead_minutes: int = 25` at [framework/cycle/orchestrator.py](framework/cycle/orchestrator.py:672)). The call itself has a 300 s timeout (`LABEL_CALL_TIMEOUT_S` at [framework/glimmer/label_step.py](framework/glimmer/label_step.py:27)), so a start that could still be running when the window opens also refuses: the refused range runs from the window's start minus that timeout to the window's end. I print a closed code and the first second it may run, Madrid time, and exit 3. There is no flag, no environment variable and no other way past this. The clock is an injected function argument in tests only, and the GET timeout is a module constant the test patches so the timeout test stays short.
2. **Configuration** comes from `build_label_client` in [framework/glimmer/label_step.py](framework/glimmer/label_step.py:313), which reads `LOCAL_LLM_*` and refuses a base URL that is not private (`is_private_llm_base_url` at line 257). It runs with the 300 s timeout. Failures print closed codes or the variable's name, never its value. The alias must name Glimmer, or it refuses before any call, because a request for another alias would evict the resident model.
3. **Prove the front door without loading anything.** I read these shapes from my own running llama-swap on Nov 2, passive endpoints only, and I give the shapes, not the values: `GET /v1/models` returns a `data` list whose entries have `id`, `owned_by` (the value is `llama-swap`) and `meta.llamaswap` holding `runtime` and `quant` among others; `GET /running` returns a `running` list whose entries have `model`, `state` (`ready` when loaded), `cmd`, `proxy`, `ttl`, `name`, `description`. Both go to the base URL's root (only a trailing `/v1` comes off its path, so a prefix and an IPv6 host survive), each GET with its own short timeout, and every request carries the bearer key, so a server with auth answers 401 to a wrong key and the proof stops closed. An empty `running` list is the normal nothing-loaded state: it proceeds with resident `no`, and only a missing key or a non-list value is a shape failure. A plain runtime, whose own `/v1/models` says `owned_by` `llamacpp`, answers neither way, so it refuses with a closed code, exit 2, and sends no POST. If `/running` names any other model in any state, it refuses with a closed code, exit 3, rather than evict someone's work, without naming that model; my own alias in a state other than ready means resident `no`, and it proceeds. I use the existing no-redirect opener in [framework/glimmer/llm.py](framework/glimmer/llm.py:30), so the key never follows a redirect.
4. **One synthetic result.** One invented calendar title, a constant in the module, goes through the pinned label prompt in [framework/glimmer/label_step.py](framework/glimmer/label_step.py:29) to the client above. I take a title from `evals/r10_cases.json` whose recorded answer in `evals/r10_results/muse-glimmer-30b.jsonl` is correct, in plain English, naming no one. The answer is one of eight words (`LABELS` in [framework/schemas/events.py](framework/schemas/events.py:13)), so no free model text is ever printed, and it takes about 20–30 s where a fact pass takes 4–9 minutes. I state the trade-off plainly: labels are off for the real run, so this proves the weights and the serving path, and the per-card log from Part 1 carries the evidence for the fact path.
5. **Weights.** The chat response's `model` field holds a path whose basename is the weights file; that basename, through the same model-id rule as Part 1, is the first source, unless it equals the alias or is unknown, in which case the chat call gives no basename. Then, only after that call succeeded, I read only `/running` to decide whether `/upstream` is safe (`/v1/models` is not read twice): only if it now shows the alias ready do I read `GET /upstream/<alias>/props`, an object with `model_path` among other keys, and take its basename: that is what the serving process itself reports. The order matters: a GET under `/upstream` can load a model, so it must never be a first probe. If the chat call gives no basename, the weights come from props and `corroborated` prints `unknown`, because that is one source; if neither source gives a basename, it exits 1 with its own closed code. Two filenames that agree print yes, two that differ exit 1, and a filename with unreadable props prints unknown and exits 0. Unknown is fine and exits 0. A disagreement exits 1.
6. **Verdict and exit codes, pinned.** 0: verdict OK, including an unknown corroboration, and including a valid label that differs from the expected one, printed as `matched=no`, because the proof is about the weights and the path. 3: refused for now, by the window or another model resident. 2: configuration or front door refused. 1: everything else, including an invalid label, an unavailable model, a disagreement and weights not named glimmer (the served basename must contain the word glimmer, case-insensitively, and no readable basename from either source is also exit 1).

Output is plain `key=value` lines a judge can read: weights, corroborated, alias, `front_door=llama-swap`, runtime and quant from `meta.llamaswap` through closed shapes that keep their original case (so `UD-Q4_K_XL` prints as itself; either prints `unknown` if it carries no closed value), whether the model was already resident, `endpoint=POST /v1/chat/completions` when the base path is exactly `/v1` else `endpoint=other`, `tls`, `host=private` or `host=loopback` (never the host or port), `synthetic_title` and `synthetic_label`, whether it was valid and matched the expected answer, latency in seconds, completion tokens, tokens per second, finish reason, verdict. I say in one line that latency includes any wait behind another request, because Glimmer serves one at a time. The refusal's `next=` prints the first second it may run, Madrid time. Before printing, one check over the whole output refuses to print it if it contains the key, the base URL's host or the home directory as whole strings anywhere, case-insensitively, or the username, the hostname or the home directory's name as a whole name bounded by non-alphanumerics or the string's ends, reusing the model-id helper, and prints a closed code instead; in that check, like the model-id rule, a name shorter than 3 characters is ignored, so a CI runner's username can't make the proof's own words fail. ## Risks

- **Leak through a new code family or exception name.** A future `main` change could store a code or class name that carries text. I mitigate with the closed code shape, the fixed placeholder that still counts, and class names printing as the placeholder, plus the canary walk over every TEXT column so a newly selected column fails loudly.
- **Selection drift from `build_statements`.** If `card_build.py` changes its 3-claim rule, cited counts would silently change meaning. The shared-briefing test in AT3 fails loudly instead, by design.
- **Origin read from the wrong place.** Reading origin from the ledger's `facts_model` step or from cycle-id equality would mislabel code-only cards as model cards. I pin origin to stored pass attempts and keep `facts_model_step` printed once on the line so a reader can see both.
- **Zero read as unknown, or unknown read as zero.** Either direction breaks the number this ticket exists for. The honest-zero table pins both, and `unknown` is a word, never `0` or null, so the two can never be confused by a parser.
- **Glimmer proof evicting a resident model.** A proof call for the wrong alias, or an early `/upstream` read, could load or evict a model during a real slot. The window refusal runs first, the alias must name Glimmer, a resident other model refuses, and `/upstream` is only read after a successful chat call with the alias ready.
- **llama-swap shape drift.** The shapes are read from my server on Nov 2 and pinned in Approach; if a later server changes them, the proof refuses closed. That is the safe direction; I amend only the proof module if needed.
- **Small doc edits colliding with other tickets today.** The `README.md`, `docs/PRIVACY.md` and `AGENTS.md` edits are one line or one sentence each, in place, so they merge cleanly. I touch nothing else in those files.

### Decisions D1 to D23, each with its reason

**D1. Package and names.** New package `framework/telegram/` with a CLI at `python -m framework.telegram`. The public names are the list above, re-exported from `framework/telegram/__init__.py`. I choose the module layout in the table above. Pyright strict covers all of it. Reason: one import surface for Tickets 13 and 14 and for tests, strict typing from the first line, and a CLI shape that matches `framework/collectors/__main__.py:135-142`.

**D2. Card type.** `Card` and `Proposal` are `SchemaModel` subclasses (`framework/schemas/base.py:11-12`: frozen, extra forbidden). They are not added to `EXPORTED_MODELS`, so `schemas/*.json` and `tests/test_schemas_export.py:16-19` stay untouched; another branch is changing the export list and the gate types, and this ticket touches none of that. `Proposal`: `letter` is `Literal["A", "B"]`; `kind` is `Literal["proposal", "fallback"]`, required with no default; `reason_codes` is a tuple of strings, default empty, each matching `^[A-Za-z0-9_.:-]{1,64}$`; `profile`, `title`, `start`, `end` are as follows: `start` and `end` aware datetimes with `end` after `start`. A side of kind `"proposal"` must have no reason codes. A side of kind `"fallback"` may have zero or more. The class keeps the name `Proposal` even when `kind` is `"fallback"`, because other tickets plan against the name. `Card`: `slot` aware; `since_line` is `str | None`; `proposals` a tuple of 1 or 2 with unique letters and A before B when both are present; a single proposal may be either letter; `statements` a tuple of non-blank strings that may contain newlines. A card still has one or two sides, so two noops cannot build a card, and sending nothing is the caller's job.

| Sides on the card | since_line | statements |
|---|---|---|
| At least one side of kind "proposal" | Required, single-line, non-blank | Zero or more |
| Every side of kind "fallback" | Must be None | Must be empty |

A `since_line` or a statement on a fallback-only card is a `ValueError` at construction. A card with a side of kind `"proposal"` and no `since_line` is a `ValueError` at construction. Only `since_line`, `profile` and `title` are single-line: no newline, no carriage return, and non-empty after stripping. A statement must be non-blank and may contain newlines; statements are stored and sent exactly as given. Times render in Europe/Madrid whatever offset the input carries, so `17:00Z` on 2026-11-02 renders `18:00`. A card whose rendered text exceeds the caption limit fails at construction with `ValueError`. Nothing is silently cut. The card input is plain values only. `framework/telegram/` imports only from `framework.schemas`, `framework.store`, `framework.collectors.common` and `framework.telegram` (AT15). It imports nothing from Ticket 11's code, nothing from `framework.briefing` and nothing from any model client. Reason: the card must stay buildable while the gate types change on another branch, a fallback must carry no factual prose by construction, and a cut caption would change what I ruled on without telling me.

Validation detail I pin here so tests can be exact: single-line means the value contains neither `"\n"` nor `"\r"` and `value.strip()` is non-empty; the stored value is the value as given, not stripped, because `statements` must reach Telegram verbatim and the same rule keeps `profile` and `title` honest. A reason code that fails the pattern above is a `ValueError`. Reason codes on a side of kind `"proposal"` are a `ValueError`. The caption check at construction renders the card text and compares its UTF-16 length (D8) against 1024; the check lives in a `model_validator(mode="after")` on `Card` that calls the same render function the sender uses, so construction and sending can never disagree about the text.

**D3. Card id.** `card_id` is a property derived from the card: `"card-"` plus the first 16 hex characters of the sha256 of canonical JSON of the card, with datetimes normalised to UTC, so the same instant under another offset gives the same id. The same card re-sent keeps its id. Ticket 13 reads `card.card_id`. Canonical JSON here means one helper, `_canonical_card_json(card)`, that builds a plain dict from the card with every datetime written as `.astimezone(UTC).isoformat()`, then applies `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False)` to that dict. The dict keys are `slot`, `since_line`, `proposals` (each with `letter`, `kind`, `reason_codes`, `profile`, `title`, `start`, `end`) and `statements`, in sorted-key order from the dumps call, so field order in the model never changes the id. `kind` and `reason_codes` are part of the canonical JSON, so they are part of the card id. Reason: identity must survive a re-send and an offset change, or the same card would take two rulings under two ids. I record under Disagreements that 16 hex characters is a birthday-bound choice, and I keep it because the brief fixes it; the ledger's primary key still refuses a silent overwrite (D9).

**D4. Callback data.** Format `"<card_id>:<target>"`, target one of `A`, `B`, `neither`, `wrong`, `why`. The Telegram limit is 64 bytes; a test asserts it on every button built. A `card_id` is `card-` plus 16 hex characters, so 21 bytes, plus 1 colon byte, plus at most 7 target bytes (`neither`), so 29 bytes at most; the test still asserts the limit on the built payload, not on this arithmetic. Parsing is strict: split must give exactly two parts, the first must match `^card-[0-9a-f]{16}$`, the second must be one of the five targets, and anything else is invalid: answered, counted, not stored. The card id always comes from the callback data, never from "the current card". Reason: a stale keyboard on an old card must rule on that old card (D14), and strict parsing keeps a crafted payload out of the store.

**D5. Event.** Source `"telegram"`, type `"app.tap"`, `source_id` `"<card_id>:<target>"`, data `AppTapData(block_id=card_id, target=target)` (`framework/schemas/events.py:123-126`), tier `"private"`, id `event_id(source, source_id)` (`framework/collectors/common.py:95-98`), `subject_id_from_env()` (`framework/collectors/common.py:90-92`), `collector_version` `"telegram@0.1.0"`. `time` and `collected_at` come from an injectable `now_fn`, because a `callback_query` carries no date. So a second tap on the same button has a different time, and `append_event` raises `ConflictingEvent` for it, since time is in `_identity_key` (`framework/store/store.py:126-135`) and `_append_one` raises at `framework/store/store.py:168-173`. The handler catches exactly that and counts a duplicate. Tap events never go to `poll_transaction`, because it would write a row to the `conflicts` table for every double tap (`framework/store/store.py:256-267`). The acceptance test uses a clock that advances between the two taps, asserts one event, no exception and zero rows in `conflicts`. A frozen clock would hide this bug, because with equal times the second append would look like an identical re-delivery and return `False` at `framework/store/store.py:166-167`. Reason: a double tap is normal phone behaviour, not a data conflict, and the store must record one ruling while the `conflicts` table stays meaningful for real collector conflicts.

**D6. What a ruling is.** `A`, `B` and `neither` are rulings; `wrong` and `why` are not. Tap A then tap B on one card, through a stale keyboard, stores both events. The ruling for a card is the earliest ruling event by `(time, id)`; `first_rulings(events) -> dict[card_id, target]` is the one place that says so, and it only reads source `"telegram"` `app.tap` events. Pure function: it takes an iterable of `Event`, keeps those with `source == "telegram"` and `type == "app.tap"` and a ruling target, groups by `data.block_id`, and picks the minimum by `(time, id)` per card. Note the store's own ordering in `events_between` is `(time, id)` (`framework/store/store.py:303`), so `first_rulings` agrees with a store read without depending on input order. The keyboard edit shows that first ruling, whichever tap arrived second, and the toast tells me which ruling stands. A later ruling never moves the keyboard. A tap on a fallback side is a ruling like any other: same event, same target, same `first_rulings`, and the event does not say which kind the side was. `kind` and `reason_codes` live in `telegram_cards` through `card_json` and are part of the card id's canonical JSON (D3), so the learner reads them with `load_card`, because a ruling for a fallback is not the same signal as a ruling for a gated proposal and the reader of that data must be able to tell. Reason: my first tap is my answer; a second tap through a stale keyboard is stored for honesty and never rewrites what the card shows.

**D7. Keyboard.** Kind changes no button. Before a ruling: one row per proposal in letter order (`[Take A]`, then `[Take B]`), then one row `[Neither now] [Something's wrong] [Why?]`. With one proposal, only that proposal's button row shows, then the three-button row. After a ruling, via `editMessageReplyMarkup` using `callback_query.message.chat.id` and `message_id`: one row with `"✓ "` plus the chosen label, carrying the same callback data so a re-tap is an idempotent duplicate, then one row `[Something's wrong] [Why?]`. The chosen label is `Take A`, `Take B` or `Neither now`, matching the target. A `wrong` or `why` tap never edits the keyboard, because I must still be able to rule after asking why. Telegram answers 400 `message is not modified` to an identical edit; that is a success. Reason: the card on my phone must show the standing ruling (D6), and asking why must not spend my chance to rule.

Button labels are exact strings: `Take A`, `Take B`, `Neither now`, `Something's wrong`, `Why?`. The post-ruling first row label is `"✓ " + <chosen label>`, for example `✓ Take A` or `✓ Neither now`. The callback payload on the post-ruling button is the same `"<card_id>:<target>"` as the button it replaces, so a re-tap produces the same `source_id` and lands in the D5 duplicate path.

**D8. Sending.** `send_card(card, chart, *, db_path=None, client=None) -> SentCard(card_id, message_id)`. One `sendPhoto` with the PNG, the card text as caption and the inline keyboard as `reply_markup`, so one card is one message and one notification, and a failure leaves no half-sent card. The card is written to the card ledger before the send, so a tap can never beat it and a crash after the send loses nothing. `send_card` writes the ledger row for every card except `SAMPLE_CARD`; that one check lives in `send_card`, so a sample never leaves a row in `telegram_cards`. No `parse_mode` anywhere; a test asserts it across every recorded request. `multipart/form-data` is built by hand from the standard library: `chat_id` and `caption` as text fields, `reply_markup` as a JSON string field, `photo` as a file part with a fixed filename `card.png` and `image/png`, a random boundary checked against the payload, CRLF line ends. The boundary check is: generate the boundary, encode the full body, and if the boundary bytes appear anywhere in the payload parts, regenerate; loop at most 100 times, then raise `TelegramError("sendPhoto failed")` without payload content. The caption limit is 1024 and the message text limit is 4096, both measured in UTF-16 code units so an astral character counts 2 and cannot push a message over. The helper is `utf16_len(text) = len(text.encode("utf-16-le")) // 2`, in `models.py`, used by the card validator, the Why? splitter and the client guard. The allowed chat id for the send comes from `TELEGRAM_CHAT_ID` read at call time through the client's config check (D17); `send_card` takes no chat argument, because there is exactly one allowed chat (D11). When `client` is `None`, `send_card` builds a `TelegramClient()`; when `db_path` is `None`, the ledger and store resolve through `resolve_db_path` (`framework/store/store.py:86-93`). Reason: one message means one notification and no orphan chart with no buttons, and the ledger-first order closes the race where I tap faster than the write.

**D9. Card ledger.** Why? must work after a restart and from another process, and the learner needs to know what A and B were on a card. A class in this package, `CardLedger` in `ledger.py`, opens its own sqlite3 connection on the same `resolve_db_path` file as `EventStore`, with its own `CREATE TABLE IF NOT EXISTS` for `telegram_cards(card_id primary key, card_json, created_at)` and `telegram_voice_arrivals(message_id primary key, received_at, duration_s)`. The store DDL in `framework/store/store.py:17-58` does not change, and `framework/store/store.py` is not edited. `load_card(card_id, db_path=None) -> Card | None` is public: it opens a ledger on the resolved path, reads `card_json`, validates it back into a `Card`, and returns `None` when the row is absent. A card already present stays as it is: the insert is `INSERT OR IGNORE` semantics by an explicit existence check, never an overwrite. `card_json` is `card.model_dump_json()`; `created_at` is the UTC isoformat of the write time from an injectable clock where the caller has one, else the ledger's own `datetime.now(UTC)`. The ledger connection is opened per operation or per service run in the calling thread (D19); the class holds a path, not a shared connection, so two processes and a restart both work. Reason: the statements and the A/B meaning of a card must outlive the process that sent it, and the event store's append-only tables are the wrong place for a mutable lookup table.

**D10. Poll order.** Per update, in this order: filter; append the event; side effects (answer first, then edit or reply); advance the cursor with `poll_transaction("telegram", [], {"offset": update_id + 1, "foreign_total": n})`. The cursor advances after each update, not after each batch. A crash at any point re-delivers at most one update. The store dedupes it and the side effects are idempotent: a re-answered query or a repeated edit is non-fatal, and a repeated Why? reply is accepted and disclosed here, not hidden. A failed side effect never stops the update or the loop; it is counted in `PollStats.side_effect_errors`. When `sqlite3.Error` hits an update (the event append, reading rulings back, the ledger read, or the cursor write), the callback is answered with the store-failure toast, that update's cursor does not advance, and the rest of the batch is not processed, because the next update's cursor write would pass the failed one and lose the tap. `poll_once` returns with `store_errors` raised; `run_poll_loop` backs off when `store_errors` grew and refetches. Any other `Exception` while handling one update (a validation error from an old ledger row, a bug) is caught at the per-update boundary and counted in `PollStats.handler_errors`; the callback is answered with `Could not handle that tap.` if its id is known, and the cursor advances, because not advancing would wedge the loop on that update forever. `BaseException` (`KeyboardInterrupt`, `SystemExit`) propagates with no cursor advance. `poll_transaction` with an empty event list is used only as the cursor write, so tap events still never enter it (D5). The cursor offset is `max(current offset, update_id + 1)`, so it can never go backward. The cursor JSON is `{"offset": int, "foreign_total": int}`; a missing cursor means offset `None` on the first `getUpdates` and `foreign_total` 0. A cursor that is present but not a dict with those int fields is malformed: `poll_once` and `run_poll_loop` raise `TelegramConfigError("telegram cursor is malformed")` with no stored values in the message and no `getUpdates` sent, so `run_poll_loop` stops and the CLI prints that line and exits 1, because guessing an offset would either re-rule old cards or skip new ones. One private helper runs one batch and returns `(PollStats, progressed)`, where `progressed` says the cursor moved; `poll_once` returns the stats and `run_poll_loop` uses both, with one store open per iteration and no race between the reads. One `try` holds the whole loop iteration: `sqlite3.Error` anywhere in it counts `store_errors`, backs off and continues. Only `TelegramAuthError`, `TelegramConfigError` and `BaseException` leave `run_poll_loop`; `poll_once` still lets `sqlite3.Error` from opening the store propagate, so the CLI prints one error line. Reason: at-most-one re-delivery per crash, with every re-delivery harmless, is the strongest guarantee this design can make without a public endpoint.

Side-effect order inside one callback update, pinned: (1) build and append the event, catching `ConflictingEvent` as a duplicate and `sqlite3.Error` as a store error; (2) `answerCallbackQuery` with the toast text for the outcome (ruling recorded, duplicate, invalid, unknown card, sample, store error); (3) the edit or reply for this tap, unless the store failed, in which case no edit or reply happens because the ruling state is not known. When the store fails, step 2 still runs with the toast `Not stored yet. Retrying.` and the cursor does not advance, so the same update returns on the next poll and the tap can land then. That toast text is a fixed line, not an f-string over an exception, and the rest of the batch is not processed.

**D11. Filter.** The allowed identity is `int(TELEGRAM_CHAT_ID)`, my private chat with the bot, where chat id equals user id. A `callback_query` is processed only when `from.id` and `message.chat.id` both equal it; a `message` only when `from.id` and `chat.id` both equal it. Values from the process context are strings and update ids are ints, and a unit test must carry ints in the update and a string in the context. So the comparison is `update_from_id == allowed_id` where `allowed_id` is the parsed int and the update values must be ints, not strings: a string `"123"` in an update does not equal int `123` and is foreign. Odd update shapes follow one rule, checked in this order:

- Not a dict, or `update_id` absent or not an int: counted `malformed`, no cursor advance, the batch continues.
- Neither `message` nor `callback_query`: counted `unhandled`, stored nowhere, no reply, cursor advances.
- `from.id` or the chat id absent or not an int (a bool is not an int): foreign, because it can't be proven to be me. No outward call. For a `callback_query` the chat id is `message.chat.id`, so a `callback_query` with no `message` lands here.
- `callback_query` from me with no string `id`: `malformed`. There is nothing to answer. Cursor advances.
- `callback_query` from me with `data` absent, not a string, or failing the strict parse (D4): `invalid`, answered with the invalid toast, not stored, cursor advances.
- `message` from me with a voice value that fails the `VoiceNote` field checks (D16): `malformed`, nothing stored, handler not called, cursor advances.
- `message` from me with anything else: `unhandled`, stored nowhere, no reply, cursor advances.

A foreign update makes no outward call of any kind, including `answerCallbackQuery`, stores nothing from the update, still advances the cursor, and raises the foreign count: per run in `PollStats.foreign` and durably as `foreign_total` in the cursor JSON, so the count and the offset commit together in the same `poll_transaction` call. `allowed_updates` is `["message", "callback_query"]`, sent on every `getUpdates`. A malformed `TELEGRAM_CHAT_ID` (missing, blank, or not an optional minus followed by ASCII digits) raises `TelegramConfigError` naming the variable, never the value (D17), before any `getUpdates` call. Reason: any other chat or user is not me, and answering a foreign callback would both leak that the bot is live and spend a call on someone I do not serve.

**D12. Why? reply.** `sendMessage` with `disable_notification` true, `link_preview_options` `{"is_disabled": true}`, and `reply_parameters` pointing at the card message with `allow_sending_without_reply` true, so a late Why? attaches to the right card. `reply_parameters` is `{"message_id": <card message_id>, "allow_sending_without_reply": true}`; the card message id comes from `callback_query.message.message_id`, never from the ledger, because the ledger stores the card, not the message. No model call is made. The reply pieces, in order, are: the statements verbatim and first; then, for each fallback side in letter order, one fixed line `"<letter> has no checked facts this time."` with `" Reason codes: X, Y."` appended when that side has any, where `X, Y` is its codes joined by `", "` in stored order. With no statements, the reply starts with the fixed line `No cited statements on this card.`, and any fallback lines follow it. On a card with no fallback side the reply is the statements joined by a blank line, verbatim, `"\n\n".join(statements)`, or that one fixed line when there are none. Each message stays within 4096 UTF-16 code units, splitting between pieces, and inside a piece only when one piece alone exceeds the limit, never inside a surrogate pair. The splitter is pinned: the statements and each fixed fallback line go through the same splitter, each as its own piece; walk pieces in order, pack whole pieces joined by `"\n\n"` into the current message while the UTF-16 length fits; when one piece alone exceeds 4096 UTF-16 units, cut it at the largest prefix whose UTF-16 length fits and whose last code point is not a high surrogate, then continue with the rest as a new piece; pieces of one split piece are separate messages in order. Every Why? tap replies, even when the event was a duplicate, because I may ask again tomorrow. An unknown card gets a toast saying I no longer have it, and no reply. The tap is still stored (D14 for the unknown-card storage rule). The reply goes to the allowed chat id from the callback's `message.chat.id`, which the filter has already proven equal to the allowed id. Reason: the cited statements are the reason for the ruling, they must arrive word for word, and a silent reply would read as a dead bot.

**D13. Something's wrong.** Stores the tap, answers with a toast, and sends one fixed request for a voice note, `disable_notification` true and attached to the card like Why? (same `reply_parameters` shape, same `link_preview_options`). The fixed request text is: `Tell me what is wrong in a voice note.` The request is sent only when the event was newly inserted; a duplicate gets only the toast. Reason: one request per card state is enough; a second identical request would be a second message asking for the same note, and Ticket 14 owns everything after the note arrives.

Toasts, one row per outcome, exact strings. `<label>` is `Take A`, `Take B` or `Neither now`; `<first label>` is the standing ruling's label. Every toast is at most 200 characters, which is Telegram's callback answer limit, and every toast here is far under it.

| Outcome | Toast |
|---|---|
| Ruling newly stored | `Recorded: <label>` |
| Re-tap of the standing ruling | `Already recorded: <label>` |
| A different ruling after one stands | `Stored. Standing ruling: <first label>` |
| `wrong` newly stored | `Noted. Voice note please.` |
| `wrong` duplicate | `Already noted for this card.` |
| `why` on a known card | `Sending the cited statements.` |
| `why` on an unknown card | `I no longer have that card.` |

**D14. Late and odd taps.** A late tap stores against its own card, from the callback data (D4), however old the card is. `answerCallbackQuery` answering 400 `query is too old` is non-fatal, counted in `answer_errors`, and never stops the update. When the ledger knows the card and the tapped letter is not on it, the tap is invalid: answered, counted in `invalid`, not stored. This check needs the card: load it, and if `target` is `A` or `B` and no proposal carries that letter, it is invalid. `neither`, `wrong` and `why` are always on a known card. When the ledger does not know the card, the tap is stored because the format is valid; the ruling still counts, and only the Why? reply degrades (no card, no statements). The post-ruling keyboard needs only the card id and the first ruling, so the edit is attempted on an unknown card too. A `why` tap on an unknown card follows D12. A `wrong` tap on an unknown card is stored and answered, and the voice-note request is still sent, attached with `allow_sending_without_reply` true, because the request does not need the card body. The first ruling for every ruling tap comes from one helper: `first_rulings` over `store.events_between(subject_id_from_env(), datetime(2000, 1, 1, tzinfo=UTC), now + timedelta(days=1), types=["app.tap"])`, filtered to the card. For the sample card, which stores nothing, the first ruling is the tapped target. If that store read raises `sqlite3.Error`, D10's store-failure rule applies. Reason: old cards stay in my chat for days, and a tap on one is still a ruling about that card.

**D15. Sample cards never reach the learner.** The CLI's sample card is a module constant with invented values in the illustrative layout and a fixed slot, so its id is fixed. Its `since_line` is `Since 15:30: sample card, synthetic values.`, its one statement is `Sample statement, synthetic values.`, its proposals follow the illustrative card, and both sides are of kind `"proposal"` with no reason codes. Its chart shows the real shape with invented small values: period labels `earlier`, `prior`, `last`; screen categories `code`, `comms` and `feed`; pushes labelled `pushes`; tally `Builder`, `Disconnect`, `Neither`. A tap on it runs the whole flow (answer, edit, reply) but appends nothing to the event store, and counts as `sample` in `PollStats`. The edit and the Why? reply still work because the handler special-cases the sample id: it loads `SAMPLE_CARD` instead of the ledger when the callback card id equals `SAMPLE_CARD.card_id`. `send_card` writes no ledger row for it (D8), and a tap on it writes none either; the sample is recognised by id comparison alone. Reason: nothing live is simulated, and a tapped sample in the real store would be a fabricated ruling in append-only data. The sample check happens after the filter (D11) and after strict callback parsing (D4), and before any store append; a foreign tap on the sample is foreign, not sample.

**D16. Voice.** `VoiceNote` is a frozen type: `message_id`, `date`, `file_id`, `file_unique_id`, `duration_s`, `mime_type`, `file_size`, `reply_to_message_id`. Field types: `message_id: int`, `date: int` (Telegram epoch seconds, kept as given), `file_id: str`, `file_unique_id: str`, `duration_s: int`, `mime_type: str | None`, `file_size: int | None`, `reply_to_message_id: int | None`. It is a frozen dataclass, not a `SchemaModel`, because it is parsed from a Telegram update inside this package and is not a wire contract I export; the parser builds it only when every required field has the right type, else the update is malformed under the D11 ordered rule. `VoiceHandler = Callable[[VoiceNote], None]`. The default handler writes one row to `telegram_voice_arrivals(message_id, received_at, duration_s)` and nothing else: no `file_id`, no `getFile`, no download. `received_at` is the UTC isoformat of `now_fn()` at handling time. A re-delivered note adds no row: the insert is keyed on `message_id` primary key with ignore-on-conflict. A handler that raises is counted in `voice_errors` and does not stop the loop, and the update still advances. The contract for Ticket 14, stated here because Ticket 14 plans against it: the handler must return quickly and persist its own work, because the poll loop processes one update at a time and a model call inside the handler would hold every tap behind it. The handler receives only the `VoiceNote`; if Ticket 14 needs the audio, it adds a `TelegramClient` method for `getFile` and download itself (D23), and it must not block the loop while doing so. Reason: arrival is a fact I can store today with no file handling and no token-bearing download URL in any table.

**D17. Transport.** `TelegramClient(api_base="https://api.telegram.org", sleep_fn=time.sleep)` holds no token. `api_base` has trailing slashes removed. It calls `urllib.request.urlopen` by attribute, so a monkeypatch reaches it: the code writes `import urllib.request` and calls `urllib.request.urlopen(...)`, never `from urllib.request import urlopen`. There is exactly one function that reads the token and builds the URL, `_request_once(method, request, timeout_s)` in `client.py`, used by both the JSON call path and the multipart path. `_request_once` never raises. It builds the `urllib.request.Request` inside its `try`, so a scheme-less `api_base` returns `failure_kind` `"network"` instead of raising a `ValueError` with the token in its message from outside the `try`. That function:

- strips the value and checks it against `^[0-9]+:[A-Za-z0-9_-]+$` with `fullmatch`, because a token with a stray newline or space makes `http.client.InvalidURL` print the whole URL in its message. A missing or malformed token returns `failure_kind` `"config"` and the caller raises `TelegramConfigError` naming the variable, never the value, after the return, because raising in the frame that holds the value would expose it under `capture_locals`. The same shape holds for the chat id: `_allowed_chat_id()` returns `None` unless the value is an optional minus followed by ASCII digits, so `"1_000"` and `"+5"` are `None`, and the caller raises `TelegramConfigError` naming `TELEGRAM_CHAT_ID`, never the value. Both are read at call time, the token inside `_request_once` and the chat id inside `_allowed_chat_id()`, never at import time and never cached on the client.
- catches `Exception`, not a list. `http.client.HTTPException` (`IncompleteRead`, `RemoteDisconnected`, `BadStatusLine`, `InvalidURL`) is not an `OSError`, and `read()` can fail after the status line. The existing collectors' narrower catch at `framework/collectors/common.py:62-63` is the counterexample that proves the list is not enough.
- returns a plain result `(status, headers, body, failure_kind)` and never raises. `failure_kind` is one of `None`, `"network"`, `"config"`. Before returning, it replaces the raw token and its percent-encoded form in the body, so nothing downstream can hold the token even when a server echoes the URL. The replacement text is the fixed string `[redacted]`. The percent-encoded form is `urllib.parse.quote(token, safe="")`. Headers are returned as a plain dict with lower-cased keys, and header values are not scrubbed because no request header carries the token; the URL is the only carrier, and the URL itself is never returned.

Every raise happens in a frame after that function has returned, outside any `except` block. The reason: `HTTPError` keeps `.url` and `.filename`, `JSONDecodeError` keeps `.doc`, and `raise X from None` only sets `__suppress_context__` while `__context__` still holds the original exception. No frame local on the traceback holds the token or the URL. So the call path is: `result = _request_once(...)`; then, in straight-line code with no active exception, classify the result and raise the pinned error. JSON parsing also happens after return, and a `JSONDecodeError` is caught, dropped, and re-raised as a plain `TelegramError` subclass in a later statement, never chained. Error messages are `"<method> network error"`, `"<method> invalid response"` or `"<method> failed (status N): <description>"`, with the description cut to 120 characters. The description is the Telegram `description` field from a valid JSON error body, scrubbed by the token replacement above; `TelegramApiError` carries it as a `description` attribute, already scrubbed and cut to 120 characters. When the body has no usable description, the message is `"<method> failed (status N)"` with no trailing colon. The description stays because the first real run will likely answer 403 until I press Start, and `failed (status 403)` alone tells me nothing. No log line in this package logs a URL, a body, a description, or an exception object; logging holds the method name, a status, a count or an exception class name, at DEBUG only. The package logs nothing above DEBUG and the tests assert `caplog` stays free of the token at DEBUG (D21).

Client surface, pinned: `TelegramClient.call(method, payload=None, *, timeout_s=30.0, attempts=4) -> Any` returns the decoded `result` value of a Telegram `ok: true` body and raises the D18 classes otherwise; `TelegramClient.send_photo(chat_id, photo, caption, reply_markup, *, timeout_s=30.0) -> dict` returns the decoded message dict and uses `attempts=4`; `TelegramClient.get_updates(offset, long_poll_s, *, timeout_s=None) -> list` returns the raw update list, computing its socket timeout as `long_poll_s + 15` when `timeout_s` is not given (D18), and uses `attempts=1` and never sleeps. Side effects inside the poll (answer, edit, reply, voice request) use `attempts=2` and `timeout_s=10`, so a network blip can't hold the taps behind them for minutes. `call` builds a JSON POST body with `json.dumps(payload)` and header `Content-Type: application/json`. Method names are validated by the caller side of this package only; the client itself accepts any method string, because Ticket 14 will add `getFile` through this same client (D23).

**D18. Failure classes.** One retry loop serves both paths: `call` and `send_photo` go through one private method taking `(method, request, timeout_s, attempts)` and returning the decoded result, with `send_photo` keeping its own check that the result is a dict, so Ticket 14's `getFile` has one obvious path to reuse.

- Network class: no status, 5xx, or a body that is not valid JSON. Between attempts, `call` sleeps through `sleep_fn`: network class 1, 2, 4 s, within the `attempts` bound (D17: `call` defaults to `attempts=4`, `send_photo` uses `attempts=4`, `get_updates` uses `attempts=1` and never sleeps, side effects inside the poll use `attempts=2` and `timeout_s=10`). After the last attempt it raises `TelegramTransportError("<method> network error")` for no-status and read failures, `TelegramTransportError("<method> invalid response")` for a non-JSON body on a 2xx, and `TelegramApiError("<method> failed (status N): <description>")` for a 5xx that stays 5xx. A non-JSON body on a non-2xx status is classified by its status, not as invalid JSON, because a proxy's HTML 502 page must still read as a server failure. Reason for pinning this split: the retry decision follows the status when there is one.
- 429: between attempts, sleep exactly `parameters.retry_after` when it is at most 300 s, falling back to the `Retry-After` header, then to the network backoff. A zero or negative `retry_after`, from the parameter or from the header, is treated as absent: a zero would spin the poll loop with no sleep, and `time.sleep` raises on a negative. A 429 above 300 s, or a 429 with no attempts left, raises `TelegramRateLimited` with `retry_after: int | None`, message `"<method> rate limited (retry_after=<n>)"`. `TelegramRateLimited` is a subclass of `TelegramApiError`.
- 401 and 404: `TelegramAuthError`. Stops `run_poll_loop` and propagates out of `poll_once` and the CLI as an error line with exit 1.
- 409 on `getUpdates` (a webhook or a second poller): `TelegramConflict`. `PollStats.conflicts` is counted by `run_poll_loop`. A 409 on any other method is a plain `TelegramApiError`, because only `getUpdates` has the two-pollers meaning.
- Any other 4xx: `TelegramApiError`, no retry. The `message is not modified` 400 on `editMessageReplyMarkup` and the `query is too old` 400 on `answerCallbackQuery` are recognised by the service layer and treated as success or counted non-fatally there (D7, D14); the client raises them as `TelegramApiError` like any other 4xx, and the service catches exactly that class and matches on the `description` attribute with a case-insensitive substring match, never a prefix check, because real descriptions start with `Bad Request: `.
- `poll_once` does no backoff and catches nothing from `getUpdates`. Every `TelegramError` propagates. So the CLI's `poll --once` prints `error: getUpdates failed (status 409): Conflict: ...` and exits 1, where the description tells me whether it is a webhook or a second poller.
- `run_poll_loop` on `getUpdates`: a `TelegramRateLimited` with a `retry_after` sleeps exactly that long whatever its size, counts `rate_limited`, does not grow the backoff, and continues (Telegram told me when to come back, and stopping the loop would only hand the wait to a supervisor). A `TelegramRateLimited` without a `retry_after`, `TelegramTransportError`, any other `TelegramApiError` or `TelegramError`, and `sqlite3.Error` count (`rate_limited`, `poll_errors`, `store_errors`) and back off 1, 2, 4 up to 60 s, reset on success, each reported through `on_batch` before the sleep. `TelegramAuthError` and `TelegramConfigError` propagate, as does `BaseException`; nothing else leaves the loop. A non-empty batch that makes no cursor progress (`update_id` unusable) also makes `run_poll_loop` back off.
- Socket timeouts: `getUpdates` uses `long_poll_s + 15`, so an idle long poll is never a timeout; other calls use a fixed 30 seconds. The test asserts the timeout passed to `urlopen` is greater than the timeout sent to Telegram: for `long_poll_s=50`, the body carries `"timeout": 50` and `urlopen` receives `timeout=65`.
- Odd update shapes follow the one ordered rule in D11, checked in that order, with no second definition here. A bool is not an int for any of those checks, matching the repo's own care at `framework/collectors/spotify.py:79`.

Exception hierarchy, pinned: `TelegramError(Exception)` is the base. Subclasses: `TelegramConfigError`, `TelegramTransportError`, `TelegramApiError`, `TelegramAuthError`, `TelegramConflict`, `TelegramRateLimited` (which extends `TelegramApiError` so a caller catching API errors still sees it, and which carries `retry_after: int | None` and the `description` attribute). Every message follows the D17 shapes. No exception carries a URL, a body, a header value, or the token, in its message, its args, or any attribute.

**D19. Entry points.** `poll_once(*, db_path=None, client=None, long_poll_s=0, on_voice=None, now_fn=...) -> PollStats` runs one `getUpdates` and handles it; it does no backoff and catches nothing from `getUpdates`, so every `TelegramError` propagates. `run_poll_loop(*, db_path=None, client=None, long_poll_s=50, on_voice=None, stop=..., now_fn=..., sleep_fn=..., on_batch=None) -> PollStats` blocks until `stop()` is true. `on_batch: Callable[[PollStats], None] | None = None` is called after each non-empty batch and after each counted failure in the loop (conflict, rate limit, poll error, store error), before the sleep, with the accumulated stats. An `on_batch` that raises leaves the loop, because it is the caller's own code. The loop's contract in D10 and D18 stays true for everything else. `stop` is checked before each `getUpdates`. Each opens its own `EventStore` and ledger in the calling thread, because sqlite3 connections are bound to their thread. `now_fn` default is `lambda: datetime.now(UTC)`; `stop` default is a callable returning `False`, so a bare `run_poll_loop()` runs until an auth error or a keyboard interrupt; `sleep_fn` default is `time.sleep`. `on_voice=None` selects the default ledger handler (D16). Nothing here reads a schedule or a clock to decide when to send: the only clock reads are `now_fn()` for event times and the backoff sleeps. `poll_once` with `long_poll_s=0` is the `--once` path and the test path. Both return the accumulated `PollStats`; `run_poll_loop` accumulates across iterations. Ctrl-C arrives as `KeyboardInterrupt`; `_request_once` catches `Exception`, so it does not catch it, and `run_poll_loop` does not catch it either. The CLI catches it (D20).

**D20. CLI.** `python -m framework.telegram send-sample` prints `sent card_id=<id> message_id=<n>`. `python -m framework.telegram poll [--once] [--long-poll N]` prints one counts line of `key=value` counts after each non-empty batch and after each counted failure, through `on_batch`, and at exit on Ctrl-C. `main(argv=None, *, client=None, db_path=None, now_fn=None) -> int`. Errors print `error: <message>` on stderr with exit 1. The counts line prints every `PollStats` field as `key=value` in field order, space-separated, one line, so a failure is never hidden by a shorter line. There is no `SIGINT` handler and no `threading.Event`: Python retries an interrupted socket read after a handler returns (PEP 475), so a handler that only sets an event leaves Ctrl-C waiting for up to a whole long poll, and `signal.signal` raises outside the main thread. Ctrl-C arrives as `KeyboardInterrupt`, which `_request_once` does not catch because it catches `Exception`; `main` catches it, prints the last accumulated line, and returns 0, and `poll --once` catches it too, prints the zero counts line and returns 0. A test uses a fake that raises `KeyboardInterrupt` after one batch. `--long-poll` defaults to `None`: `poll --once` uses 0 when it is not given, `poll` uses 50. `--long-poll N` must be an int from 0 to 50; out of range is an argparse error with exit 2, matching argparse behaviour in `framework/collectors/__main__.py`. Every print of a counts line or a sent line uses `flush=True`. `send-sample` sends `SAMPLE_CARD` with `SAMPLE_CHART` through `send_card`. Tests cover the CLI on an HTTP error, a timeout and malformed JSON with `capsys` and `caplog`, asserting exit 1, the `error:` line shape, and no token anywhere in captured output. The CLI reads no token itself; the client does (D17), so the CLI has nothing to leak.

**D21. Leak test shape.** For an HTTP error, a timeout at `urlopen`, a timeout during `read()` and malformed JSON whose body echoes the full URL: the fake asserts the token was in the requested URL, so the test cannot pass by never getting there. Then it asserts the token is absent from `str`, `repr`, `args` and `vars` of the exception, from every exception reachable through `__cause__` and `__context__`, from `"".join(traceback.format_exception(exc))`, from `traceback.TracebackException.from_exception(exc, capture_locals=True).format()`, from `caplog` at DEBUG, from `capsys`, and from every byte of every table in the scratch database. The same for a token with a trailing newline, a token with an inner space, and a malformed chat id, each asserting the value is absent under `capture_locals`. The synthetic token is shaped so gitleaks' Telegram rule (`\d{5,16}:A[A-Za-z0-9_-]{34}`) cannot match, for example `1:synthetic-token-marker`, or `make check` fails at commit time. The newline variant is `1:synthetic-token-marker\n` set in the context; D17 strips it, the stripped form passes the shape check, and the leak assertions run on the stripped form and also assert the raw newline form's repr is absent, because a token read from a file with a trailing newline is the realistic accident. Every table in the scratch database means: list tables from `sqlite_master`, select every column of every row, encode to bytes, and assert the token bytes are absent. That covers `events`, `cursors`, `telegram_cards` and `telegram_voice_arrivals` without naming them, so a future table inherits the check.

**D22. Chart.** `render_chart_png(data: ChartData) -> bytes` is pure. `ChartData`: `period_labels` (three strings), `screen` (tuple of `ChartSeries`, 0 to 8), `pushes` (one `ChartSeries`), `tally` (tuple of `TallyItem(label, count)`, at most 4 items). `ChartSeries`: `label`, `earlier`, `prior`, `last`. Values are finite, non-negative, and at most 1,000,000. Labels are short (cap pinned below), single-line, and reject anything URL-shaped; that is how "no titles, no URLs" is enforced by type. `chart.py` checks `isinstance(font, ImageFont.FreeTypeFont)` and raises `RuntimeError` otherwise, because `ImageFont.load_default(size=...)` returns a tiny bitmap font with no error when FreeType is missing and the chart would be unreadable with nothing saying so. Form, because minutes and pushes do not share a scale:

- Two panels with independent scales, never two scales on one plot. Screen: one row per category, three thin horizontal bars from one baseline on one shared scale. Pushes: the same marks on its own scale.
- Periods are ordered, so they take a one-hue ramp, light to dark: `#86b6ef`, `#2a78d6`, `#104281` on surface `#fcfcfb`. I ran this ramp through a palette validator in ordinal mode and every check passed.
- Text uses ink `#0b0b0b` or `#52514e`, never a bar colour. A legend row of swatch plus period label is always present.
- No axes, ticks, gridlines, title, date or units unless passed in a label. The value sits at the tip of the last bar only. A zero draws no bar.
- The tally is text of label and count, because a few counts are not a chart. Tally items wrap to further rows by measured width, at most 4 items. Separators are spacing, not glyphs, because a drawn `·` would not be a passed-in label.
- Nothing clips. The label column and the value column take their widths from measuring the actual strings of this render, so layout stays deterministic for one input. A non-zero bar is at least 4 px wide, so a small value stays visible.
- All-zero input must not divide by zero. Empty screen drops its panel. Under 1280 px on the long side, since Telegram downsizes larger photos; text at least 30 px at about 1080 px wide so it reads on a phone after Telegram's JPEG recompression. Bars 24 to 32 px with a rounded data end.

Every string reaches the image through one text-draw seam. The label test intercepts at the library's own text call, so a bypass of the seam cannot hide. It asserts both directions: every passed-in label is drawn, and nothing else is drawn except the formatted last values and tally counts. The label test also records each drawn string's position and asserts, on a worst-case input (8 screen series, 18-character labels of wide letters, large values, 4 tally items with long labels), that every string's bounding box lies inside the canvas, no two overlap, and the long side stays under 1280 px. Other tests: PNG signature; render twice gives equal bytes; a chunk walk finds no `tEXt`, `iTXt`, `zTXt` or `tIME`; input with odd labels draws those labels and no default ones; the FreeType check raises `RuntimeError` on a non-FreeType font.

Pinned chart numbers, my choices where the brief leaves them open: canvas width 1080 px. Label cap is 18 characters per label, counted in characters, single-line, and URL-shaped means the label contains `://`, or starts with `www.`, or matches `^[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)+(/|$)`; any of those is a `ValueError` at construction. Period labels follow the same rule. `TallyItem.count` is an int at or above 0. Values are floats, checked finite with `math.isfinite`, at or above 0 and at most 1,000,000. Bar height 28 px, gap 6 px inside a series, series block gap 18 px, panel gap 28 px, outer margin 36 px, legend swatch 22 px square, font size 32 via `ImageFont.load_default(size=32)`. The label column and the value column take their widths from measuring the actual strings of this render. The last value formats as an integer when it is whole (`42`), else with one decimal (`42.5`); that formatted string and the tally counts are the only drawn strings besides labels. Height is computed from the content: legend row, then the screen panel when present, then the pushes panel, then the tally rows; every other layout number is a module constant so two renders of one input cannot drift. The scale of a panel is its own maximum across all three periods and all its series; bar length is `round(value / panel_max * bar_area_width)` when `panel_max > 0`, else 0, and a non-zero bar is at least 4 px wide. The data end is rounded with a radius of half the bar height drawn as a filled ellipse segment or `rounded_rectangle` on the bar's right end only; the baseline end stays square. Image mode is `RGB`, saved as PNG with no metadata arguments.

### Card text layout (D2, D7)

`render_card_text(card)` produces exactly this shape, with no trailing newline. A side of kind `"proposal"` prints as the line below. A side of kind `"fallback"` prints the same line plus the fixed suffix ` (no checked facts)`. Reason codes do not print on the card.

```text
<HH:MM>  <since_line>

A  <profile> · <title>, <HH:MM>-<HH:MM>
B  <profile> · <title>, <HH:MM>-<HH:MM>
```

Pinned precisely: line 1 is the slot time in Europe/Madrid as `%H:%M`, two spaces, then `since_line`, unchanged, when the card has a side of kind `"proposal"`. `since_line` is the whole line as passed in, for example `Since 15:30: build time up, family call not logged.` Line 1 of a fallback-only card is the slot time, two spaces, then the fixed sentence `No checked facts this time.` Then one blank line. Then one line per proposal in letter order: the letter, two spaces, `profile`, one space, `·`, one space, `title`, a comma, one space, `HH:MM-HH:MM` for start and end in Europe/Madrid, plus ` (no checked facts)` on a side of kind `"fallback"`. With one proposal, only its line appears. The proposal lines carry no button text; the buttons are the keyboard (D7). Buttons follow the sides as D7 pins: only the buttons for sides that are on the card, then the three-button row.

The four pinned expectations below are compared byte for byte. Each uses a slot at 18:00 Madrid, proposal A profile `Builder` title `Write-up draft` 18:00-18:25, and proposal B profile `Disconnect` title `Family call` 18:00-18:25.

Mixed card:

```text
18:00  Since 15:30: build time up, family call not logged.

A  Builder · Write-up draft, 18:00-18:25
B  Disconnect · Family call, 18:00-18:25 (no checked facts)
```

Fallback-only card, two sides:

```text
18:00  No checked facts this time.

A  Builder · Write-up draft, 18:00-18:25 (no checked facts)
B  Disconnect · Family call, 18:00-18:25 (no checked facts)
```

One side alone, kind `"proposal"`, letter B:

```text
18:00  Since 15:30: build time up, family call not logged.

B  Disconnect · Family call, 18:00-18:25

One side alone, kind `"fallback"`, letter A:

18:00  No checked facts this time.

A  Builder · Write-up draft, 18:00-18:25 (no checked facts)
```

The exact-text tests compare against these bytes, with the middle dot as the single character `·` and the two spaces after the slot time and after each letter. The caption check in D2 runs on this text, so a card with a long `since_line` fails at construction, never at send time.

### The faithful fake (test support)

Tests never touch the network. Unit tests monkeypatch `urllib.request.urlopen`. The fake lives at `tests/telegram_fake.py`, so both test modules import it as `from telegram_fake import FakeTelegram` (pytest puts the test file's directory on `sys.path`; `pyproject.toml:29-31` sets `testpaths = ["tests"]`). It is not a test file itself (no `test_` prefix), so pytest does not collect it. No new config is needed and none is added. `tests/telegram_fake.py` also holds a `no_sockets` autouse fixture, imported by each telegram test module, that makes `socket.socket.connect` and `socket.socket.bind` raise.

`FakeTelegram` is a callable class with the `urlopen(request, timeout=...)` shape. It records every request as `(method_name, url_path_tail, headers, body_bytes, timeout)`, asserts the token path segment equals the configured synthetic token, and routes on the last path segment. It enforces what the real API enforces, so a test fails when the code sends something Telegram would refuse:

- Known method names only: `getUpdates`, `sendPhoto`, `sendMessage`, `editMessageReplyMarkup`, `answerCallbackQuery`. Anything else gets a 404 body `{"ok": false, "error_code": 404, "description": "Not Found"}`.
- The token path: the URL must be `<api_base>/bot<token>/<method>`; a wrong token gets 401.
- `callback_data` at most 64 bytes in any `reply_markup`, checked on the parsed JSON; over the limit gets 400.
- Caption at most 1024 UTF-16 units (the fake counts the same way the code does); text 1 to 4096 UTF-16 units; violations get 400.
- `reply_markup` must be valid JSON when present; `sendPhoto` bodies are parsed as multipart with the standard `email` parser (`email.message_from_bytes` with a synthesised `Content-Type` header), and the PNG signature is checked on the received photo bytes.
- Updates carry int chat ids and int user ids, always; the fake refuses to build an update with a string id, so a test cannot pass by comparing strings.
- `getUpdates` honours `offset` as confirmation: it serves only updates with `update_id >= offset` and drops confirmed ones from its queue.
- `editMessageReplyMarkup` answers 400 with description `Bad Request: message is not modified: specified new message content and reply markup are exactly the same as a current content and reply markup of the message` when the markup equals the stored markup for that message.
- `answerCallbackQuery` answers 400 with description `Bad Request: query is too old and response timeout expired or query ID is invalid` for a query id the fake has marked expired.
- `getUpdates` answers 409 with description `Conflict: terminated by other getUpdates request; make sure that only one bot instance is running`.
- Scripted failures: the test queues a script of outcomes per method (`429` with description `Too Many Requests: retry after 7` and parameters `{"retry_after": 7}`, `409`, `401`, `5xx`, a `urlopen` timeout, a `read()` timeout, a malformed body, a body echoing the full request URL). The fake uses Telegram's full descriptions verbatim. The fake asserts, in the echo case, that the token really was in the requested URL (D21).
- `sendPhoto` returns a message dict with an incrementing `message_id` and records the stored markup for the not-modified check.

The fake binds no socket and opens no connection. A test that imports it and a test that patches `urlopen` with it are both offline by construction. The fake itself is synthetic: its chat id, user id, token and card values are invented constants at the top of the file, shaped so gitleaks cannot match them (D21).

### Known gaps, stated plainly

- An ambiguous timeout on a send can duplicate a card. If `sendPhoto` times out after Telegram accepted it, `send_card` retries under D18 and I can get the same card twice, with two message ids and one card id. The ledger holds one card, both messages rule on it, and the first ruling stands (D6). I accept this; there is no client-side key Telegram would dedupe on.
- If no update arrives for a week, Telegram may pick the next `update_id` at random; if it is below my stored offset, `getUpdates` returns nothing until I reset the cursor by hand. The experiment has updates every day, so I accept this. The cursor is one JSON value I can inspect and reset by hand, and the plan keeps it human-readable for that reason.
- A real phone may truncate `Something's wrong` in a three-button row. The label is pinned by the brief. If it truncates on my phone, the fix is a shorter label, which is a plan amendment because tests assert the exact label.
- The live Bot API is not exercised in this ticket's tests. Every test runs against the fake. The live test is run outside the Muse session by the reviewer, and its result goes in the session note at commit time.
- A repeated Why? reply on a re-delivered update sends the statements again (D10). I accept the duplicate message rather than add reply dedupe state that could swallow a real second ask.
- A `callback_query` carries no date, so an event's time is when my poller handled the tap, not when my thumb hit the button. While the poller is down, taps wait at Telegram, keep their order, and take the restart's time. Telegram keeps an unconfirmed update for at most 24 hours, so a tap older than that is gone. Whoever learns from the time must read it as "handled at".
- A voice handler that raises is counted and the cursor advances, so that note is not delivered again. Ticket 14's handler must persist first or retry on its own.
- The counts line gives no cause for a poll error. `poll --once` prints the message when a failure persists, and DEBUG logging names the method and status or the exception class. I don't record a transient failure's cause anywhere else.

## Risks

- **The token rule is the easiest thing to break quietly.** One f-string in a new error path, one logged exception, one stored body, and the token is in a traceback or a table. The D17 shape (one function, raise after return, scrub the body) plus AT4 is the defence. The residual risk is a future edit adding a second request path; the mutant K3 and the fake's request-count assertions make a bypass loud, and Ticket 14's `getFile` work must go through the same function or AT4 stops covering the real surface.
- **A double tap is a conflict in the store's terms, and that is easy to get wrong.** With an advancing clock the second append raises (D5). If a future change routes taps through `poll_transaction`, every double tap writes a `conflicts` row and AT6 catches it. The double-tap test asserts `now_fn` returned two distinct instants and that the stored event's time is the first one; K4 deletes the `except ConflictingEvent` handler and the test must fail with it.
- **The 16-hex card id can collide in principle.** Two different cards with the same id would share a ledger row, and the second card's taps would rule on the first card's proposals. At one person's card volume this is not a practical event, and the ledger's no-overwrite rule means the failure is visible (a load returns the wrong card) rather than silent data loss. Widening the id is a one-line change to D3 plus a callback-length recheck, if I ever want it.
- **Telegram may change what a photo message does to the chart.** The size and font floors in D22 are picked for today's recompression. If the chart reads badly on the phone, the fix is layout constants in `chart.py`, not a new library.
- **The first live run will probably fail with 403 until I press Start in the chat.** That is why the description stays in error messages (D17). The live test is run outside the Muse session by the reviewer, and its result goes in the session note at commit time, so a green fake never gets reported as a green live run.
- **Polling and a webhook cannot coexist.** If a webhook is ever set on the bot, `getUpdates` answers 409 forever and the loop backs off and counts without storing anything. AT14 covers the count and the backoff; clearing a webhook is an operational act I do by hand, not code in this ticket.
- **The ledger grows one row per card, forever.** That is the point (D9), and at five cards a day it is a non-issue for years. No pruning is built; a prune would need a rule about which cards the learner still needs.

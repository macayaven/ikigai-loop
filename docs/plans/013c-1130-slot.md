## Risks

- **A live slot today, or on Nov 3 or Nov 4, runs late or different.** The failure shape I most fear is a change that quietly widens something daily: 11:30 added to `SLOT_TIMES` (pins it every day, grows the registered run past 13), 11:30 added to `_BUILDER_ONLY_TIMES` (strips Disconnect from forced 11:30 runs on Nov 2 and Nov 4), or `SLOT_LIMITS.allowed_start` widened to 11:30 (lets the gate accept any day's morning slot). Each is a one-line change and each breaks a registered rule. D1, D2 and D4 forbid all three, and T2, T7 and T9 exist to fail loudly if an implementer reaches for one anyway.
- **The five daily slots on Nov 3 itself.** Nov 3 is the day with most to lose: it holds five registered cards. The dated check is instant equality against one constant, so 13:30, 15:30, 18:00, 20:30 and 22:30 on Nov 3 cannot match it — their instants differ — and T9 asserts their limits are the identical `SLOT_LIMITS` object on Nov 3 as on other days. The one real interaction is D11: a delivered 11:30 card becomes the 13:30 card's Builder parent. I accept that; a reviewer who does not should say so before implementation, because removing it is a different, bigger ticket.
- **Reliability of the new slot itself.** The 11:30 facts run cuts its facts at 11:05 and must finish by 11:26. If my machine is busy with the morning, this card degrades to code facts or a fallback like any slot whose model misses its deadline; it does not wait, and it never delays the 13:30 slot, whose own deadlines are computed from its own slot instant. `check-slot` on an unarmed 11:30 timer reports `NO_RUN` (D12), so a forgotten timer alerts rather than passing silently.
- **The Glimmer proof and the model slot.** Without D7, a `make glimmer-proof` run at 11:10 on Nov 3 would contend for the one Glimmer slot against the 11:30 card's facts. With D7 the proof refuses in that window. The mirror risk is over-refusal: the dated candidate is added only when the nearby day is 2026-11-03, and T6 pins Nov 2 and Nov 4 at the same clock time as free, so the proof keeps working on the days around it.
- **Voice corrections.** A correction is the one path that re-proposes at an old slot with its own limits. If D8 were missed, a correction to the 11:30 card would fail as outside the allowed hours and I would read that as the voice path being broken. If D8 were done by widening the deps default instead, every slot's correction window would move. The conditional in D8 avoids both, and T11 pins the injection seam so a test-injected limits value still reaches the propose call for ordinary slots.
- **Tests that cannot fail.** Three traps I checked for. An equality test on limits (`==`) cannot catch an implementer who builds a fresh copy of `SLOT_LIMITS` per slot, so T9 asserts identity (`is`). An exit-0 assertion on the end-to-end run cannot catch a noop, because `run_slot` exits 0 for explained noops, so T12 asserts the sent card and its hour. A `run_slots` test that only counts cannot catch the dated slot sneaking in while another drops out, so T7 also asserts the dated instant is absent and AT3 keeps the existing first-and-last-instant assertions green. The pinning tests T2, T3, T7 and T11 pass on main by design; I named them pinning so nobody counts them as evidence the feature works — T1, T4, T5, T6, T8, T9, T10 and T12 carry that weight, and AT11 proves they fail before the change.
- **The Deviations entry lands late.** If the implementation slips past 11:30 on Nov 3, entry 17 would be written after the card it describes, which breaks the rule that deviations precede what they describe. Step 5 puts the docs before the code runs anywhere near a card, and A3 covers a same-morning landing honestly. If Nov 3 11:30 passes with no implementation, this ticket is void, not late: the constant names a past instant and classifies nothing in the future.
- **Another ticket lands its bookkeeping first.** Another ticket being built right now also adds a Deviations entry and a `CONTRIBUTIONS.md` entry. Whichever lands second takes the next number and moves its entry after the other, in a docs-only rebase, and no entry's text changes.

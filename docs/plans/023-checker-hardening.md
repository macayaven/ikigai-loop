## Approach

### Key decisions (binding on the implementer; each with its reason)

- **D1, one new module, outside the closure, with its own report type.** New file `framework/verify/hardened.py` holds the new checker: input models, loader, `check_claims`, `CheckReport`, `ClaimCoverage`, `HARDENED_LIMITS_NOTE`, `format_check_report` and `page_render_hardened`. Reason: one module keeps the browser bundle small and the one-session cut line honest, and nothing in the closure imports it, so the freeze holds by construction. Detail, all binding:
  - `framework/verify/__init__.py` is in the closure and does not change, so the new names are imported from `framework.verify.hardened` directly, never re-exported from the package. `framework/verify/__main__.py`, `framework/verify/page_bundle.py`, [docs/verify/verify_page.py](../../docs/verify/verify_page.py) and [docs/verify/index.html](../../docs/verify/index.html) are outside the closure and switch to `check_claims` / `page_render_hardened`.
  - The new module imports only public names: from `framework.verify.core` the public `verify_claims`, `load_input` helpers' constants (`MAX_CLAIM_TEXT_CHARS`, `MAX_TOTAL_CLAIM_TEXT_CHARS`, `MAX_INPUT_BYTES`, `MAX_CLAIMS`, `MAX_REFS_PER_CLAIM`, `MAX_TERMS`, `MAX_LABEL_WORDS`, `MAX_SERIES_IDS`, `MAX_JSON_DEPTH`, `MAX_WORD_CHARS`, `MAX_CLAIM_ID_CHARS`, `MAX_LABEL_CHECKS`), `VerifyInputError`, `Violation` and `Report`; from `framework.briefing.gate` the public `collapse_text`, `contains_token`, `ref_backs_token`, `text_check_codes`, `word_list_hit`, `direction_sides`; from `framework.briefing.normalize` the public `normalize_text`; from `framework.briefing.numbers` the public `extract_number_tokens`, `token_backed_by` and `find_known_names`; from `framework.briefing.quantities` the public `find_unverifiable_quantities` (which routes its time arm through `time_scope_hit` with the caller's exempt words, D5) and the public `time_scope_hit` itself (for the D6 recomputation); from `framework.briefing.claim_text` the public `has_negator`, `counted_periods`, `UP_WORDS`, `DOWN_WORDS`, `SAME_WORDS`. No underscore name from `framework/briefing` is imported anywhere in the new module, because pyright runs strict on `framework/` and a private name is not a public contract. Test files, which sit outside `framework/`, may import `metric_label_binding` and `metric_unit_class` from `framework.briefing.labels` to build translator inputs, as the parity test already does.
  - Base verdicts come from calling the old `verify_claims` on the same input with `units` and `periods` removed (D2), so everything the old checker reports, the new one still reports, with the same codes, by construction rather than by a second copy of those rules. The one exception is the D6 time-arm recomputation, the only base finding the new checker ever removes, and only when `periods` are declared. The new arms (D3 to D7) add violations on top; the merged list keeps old-checker order first, then new arms in D8 order, de-duplicated per `(code, claim_id)` keeping first-seen order, the same rule the old report uses.
  - `CheckReport` is the new module's own frozen dataclass: `violations: tuple[Violation, ...]` (the core `Violation` type, reused because it is public and frozen in the closure), `limits: str` (the D10 note), `coverage: tuple[ClaimCoverage, ...]` in input claim order, and a `complete: bool` that is true exactly when no claim has a skipped check. `passed` is a property true exactly when `violations` is empty, matching the old report. `ClaimCoverage` is a frozen dataclass `(claim_id: str, ran: tuple[str, ...], skipped: tuple[SkippedCheck, ...])`; `SkippedCheck` is a frozen dataclass `(check: str, reason: str)` with reason from the fixed D9 strings only. `feedback()` returns one `CODE claim_id: message` line per violation, so the repair loop's protocol still holds for callers who pass the new report to it by hand; `verify_and_repair` itself is untouched and still wraps the old checker, and the docs say so (D10).
- **D2, input gains `units` and `periods` as two flat optional maps beside `labels`.** Reason: my stated preference, and flat maps keyed by metric id are the shape `labels` already teaches, so a stranger needs no new idea to supply them. Detail, all binding:
  - Shape: `units: dict[str, UnitName] | None = None` and `periods: dict[str, str] | None = None` on the new input model only. `UnitName` is the closed D3 list. A `periods` value is the period phrase as the agent writes it, for example `October`, `November`, `last week`; matching is whole-phrase on the collapsed normalised copy, case-insensitive, through `contains_token`. `claims`, `facts`, `metrics`, `labels`, `order`, `deny_terms` and `advice_words` keep their current meaning and validation.
  - The new input model is a subclass of the old `VerifyInput` adding only the two optional maps, so the old validators are inherited rather than copied, with `extra="forbid"` at every level, so a typo still cannot switch a check off silently. Assumption: subclassing `VerifyInput` and adding two optional fields works the same under pydantic 2.10.5, because the page runs pydantic 2.10.5 under Pyodide 0.27.7 (017a D12) and the subclass uses no feature the old model does not already use. It uses no pydantic feature newer than 2.10; `Literal`, `ConfigDict`, field and model validators of the kinds `core.py` already uses are the allowed set.
  - Validation rules, each bad input (`VerifyInputError`, CLI exit 2, one safe message, never echoing input): a `units` key blank after stripping; a `units` value outside the closed list (a typo is bad input, not a silent pass, and the message names the field, never the typed value: the loader renders errors with `include_input=False, include_url=False, include_context=False` and replaces any location part that is not a schema field name or an integer with `<key>`, exactly as the old loader does); a `periods` key blank after stripping; a `periods` value blank after stripping, longer than `MAX_WORD_CHARS` (100), or holding no letter or digit; more than `MAX_TERMS` (1,000) entries in either new map. An entry whose metric id nobody cites is ignored, as with `labels`; a cited id with no entry is not bad input, it is a coverage gap (D9). Two cited metrics in one comparison whose declared period phrases collapse to the same phrase are not bad input; the value-period check cannot tell them apart, so it is skipped for that claim with the D9 reason (D7).
  - One parser: `load_check_input(raw: str | bytes)` in the new module, used by `check_claims` for text input, by the CLI and by the page. It reuses the old loader's guards by construction: UTF-8 with BOM accepted, `MAX_INPUT_BYTES` read cap, `MAX_JSON_DEPTH` depth check before `json.loads`, duplicate keys rejected, `NaN`/`Infinity`/`-Infinity` rejected, `1e999` and oversized integers rejected through the same strict-number and finite checks, `RecursionError` and `ValueError` re-raised as `VerifyInputError`. The old `load_input` cannot be called on the new shape (it forbids the new keys), so the new loader carries the same guard code in the new module; the hostile-input table in the Test Plan runs against both loaders and pins that they agree on every row that the old shape can say. Messages name the problem class or the cap, never input bytes, claim text, terms, values or metric ids.
  - After validation, the new checker builds the base call's input from a dump of the validated model that leaves out the two new fields (`model_dump(exclude={"units", "periods"})`, validated as the old `VerifyInput`) and calls `verify_claims` on it for the base verdict (D1). Caps therefore apply once, in the new loader, with the old checker's own caps re-checked by its validation of the stripped input; no cap is widened.
- **D3, units: a closed list of six names, with the gate's conflict rules re-expressed over the declared unit.** The closed list is `count`, `hours`, `minutes`, `seconds`, `days`, `percent`. Reason for the six: `count` and `hours` mirror the gate's two unit classes (010b D11), and `minutes`, `seconds`, `days` and `percent` are units a stranger's metrics plainly come in, so leaving them out would make the common case a coverage gap instead of a check; a closed list keeps a typo as bad input (D2). Word families, pinned in the new module as constants: hours family `hour, hours, hr, hrs`; minutes family `minute, minutes, min, mins`; seconds family `second, seconds, sec, secs`; days family `day, days` only; the coarser calendar words `week, weeks, month, months, year, years` are their own family, which agrees with no declared unit. The gate groups those calendar words with `day`/`days` for its mismatches on `hours` and `count` metrics, and that grouping stays that way in the gate; it does not carry over to a declared `days` metric, where `3 weeks` against a value of 3 days is a false number. Percent forms are a `%` sign on the number token, or `percent`, `pct`, or `per cent` straight after the number. Magnitude words straight after a number are pinned as `thousand, million, billion, trillion` and the glued letters `k`, `m`, `bn` when glued to the number; that small list re-expresses the gate's magnitude arm (010b D11, D32) without importing its private constant. Conflict rules, per claim, over the units declared for its cited metrics (a claim citing metrics with two different declared units is checked against each cited unit and fires once if any cited unit conflicts; the mixed-unit case is also named as a disclosed limit, D13):
  - Declared `hours`: a minutes- or seconds-family word anywhere in the claim is `L1B_UNIT_MISMATCH`; a days- or calendar-family word straight after a number token is a mismatch; a percent form or a magnitude word straight after a number is a mismatch; a glued form whose family is not hours is a mismatch. Each glued form maps to its family: `h`, `hr` and `hrs` are hours; `m`, `min` and `mins` are minutes; `s`, `sec` and `secs` are seconds. An agreeing glued form (`1.75h` on hours, `90m` on minutes, `90s` on seconds) passes; a conflicting one (`105m`, `90s` on hours) is a mismatch. Hours-family words agree.
  - Declared `count`: any time-family word (hours, minutes, seconds, days or calendar family) straight after a number token is a mismatch; a percent form or a magnitude word straight after a number is a mismatch; a glued time form is a mismatch.
  - Declared `minutes`: a seconds-family word anywhere in the claim is a mismatch (the same finer-unit-anywhere arm as hours, one step down); an hours-, days- or calendar-family word straight after a number, a percent form, a magnitude word, or a glued form of another family is a mismatch.
  - Declared `seconds`: an hours-, minutes-, days- or calendar-family word straight after a number, a percent form, a magnitude word, or a glued form of another family is a mismatch; there is no finer family, so no anywhere arm.
  - Declared `days`: a declared `days` metric agrees with `day` and `days` only. An hours-, minutes- or seconds-family word anywhere in the claim is a mismatch (a finer unit anywhere implies a different scale, as with hours); a calendar-family word (`week`, `weeks`, `month`, `months`, `year`, `years`) beside its number is a mismatch, because "3 weeks" against a value of 3 days is a false number; a percent form, a magnitude word, or a glued form of another family straight after or on a number is a mismatch.
  - Declared `percent`: percent forms agree; any time-family word (including a calendar-family word), magnitude word or glued time form straight after or on a number is a mismatch.
  - A number with no unit word after it never fires the unit rule on any declared unit, so "Deploys reached 5" on a `count` metric and "Programming was 1.75" on an `hours` metric pass the unit arm (other arms still apply). The gate's closed list of words allowed after a number (010b D32) stays out on purpose: it is tuned to my product's nouns, and a stranger's nouns would fail it for wording, not for units. That exclusion is an intentional difference and sits in the D13 list.
- **D4, negation: always on, no metadata, mirroring the gate with caller labels in place of bindings.** Reason: a negated claim states the opposite of its cited value, and the caller labels already say which words name the cited metric, so no new metadata is needed. Detail: the new module calls the public `has_negator` on the collapsed normalised copy, with the claim's fact ids and cited metric ids as `known_ids`, exactly as the gate does. The gate's stated-zero helper keys on my metric id scheme through `metric_label_binding`, so it cannot be called on a stranger's ids (it would silently do nothing); the new module re-expresses it over caller metadata, and the parity test (D12) proves the two agree on the gate's own ids:
  - Metric claim with a negator: `L1B_NEGATED_CLAIM`, except the stated zero. Stated zero: `no` or `zero` sits directly before any one label entry of the cited metric, each entry tried in the caller's order on the normalised copy (never a set join, whose order shifts under hash seeds), the `zero` inside `non-zero`, `nonzero` or `non zero` never counts (010b D40, re-expressed as a small guard in the new module), and then: if that metric's cited value is 0, no negation code fires; if it is not 0, `L1B_NUMBER_WITHOUT_METRIC_REF` fires instead (a stated zero with no zero behind it is a number without backing, as in the gate). A negator with no stated-zero shape fires `L1B_NEGATED_CLAIM` once per claim.
  - Fact-only claim (fact ids, no metric refs) with a negator plus a direction word (`UP_WORDS`, `DOWN_WORDS` or `SAME_WORDS` from `claim_text`, matched as whole tokens on the normalised copy), a same word, or a period word (`counted_periods` non-empty): `L1B_NEGATED_CLAIM`. A fact-only negator with none of those passes this arm, as in the gate.
  - Negation runs before the direction arm's reading in the new module's own order only in this sense: the old checker already ran without a negation arm, so no old verdict changes; the new arm only adds codes (D8).
- **D5, quantity forms: always on, no metadata, calling the gate's scan the way the gate calls it.** Reason: "over 1.75 hours" and "about 1.75 hours" state a quantity the cited value does not prove, and the gate already owns the word lists, so the new checker calls them rather than copying them. Detail: the new module calls the public `find_unverifiable_quantities` once per claim and maps any non-empty result to one `L1B_UNVERIFIABLE_QUANTITY` per claim. Arguments, pinned, mirroring the gate exactly: `has_metric_refs` is whether the claim cites any metric; `has_backed_fifty` is true when any number token of value 50 is backed by a cited ref under `token_backed_by`, with no percent-sign condition (the gate's `half` beside a backed 50 stays free on the same condition); `in_since_last` is always false, because the public shape has no such section (010c stays mine, D13); `cites_hours_metric` is true when any cited metric has declared unit `hours` in `units` (false when no unit is declared; the current gate function accepts and ignores this argument, and the call passes it so the call shape matches the gate's); No names are read from cited facts at all (`known_names` is empty, and the new module imports no `find_known_names`): the `find_known_names` scan is quadratic in a long run of letters and hung the 5 MB-fact command-line run. A number-like or quantity-like word inside a name that a cited fact carries is not skipped, which can only make the check stricter (limit 7 in D13). `known_ids` is the claim's fact ids plus cited metric ids; `cited_labels` and `cited_label_tokens` are where caller metadata replaces the gate's bindings: the label words of every cited metric, plus the declared period phrase of every cited metric (D6), tokenised on the normalised copy. Feeding the caller's words there is what stops a stranger's ordinary words from firing arms the gate only runs against its own bindings.
  - Time-scope arm, decided here as the ticket requires: a period phrase or label word the caller declared for a cited metric must not make a true claim fail. The new module passes the same `cited_labels` set (labels plus declared period phrases of cited metrics) as the exempt set, and `find_unverifiable_quantities` already routes its time arm through `time_scope_hit` with that exemption. On top of that, the old checker's own time-outside-the-metric arm (in the frozen core, reached through the base `verify_claims` call) keys on label words only; D6 pins the recomputation inside the new module that fixes its reading when a declared period phrase is split across label words, and a named test proves "Programming in last week was 1.75 hours" citing a metric labelled `programming`, `last` and `week` with declared period `last week` and unit `hours` passes every arm. If feeding caller phrases to the scan makes a gate case disagree, the case stays excluded with that reason (D12), it is not fixed by editing the gate.
- **D6, period binding: a cited metric with a declared period must be named by that period, and the declared phrase is exempt from the time checks.** Reason: once the caller declares which period a metric belongs to, a claim that never names that period has not tied its number to that period, and the phrase the caller declared cannot also be treated as a stray time word. Detail:
  - With `periods` given: for each cited metric with a declared period phrase, the claim text must contain that phrase (whole phrase, `contains_token` on the collapsed normalised copy) or `L1B_PERIOD_WORD_MISSING` fires once per claim. This reuses the gate's code name for the same reading; the gate emits it from its binding check, the new checker from the declared phrase. A cited metric with no declared period does not fire this arm; it is a coverage gap (D9), not a pass and not a violation.
  - A period the claim names but does not cite: a claim that names the declared period phrase of an uncited metric sitting in the same declared `order` series as a cited metric fires `L1B_PERIOD_WORD_MISSING` once per claim, because the gate requires the period words a claim names to match the periods it cites. Without this arm, "Deploys were 9 in November, the same as October" citing only November passes while it states something about October that nothing backs. Outside a declared series this arm does not run: with no `order` series joining the uncited metric to a cited one, naming its declared phrase fires nothing here.
  - Relation to labels, decided here: `periods` phrases and `labels` words are separate. Labels still govern `L1B_METRIC_LABEL_MISSING` exactly as the old checker runs them (every listed word must appear). A declared period phrase is not added to the label word list, so declaring `periods: {"m1": "October"}` never makes "October" a label word, and a label word never satisfies the period arm. Both must be named when both are declared, because they say different things: which metric, and which period of it.
  - Relation to the existing time-outside-the-metric check (`time_scope_hit`, reached in the frozen core through labels), decided here: the new module cannot change the frozen core's arm, so it corrects the false reading at its own layer, with no closure change. The public `time_scope_hit` in `framework/briefing/quantities.py` exempts whole phrases only, so a metric labelled `programming`, `last` and `week` still fails "Programming in last week was 1.75 hours" on `main` with the old checker's message about a time outside the cited metric, while the single label entry `last week` passes. After the base call, when the base report carries the old checker's label finding whose fixed message is `claim names a time outside the cited metric`, the new module recomputes the public `time_scope_hit` over the same normalised collapsed text, exempting the cited metrics' label words and their declared period phrases; when nothing is left, it drops that one base finding. That fixed message identifies the time arm because the old checker keeps the first label finding per claim and runs the time arm last, so a label finding carrying that message can only have come from the time arm. This is the only base finding the new checker ever removes, and only when `periods` are declared. Tests pin it: a declared period phrase with labels that leave it out (`programming`, `last`, `week` beside declared period `last week`) passes; another time phrase in the same claim still fails, because the recomputation still finds it; and the same input without `periods` keeps the old verdict, because no recomputation runs. No caller wording is required beyond declaring the period, and no closure file changes to fix this.
  - Reserved period vocabulary stays mine: the gate's `earlier`/`prior`/`last` counting (`counted_periods` phrase removals, compounds, non-period senses) is used only where D4 and D7 call `counted_periods`; the new checker never requires a stranger's claim to use my three period words. A caller declares their own phrases, including `October` or `last week`, and only those phrases are required.
- **D7, value-period binding comes last and can drop to a disclosed limit without unpicking anything else.** Reason: the gate's version is long and tuned to my phrasing, so it is the one part that must not hold the rest of the ticket hostage. Detail: this arm runs only when a claim cites two or three metrics that all sit inside the same declared `order` series (every cited metric must sit in that one series; a claim citing one series member and one metric outside every series is not eligible), each cited metric has a declared period phrase, and the declared phrases are pairwise distinct after collapsing and casefolding. The skip reasons are checked in this order: a cited metric without a declared period first, then no common series, then periods that are not distinct. Then, mirroring the gate's `L1B_VALUE_PERIOD_MISMATCH` rules (010b D21, D27, D28, D29) as far as they carry over to caller phrases:
  - Value beside period: a number token written beside a cited metric's declared period phrase must be backed by that period's cited ref under `token_backed_by` at the token's decimal places, or `L1B_VALUE_PERIOD_MISMATCH` fires once per claim. Beside means the gate's three passes re-expressed over caller phrases: value-then-period (value, optionally one label or unit word, then `in`, `during` or `for`, optionally `the`, then the period phrase), period-then-value (period phrase, then `was`, `were`, `at`, `of`, `:` or `=`, then a value), and period-comma-value; plus the clause pass (the claim split on commas, semicolons, colons and clause words, a clause holding exactly one declared period phrase and exactly one value is tested as that pair alone). A value that runs on into `and` or a comma plus another value is a positional list and is skipped in the backward and comma passes, as in the gate.
  - Stated change: a value after `by`, after `net`, or after `a change of` / `a difference of` (and the bare `change of` / `difference of` forms) must equal a difference of the cited values (every pair by position, as the gate does: ordered pairs with different positions, including equal values, so two equal cited values give a difference of 0; compared through `token_backed_by`), or `L1B_VALUE_PERIOD_MISMATCH` fires once per claim. ## Risks

- **The freeze is the hard edge.** Any import of the new module from a closure file, or a helpful edit inside `core.py`, changes the closure hash and breaks the pin my live run rests on. AT4 before and after, plus the closure test, are the guard; the D6 recomputation works around the frozen core's whole-phrase exemption inside the new module, so the freeze costs no caller wording there.
- **Caller phrases are not my phrases.** The gate's arms were tuned against my period words and labels; a stranger's `last week` or `October` can sit next to a time-scope or quantity word in a way my cases never showed. D5 and D6 feed the caller's declared words into the scan exemptions for exactly this reason, the D6 test pins the known shape, and any further shape that disagrees stays a named parity exclusion, not a silent pass.
- **Quantity forms may over-fire on plain prose.** The new checker reads no names from cited facts (D5, limit 7 in D13), so a number-like or quantity-like word inside a name a stranger's fact carries is not skipped; what remains is the gate's own reading of the claim itself, which I keep, and the check can only be stricter for it.
- **Parity counts move.** Reclassification (D12) will move the pinned counts in the new sibling file and rewrite some exclusion reasons; a reviewer reading only the diff could mistake that for drift. The sibling test keeps base, round and ticket counts stated separately from the old file's, and the session note reports before and after.
- **Coverage can be misread as a pass.** `passed` true with `complete` false keeps exit 0 (D9); a caller who reads only the exit code will miss the gaps. The first line, the JSON flag and the docs sentence all carry the gap, and changing the exit code would break the existing contract; I accept the reading risk and state it.
- **Value-period binding is the long tail.** The gate's version grew over several review rounds against my phrasing. D7 carries over only the passes a caller phrase can support, runs last, and can drop to a disclosed limit whole; the risk is spending the session there, which the cut line exists to prevent.
- **The page runs an older pydantic than the CLI.** Pyodide 0.27.7 carries pydantic 2.10.5; the repo lock carries newer. D2 restricts the new models to features `core.py` already proves under that version, and AT7 is the only leg that can catch a browser-only validation difference.
- **Mixed-unit claims.** A claim citing an hours metric and a count metric can fire on a unit word that agrees with one of them (D13, limit 4). The sentence does not say which metric the word belongs to, so no reading is clearly right; firing is the fail-closed choice and it is named as a limit.

## Success Criteria

- **Whole-hour cuts.** Every event-time bound (window, three periods, snapshot totals, prompt rows, evidence) ends at `floor_hour(as_of)`. A screen hour bucket always falls wholly in one period. Nothing is prorated. A whole-hour `as_of` behaves byte-identically to today.
- **No false zero from the open hour.** Activity in `[floor_hour(as_of), as_of)` counts in no period and no total, and no kept fact and no snapshot key — code or model — says `0` in `last` for a family that has activity in that open hour.
- **Reconcile first, select second.** Calendar winners are chosen over every revision collected by `as_of`, per calendar, before any window selection. A one-off block moved in one poll is not counted as cancelled. Selection is by interval overlap, clipped. One rule in loading, validation, and metrics.
- **Clock time, not row time.** Busy hours and per-tag hours are unions of clipped intervals. Two overlapping appointments in one clock hour give one busy hour.
- **Collector lifecycle is content-and-stamp-driven.** `STATUS:CANCELLED` cancels; a restored event wins again; a silent content change and a stamp-only change each emit; an unchanged poll emits nothing — including the first poll after deploy on today's exact cursor shape. A feed holding zero VEVENTs cancels nothing.
- **Numbers bind to their named period.** A backed number, zero above all, is backed by the period the statement names for it. A statement naming no period keeps today's behaviour.
- **GitHub bursts survive.** The collector follows pages to the last one (at most 3 pages, 300 events) and advances the ETag only after every page succeeded.
- **No migration.** The real store and real cursors keep working as they are. Stored rows already carry their calendar in `source`.

### Key decisions (binding on the implementer)

#### D1 — Floor every event-time bound to the whole hour; the raw `as_of` still identifies the cycle (item 1)

New helper in `framework/glimmer/metrics.py`, next to `fixed_offset` at [framework/glimmer/metrics.py:16](../../framework/glimmer/metrics.py:16):

```python
def floor_hour(as_of: datetime) -> datetime:
    pinned = fixed_offset(as_of)
    return (
        pinned.astimezone(UTC)
        .replace(minute=0, second=0, microsecond=0)
        .astimezone(pinned.tzinfo)
    )


def window_bounds(as_of: datetime) -> tuple[datetime, datetime]:
    end = floor_hour(as_of)
    return (end - WINDOW, end)  # (window_start, window_end)
```

Flooring after `fixed_offset` is the point: arithmetic stays on the pinned fixed offset, so on Madrid's fall-back day the two wall-clock 02:00 hours keep different offsets and floor to two different instants, and every period stays exactly 24 hours of absolute time. Never re-resolve through `ZoneInfo` after flooring. The floor itself is taken in UTC, not on the pinned wall clock: screen buckets are UTC hours ([framework/collectors/activitywatch.py:199](../../framework/collectors/activitywatch.py:199)), and in a zone with a half-hour offset a wall-clock `replace(minute=0, ...)` would land inside a bucket and split it. Madrid's offset is a whole number of hours, so Madrid's result is unchanged, including both fall-back hours — but the UTC form is still the right one, because it floors on the grid the buckets are stored on instead of relying on Madrid's offset lining up with it.

What floors, and what does not, pinned:

| Thing | Value after this ticket | Reason |
|---|---|---|
| `cycle_id`, `FactResult.as_of`, `cycles.as_of` | raw `as_of`, unchanged | Ticket 13 writes the raw value to its ledger and reads cycle ids back; identity must not move |
| Knowledge guard | `collected_at <= raw as_of`, unchanged ([framework/glimmer/facts.py:297](../../framework/glimmer/facts.py:297)) | A 12:00 screen row collected at 13:02 is real knowledge at 13:05 |
| `window_end` | `floor_hour(as_of)` everywhere: `FactResult.window_start`'s pair, `Fact.window.end`, stored `facts.window_end` | The stored window is the data window the fact was proven against |
| `window_start` | `window_end - 72h` (also whole-hour) | Three whole periods; the old start was whole only by accident of `as_of` |
| `period_bounds(as_of)` | floors inside, same name and signature | Ticket 13 calls it with the raw value and must get the same bounds |
| `build_period_rollup(as_of, winners)` | same signature; bounds come from the floored `period_bounds` | A caller holding unfiltered winners and the raw value gets floored periods |
| `build_metric_snapshot(as_of, winners, *, open_families=frozenset())` | same positional signature, one new keyword with a default (D2); totals count only rows inside the floored window (calendar clipped to it) | Today the totals at [framework/glimmer/metrics.py:162](../../framework/glimmer/metrics.py:162) trust the caller to have filtered; after D2 the caller deliberately passes wider winners, so the snapshot must apply the window itself |
| Prompt `WINDOW_START` / `AS_OF` lines | floored start / floored end, by passing `window_end` as the builder's `as_of` argument; [framework/glimmer/prompt.py](../../framework/glimmer/prompt.py) is not edited | Offset is identical (same fixed offset), the PERIODS block already ends at the floored bound, and a whole-hour cycle's prompt bytes — and `prompt_hash` — stay exactly as today |

Consequences, stated plainly. Activity in the open hour `[window_end, raw as_of)` — at most 59 minutes — appears in no period, no total, no prompt row, and no evidence. It is not lost: the next cycle's floor passes it and it counts then, whole. A screen bucket whose `time` is the open hour's start is excluded by the half-open window even though some of its minutes may already exist, because a stored hour cannot say which part of it happened before the cut; prorating it would invent minutes. That is the defence of the floor over splitting: any split of an hour bucket is a guess, and a guessed number is what this ticket exists to remove. Calendar and GitHub rows get the same bound for one reason: one window rule everywhere, or the same card would compare a floored screen period against an unfloored push period. A calendar block crossing `window_end` is clipped there; its remainder counts next cycle. Replay is unchanged in kind: same raw `as_of` plus same stored responses give the same floored bounds and byte-identical output; re-running an old stored cycle's `as_of` under new code gives a different `window_end`, so the replay identity at [framework/store/fact_store.py:121](../../framework/store/fact_store.py:121) records a new run instead of pretending it is the old one. Old stored rows are never rewritten.

What a card's `since` line may claim, stated for Ticket 13 (not built here): the orchestrator's own difference is computed at the raw instants, so it may say what happened *since the last card* and count a push from three minutes ago. It may not call that count `last`, or any period name, because `last` now ends at the floored hour. The two lines measure different windows and the card must not let one borrow the other's name.

#### D2 — The false zero: a `0` in `last` is unbacked while its family has open-hour activity (item 1, second half)

The floor alone would let code write "Pushes fell from 1 in prior to 0 in last" while a push from three minutes ago sits in the open hour. It has two paths and both close. The fact path runs through `check_fact`, so code facts (which pass through it at [framework/glimmer/facts.py:353](../../framework/glimmer/facts.py:353)) and model facts get the same rule. The metrics path runs through the snapshot to the gate: while `extract_facts`'s snapshot still holds `period.last.pushes: 0.0` for an open family, a later claim "Pushes fell from 1 in prior to 0 in last" with metric refs passes the gate, which reconciles the ref against that snapshot at [framework/briefing/gate.py:768](../../framework/briefing/gate.py:768), while the card's since line counts that same push. Mechanism, kept small:

- `extract_facts` computes `open_families: frozenset[str]` of period-family rests (`pushes`, `prs`, `screen_hours.<category>`, `tag_hours.<tag>`, `cancelled.<tag>` — the same rests `_cited_period_families` builds at [framework/glimmer/checks.py:116](../../framework/glimmer/checks.py:116)) with activity in `[window_end, raw as_of)` among reconciled winners (D4) with `collected_at <= raw as_of`: a push or opened-PR row by `time`; a screen bucket at the open hour with minutes > 0 for the category; a non-cancelled calendar row whose clipped overlap with the open interval is > 0 for its tags; a cancelled winner by `time` for its tags.
- `check_fact` gains one keyword, `open_families: frozenset[str] = frozenset()`, so every existing direct call keeps working. A zero token bound to period `last` (binding per D8) for a family in `open_families` fails with the new code `FACT_OPEN_HOUR_ZERO`; a code fact drops as `CODE_FACT_OPEN_HOUR_ZERO` by the existing prefix rule at [framework/glimmer/facts.py:365](../../framework/glimmer/facts.py:365). The cycle degrades to its other facts; nothing is rewritten to avoid the zero, because a rewritten comparison would still be answering a question the data cannot yet settle.
- `build_metric_snapshot(as_of, winners, *, open_families: frozenset[str] = frozenset())` omits a zero-valued `period.last.<rest>` key when `<rest>` is in `open_families`; a non-zero value stays, and `extract_facts` passes the same set it computed for `check_fact`. A ref to the omitted key then fails at [framework/briefing/gate.py:768](../../framework/briefing/gate.py:768) with `L1B_UNKNOWN_METRIC` (the arm at :768-776), which is the gate saying the snapshot cannot prove that zero — true, and the honest side. `build_period_rollup` is unchanged, and `code_facts` reads the rollup rather than the snapshot ([framework/glimmer/code_facts.py:132](../../framework/glimmer/code_facts.py:132)), so the code path is still governed by the `check_fact` arm above, not by the missing key.
- Ordering inside `check_fact` is pinned: a zero bound to `last` hits this open-hour arm *before* any "absent key backs a zero" rule (D8), because the snapshot key for an open family is now absent by design, and an absent key must not quietly back the very zero this decision exists to drop.
- A whole-hour `as_of` has an empty open interval, `open_families` is empty, its snapshot bytes do not move, and behaviour is exactly today's. A non-zero `last` value is not suppressed: "fell from 5 in prior to 2 in last" is true of the floored period as defined, and the period definition is what the sentence cites. Only the zero is special, because zero claims absence, and the open hour is exactly where absence cannot yet be claimed. A zero naming no period keeps today's behaviour (D8) and is a stated limit.

#### D3 — Busy and tag hours are unions of clipped intervals (item 3)

One interval-merge helper in `framework/glimmer/metrics.py` (the collector's `_merge_intervals` at [framework/collectors/activitywatch.py:154](../../framework/collectors/activitywatch.py:154) is the same idea, but `glimmer` does not import a collector). `calendar.busy_hours` becomes the union, clipped to the floored window, of `[start, end)` over winning non-cancelled `busy` rows. Per period, the same union clipped to that period. `tag_hours.<tag>` and `period.<name>.tag_hours.<tag>` become, per tag, the union over winning non-cancelled rows carrying that tag, clipped the same way.

Decision on same-tag overlap: two overlapping blocks with the same tag count the overlapped clock time once. Reason: tag hours answer "how many clock hours carried this tag", the same clock question as busy hours. Summing would let tag hours exceed the hours in the period and exceed busy time for the same blocks, and my real store has overlapping rows today, so the sum is live-wrong, not theoretical. Two *different* tags on overlapping blocks still count the overlap under each tag, and a row with two tags still counts under both: those are different questions, and Ticket 9c already pinned that behaviour. Non-`busy` rows still contribute tag hours and never busy hours, as today. Cancelled winners contribute to neither, as today.

#### D4 — Load wide, reconcile per calendar, combine, then select by overlap (items 2, 6, and 11)

One rule, in order, everywhere calendar rows are turned into numbers:

1. **Knowledge guard first, on collection time only.** A row enters reconciliation iff `subject_id` matches, its type is allowed, and `collected_at <= raw as_of`. Event time does not filter reconciliation. The existing guard at [framework/glimmer/facts.py:297](../../framework/glimmer/facts.py:297) therefore *stays* — what goes is the event-time clause next to it at :296. A revision collected after `as_of` still cannot win a replay, wherever it moved the block.
2. **Reconcile per calendar.** `_logical_key` for calendar rows becomes `("calendar", event.source, uid@rid)`. Winner per key as today: greatest `collected_at`, then greatest `id` ([framework/glimmer/metrics.py:64](../../framework/glimmer/metrics.py:64)). `select_winners` keeps its name and signature — Ticket 13 and the label sweep call it — and the per-calendar split lives inside it.
2a. **A moved one-off block is not a cancellation (item 11).** Still inside `select_winners`, after the per-calendar winners and before the combine, so every caller gets it and stored rows need no migration. The active sibling must be an appearance of its own key, not any active row. Within one `source`, group each `uid@rid`'s rows and order them by `(collected_at, id)`. An active row is an appearance when it is its key's first row, or the row before it for that key is cancelled. A cancelled winner is a move, and is dropped, only when the same `source` holds an appearance with the same UID (the part of `uid@rid` before the last `@`), a different `rid`, and the same `collected_at` as the cancelled row. One poll mints one `now` at [framework/collectors/calendar_ics.py:77](../../framework/collectors/calendar_ics.py:77) and stamps it as `collected_at` on all its rows, so that equality means "the same poll" — for a one-off block the key holds the start ([framework/collectors/calendar_ics.py:190](../../framework/collectors/calendar_ics.py:190)), so a move in one poll is exactly a cancelled old key beside a new key's first row under one UID. The narrower rule matters because cancelling one instance of a recurring series can bump the master VEVENT's `LAST-MODIFIED`: that instance's key goes, and every other instance of the series emits `updated` in the same poll, with the same UID and the same `collected_at`. Those `updated` rows follow active rows for their own keys, so none of them is an appearance, and the real cancellation stays. A cancellation is a real signal for me: [docs/PREREG.md:99](../PREREG.md:99) and [docs/PREREG.md:105](../PREREG.md:105) predict on "Cancelled … blocks rose", so I won't let a stamp bump swallow one. The pinned cases still hold as written: a plain move (the new key's first row is an appearance), move then stamp bump (the new key's first row is still an appearance at that poll, so a later edit does not bring the cancellation back — which is why the scan reads all the input rows, not only the winners), there and back (the old key's restored row follows its cancelled row, so it is an appearance), and move then delete (the delete's poll holds no appearance, so exactly one cancelled block counts). A dropped old key has no winner, so it counts neither as hours nor as a cancelled block. Rescheduling is ordinary, so this is live, not theoretical; its two stated limits are in Known gaps.
3. **Combine across calendars by `uid@rid`** (inside `select_winners`, calendar rows only): if any calendar's winner for the invitation is active (created/updated), every cancelled winner for it is dropped and the active winners are kept (D3's unions make identical intervals count once; differing intervals union). If every winner is cancelled, exactly one cancelled row is kept — greatest `collected_at`, then `id` — so `cancelled_blocks_by_tag` counts one cancelled block, not one per calendar. All other families are untouched.
4. **Select by overlap.** A combined winner enters the cycle iff it touches the floored window: point rows (screen, GitHub, feed) by `time` in `[window_start, window_end)`; non-cancelled calendar rows by positive clipped overlap with the window, or `start == end` with `start` in the window (an instant block contributes no hours but stays visible, as today); cancelled rows by `time` in the window, matching how the rollup counts them at [framework/glimmer/metrics.py:141](../../framework/glimmer/metrics.py:141). Open-hour detection (D2) reads the combined winners between steps 3 and 4. `check_fact`'s evidence window test at [framework/glimmer/checks.py:265](../../framework/glimmer/checks.py:265) becomes the same selection rule against the floored bounds (its `period_bounds` already floors via D1), so a block that starts before the window and overlaps it is citable for the hours it contributes. Code-fact evidence pools already select tag rows by overlap at [framework/glimmer/code_facts.py:194](../../framework/glimmer/code_facts.py:194); [framework/glimmer/code_facts.py](../../framework/glimmer/code_facts.py) needs no edit.

How far back the load goes, and why it is enough: `run_cycle` loads calendar rows and `calendar.label` rows with **no event-time bound at all**: every stored row for the subject of those types, implemented as `events_between` over sentinel bounds (`datetime.min`/`datetime.max` with UTC) so [framework/store/store.py](../../framework/store/store.py) is not edited. Then the `collected_at <= raw as_of` guard in `extract_facts` does the only filtering. This is enough by construction: a revision that should win is a stored row with `collected_at <= as_of`, and every such row is in the set, wherever it moved the block (past `as_of`, before the window, anywhere). Any finite event-time bound fails that argument: the collector only ever *stores* rows with `start` in `[collected-2d, collected+14d)`, but a revision's new start is bounded relative to its collection, not relative to this cycle's window, so no window-relative bound proves it captured the winner. The cost is loading one person's calendar history per cycle; at this store's scale that is the right trade for a proof. Non-calendar allowed types load `[window_start, raw as_of)` (the floored window plus the open hour D2 must see). Label rows follow the calendar rule for the reason above: their `time` is the target's start, so only the wide load guarantees a pre-window block finds its label; `apply_labels` in `run_cycle` runs over the wide set before `extract_facts`, as today at [framework/cycle/__init__.py:59](../../framework/cycle/__init__.py:59). The label *sweep*'s own loads ([framework/cycle/labels.py:102](../../framework/cycle/labels.py:102)) are unchanged: a stale winner there wastes at most one label call on a row no fact cycle will use; it cannot move a number.

Rows already stored: `source` has carried the calendar since the collector existed, so per-calendar reconciliation works on the real store with no migration and no backfill. If a feed's label were ever renamed, its old and new rows would reconcile as two calendars and combine by `uid@rid` — wrong in the safe direction (an invitation stays active while either copy is active). Stated as a limit.

`extract_facts` cannot invent rows a direct caller never passed. Its contract after this ticket: pass the reconciliation set (step 1), get steps 2–4 inside. `run_cycle` is the caller that guarantees the wide load; tests cover both layers.

#### D5 — Calendar collector: content or stamp decides, a per-key revision counter mints identities (items 4, 5, 9)

The snapshot at [framework/collectors/calendar_ics.py:159](../../framework/collectors/calendar_ics.py:159) gains one internal field, `cancelled: bool`, from `STATUS` (`str(component.get("STATUS", "")).upper() == "CANCELLED"`), and keeps the summary in an in-memory side value that is never written to the cursor (Ticket 9c's rule: no title on disk). The poll diff then compares **content** (`(start, end, busy, tags, is_new, cancelled)`) and the provider **stamp** between the cursor entry and the current snapshot: content differs OR stamp differs → emit; same content and same stamp → nothing. A stamp change must emit, for two checked reasons. [tests/test_calendar_ics.py:124](../../tests/test_calendar_ics.py:124) (`test_disappearance_emits_one_cancelled_and_bumped_emits_updated`) already pins that a `LAST-MODIFIED` bump alone emits `updated` today. And the title is not in the snapshot (its fields are at [framework/collectors/calendar_ics.py:220](../../framework/collectors/calendar_ics.py:220)), so a rename shows up only as a stamp change, and Ticket 9c needs a new row to label the new title. Content alone also emits, which is what fixes item 9: a silent edit under an unchanged stamp no longer gets absorbed by the cursor. Content compares as values, never as stored strings: `start` and `end` compare as instants via `datetime.fromisoformat` on both sides, since the same instant can arrive under a different offset in the feed (the cursor stores `start.isoformat()` at [framework/collectors/calendar_ics.py:224](../../framework/collectors/calendar_ics.py:224)); `tags` compare as a list after the JSON round trip. A stored value that will not parse counts as changed, emits `updated`, and never raises.

Cursor v2, per instance key `{uid}@{rid}`: today's fields (`source_id`, `start`, `end`, `busy`, `tags`, `is_new`) plus `cancelled: bool`, `rev: int`, `stamp: str`. On today's exact cursor shape every new field reads as its default (`cancelled=False`, `rev=0`, `stamp` derived from the stored `source_id` after the last `@`), UIDs containing `@` included. `source_id` in the cursor always names the last *emitted* (or carried) row for the key — never an unemitted identity — because two other lookups trust it: the label target at [framework/glimmer/labels.py:52](../../framework/glimmer/labels.py:52) and the title sink.

Identity rule. The first emission for a key keeps today's shape, `source_id = {key}@{stamp}`, no suffix, so an unchanged feed after deploy emits nothing and no stored row is re-minted. Every emission after a key's first increments the cursor's per-key `rev` and uses `source_id = {key}@{stamp}#r{rev}` — uniform, including stamp-only emissions. A stamp-keyed identity without the counter is not enough: a re-imported event can bring back an older stamp and reuse the first identity, the store treats it as a re-delivery, and that is the stuck-row bug again. The suffix carries no `@`, so `_logical_key` ([framework/glimmer/metrics.py:28](../../framework/glimmer/metrics.py:28)) and `_label_target_id` ([framework/glimmer/labels.py:47](../../framework/glimmer/labels.py:47)) strip it exactly as they do today's. A monotonic counter, not a content hash, because a hash reuses the first identity when content returns to an earlier value (A, B, A, B with one stamp must end on B; cancelled, restored, cancelled, restored must end active) and the store treats that re-delivery as a no-op with its old `collected_at`, so the wrong row would win forever. A cancellation's `source_id` is the last emitted active `source_id + "#cancelled"`, exactly as `_build_cancelled` does today at [framework/collectors/calendar_ics.py:277](../../framework/collectors/calendar_ics.py:277) (`…#r2#cancelled` strips correctly under both lookups above).

Emission rules, pinned. Type for an emission on a key already in the cursor (active or tombstoned) is `calendar.event.updated`; first sight is `created`. Metrics treat both identically; the one type change from today is a restore, which today reads `created`.

| Previous cursor entry | Current feed | Emit |
|---|---|---|
| absent | active instance | `created`, `rev=0` identity |
| absent | `STATUS:CANCELLED` instance | `cancelled` (the provider says this block was cancelled; window is only `[now-2d, now+14d)`, so this cannot flood history) |
| active, same content and same stamp | active | nothing; emitted `source_id` and sink key do not move |
| active, content differs OR stamp differs | active | `updated`, `rev+1`. The content arm is item 9: the second poll emits even with identical `LAST-MODIFIED` and `SEQUENCE`. The stamp arm carries a rename (title is not in the snapshot) as a new row Ticket 9c can label |
| active | `STATUS:CANCELLED`, or key gone | `cancelled` from the current snapshot's fields when present, else the stored fields; cursor keeps a tombstone (`cancelled=True`, last `rev`/`source_id`). Disappearance keeps today's guard: no cancellation when the stored start is before the collector window ([framework/collectors/calendar_ics.py:152](../../framework/collectors/calendar_ics.py:152)) |
| tombstone | key still gone or still `STATUS:CANCELLED` with same content | nothing |
| tombstone | still `STATUS:CANCELLED` with different content or stamp | nothing emitted; the tombstone is refreshed to the current content and stamp; no conflict and no raise |
| tombstone | active instance again (any content) | `updated`, `rev+1` — a restored event gets a fresh revision and wins by `collected_at` |

An older active revision stops contributing after an explicit cancellation by the ordinary winner rule: the cancelled row is collected later under the same per-calendar logical key. Tombstones are pruned when their stored start falls before the collector window, the same bound that already stops cancellations; an instance older than that cannot re-enter the expansion at [framework/collectors/calendar_ics.py:172](../../framework/collectors/calendar_ics.py:172), so pruning loses nothing.

The first poll after deploy on an unchanged feed still emits nothing under the stamp arm, because content and stamp both match the carried cursor entry (the stamp default is derived from the stored `source_id`).

Implementation note on one-instance overrides: a `STATUS:CANCELLED` override of one recurring instance must behave the same whether `recurring_ical_events` returns it or drops it. If returned, the table's cancelled row applies. If dropped, the key is gone and disappearance applies. Either way the outcome is one cancelled row and a tombstone, and the implementer's test pins that outcome through a real poll, not a mock of the library.

The title sink moves: `_snapshot_instance` no longer writes it. After the diff decides each current key's final (emitted or carried) `source_id`, `poll` writes `sink[event_id(self.name, final_source_id)] = summary` for active instances with a non-blank summary. That is the id of the row actually in the store, so Ticket 9c finds a title for a restored or silently-updated row. A test pins that the serialised cursor contains no summary text.

What this does *not* repair, stated plainly: a restoration that already no-op'd into the real store before deploy stays stuck behind its cancellation until that block next changes, disappears, or is explicitly cancelled. The first poll after deploy on an unchanged feed must emit nothing (pinned below), so no collector rule can both honour that and heal old rows. No migration is specified; the reviewer steps surface the counts on a copy of the real store, and any one-off repair after that is the reviewer's call, not this ticket's code. New restorations after deploy cannot get stuck, and unchanged polls never duplicate rows already stored.

Empty feed. The threshold is zero VEVENT components in the parsed calendar (`cal.walk("VEVENT")` empty), not zero instances in the expansion; the brief's rule is "a feed that parses and holds zero events", and events means VEVENTs in the body. If `cal.walk("VEVENT")` is empty and the cursor holds an active instance: emit nothing, return the previous cursor unchanged, raise nothing. Zero VEVENTs is the broken-feed signature, and the only threshold: any non-zero drop has no principled line between "feed broke" and "I deleted a lot". With any VEVENT in the body the normal diff runs, including cancellations. The expansion must not set the threshold, because feeds are sparse: a calendar with one upcoming block and a long history holds many VEVENTs and one in-window instance, and when I delete that one block the expansion is empty while the body is not. Under an expansion threshold that block would stay active forever. If I ever truly delete every VEVENT, the cancellations land when the next event appears, all at once. Stated as the price, in Known gaps.

#### D8 — Bind every backed number to the period its statement names (item 8)

Ticket 10b's period-binding check in `framework/briefing/quantities.py` has not merged and the file does not exist in this tree, so this ticket writes the smallest local check in `framework/glimmer/checks.py` and says so here, per the brief. When 10b lands later, replacing this local pairing with it is that ticket's job.

Rules. Period words are found casefolded with `(?<![\w-])(earlier|prior|last)(?![\w-])`, so a hyphenated tag like `iki-last` is not a period word (the `\b` form used at [framework/glimmer/code_facts.py:36](../../framework/glimmer/code_facts.py:36) would match it; that duplicate-matcher is out of this ticket's scope and unchanged). Period words are found on the statement after `_mask_cited_repos` ([framework/glimmer/checks.py:213](../../framework/glimmer/checks.py:213)), the same text the number tokens come from, so a period word inside a cited repo name is not a mention. Mentions and number tokens share offsets because both masking steps preserve length ([framework/briefing/numbers.py:132](../../framework/briefing/numbers.py:132), [framework/glimmer/checks.py:213](../../framework/glimmer/checks.py:213)). Pairing, in order: **when a statement has as many number tokens as period mentions, pair them by order — the i-th token with the i-th mention.** Otherwise each token pairs to: (a) the first period word after it and before the next token; else (b) the last period word before it and after the previous token; else (c) the statement's only named period, if exactly one is named; else unbound. The by-order rule comes first because (a)–(c) alone have a hole both ways: with truth prior=1 and last=2, "In prior pushes were 2, in last 2" would pair both tokens to `last` and pass falsely, while the true "In prior pushes were 1, in last 2" would pair the 1 to `last` and drop. By order, both pair as written. The fallback still pairs both phrasings the model and the templates use: "fell from 3 in prior to 1 in last" and "In prior, 3 pushes…".

A paired token is backed only by `period.<paired>.*` keys — under the existing family and cited-row rules at [framework/glimmer/checks.py:149](../../framework/glimmer/checks.py:149), restricted to that period. A paired *zero* is backed only when that period's key for a cited family is absent or `0.0` (and, for `last`, only when D2 also passes — D2's open-hour arm runs before this absent-key rule, since D2 now makes that key absent on purpose). Non-period totals (`github.push.count`, `screen_hours.<category>`, `tag_hours.<tag>`, `calendar.busy_hours`) never back a paired token: a statement that names a period for a number must be right about that period, not about the 72 hours. An unbound token in a statement that names periods is backed only within the named set. A statement naming no period keeps today's behaviour exactly, `_zero_token_backed` included. The all-feed cited-count arm at [framework/glimmer/checks.py:284](../../framework/glimmer/checks.py:284) still runs first, so a feed topic containing a period word cannot trip this check on its count.

This binds a swap: with prior 6.75 and last 2.0, "fell from 2 in prior to 6.75 in last" pairs 2 to `prior`, whose value is 6.75, and drops `FACT_NUMBER_UNBACKED`. And the false zero: "Pushes were 0 in last" pairs 0 to `last` and dies when `last` holds 2 — before D2 is even needed. Every code-fact template at [framework/glimmer/code_facts.py:78](../../framework/glimmer/code_facts.py:78) writes "from {value} in {period} to {value} in {period}", two tokens and two mentions, which pairs cleanly by order (and under (a)); a test pins all five shapes passing. Stated limit: exotic phrasing ("3 and 1, in prior and last respectively") can mispair and drop a true statement. Conservative, and the templates plus the prompt's own instruction to name the period keep real statements inside the paired shapes.

## Risks

- **The floor trades freshness for honesty.** A cycle at 13:05 sees periods ending at 13:00, and the last minutes of activity wait a cycle. Accepted: the alternative is inventing which half of a stored hour happened when, and an invented change already reached my phone once.
- **Suppressing the zero loses some true sentences.** When the open hour holds a push, "fell to 0 in last" is dropped even on the reading where `last` is the floored period and the sentence is technically true of it, and at the gate the same claim now fails `L1B_UNKNOWN_METRIC` because the snapshot omits that key entirely. A reader does not carry the floor definition in his head; I would read it as "nothing since yesterday" next to a card counting that push. Dropping is the honest side.
- **Loading all calendar history per cycle** is O(my calendar) every cycle. Correct at this scale by the argument in D4; if the store ever makes it slow, the fix is an index or a reconciled-cache, not a narrower event-time bound, which would reintroduce item 2.
- **Period pairing is a heuristic** (D8). By-order pairing plus (a)–(c) cover the template shapes and the prompt's instructed shapes exactly, and can drop a true exotic phrasing. A drop is visible as a code; a false keep is not. That asymmetry is why the heuristic is acceptable here and why Ticket 10b's binding should replace it when it lands.
- **Move suppression reads one `collected_at` as one poll, and only an appearance counts as the sibling** (D4 step 2a). That equality is how the collector stamps a poll, so it holds for collector rows; the `updated` rows a master stamp bump mints for the surviving instances are not appearances of their keys, so they no longer hide the cancellation that came with them. Hand-built rows that share a timestamp across polls could still look like one poll and, if one of them is an appearance, lose a real cancellation. It fails in the safe direction — it undercounts by one and invents nothing (Known gaps) — against a live bug that invents a cancellation every time I reschedule a block.
- **The stamp arm writes more rows** (D5). A provider that bumps `LAST-MODIFIED` on every fetch would emit an `updated` per poll. That is also what today's collector does, the extra rows reconcile to the same winner, and the alternative — ignoring stamp changes — loses renames entirely, because the title is not in the snapshot.
- **Cursor v2 tombstones grow the cursor** by one entry per cancelled instance inside the collector window. Bounded by the same window that bounds instances, and pruned on the same rule.

## Known gaps (not in this ticket)

- A calendar restoration that already got stuck in my real store before this deploy stays stuck until that block changes again (D5). New ones can't get stuck. I'd rather say that here than pretend the deploy heals history.
- A block cancelled before this deploy and restored after it stays cancelled too. The cursor no longer holds it, so it gets its first identity again, and the store treats that as a re-delivery of a row it already has. The cancellation still wins. Same reason as the line above, seen from the other side of the deploy.
- If I ever delete every VEVENT from a calendar, the empty-feed guard means nothing gets cancelled until a new event shows up. I accept that: a feed holding zero VEVENTs is far more likely to be a broken feed than me deleting my whole calendar. Deleting some events, or the only upcoming one, cancels normally — the guard counts VEVENTs in the body, not instances in the window.
- A recurring instance cancelled in the same poll where a new instance of that series enters the 14-day horizon still reads as a move and isn't counted (D4 step 2a). That new instance's first row is a real appearance of its key, so the narrowed rule can't tell it apart from a move. That undercounts by one and invents nothing. I'll take a missing cancellation over a made-up one every time.
- A block moved beyond the 14-day horizon, or more than 2 days back, still reads as cancelled until it comes back into the window. The collector only expands that window, so it can't see where the block went, and neither can the metric. For a recurring instance the count rights itself when the block comes back into view, because its key holds its `RECURRENCE-ID` and it comes back under the same key. A one-off block doesn't: it comes back under a new key in a later poll, so its old cancellation stays on the count until that date ages out of the three periods. Until then it says cancelled about a block I only moved.
- A zero that names no period still passes under the old rule, and the word `other` as a screen category still reaches model facts. Both are written down in D8 and D7 with their reasons; neither gets fixed by guessing.

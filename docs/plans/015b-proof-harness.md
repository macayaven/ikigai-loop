## Approach

### Key decisions — shared by R2, R3, R4 (binding; each with its reason)

- **D1, modules live in `evals/`, pure cores split from edges.** `evals/gate_identity.py` (identity, dirty checks, tree state), `evals/live_guard.py` (live gate, quiet windows, drain, stop logic), `evals/r2.py` (harness, scanner, pure report + `docs/r2.md` renderer), `evals/r3.py` + pure `evals/r3_score.py`, `evals/r4.py` + pure `evals/r4_scenario.py` + pure `evals/r4_score.py`. Reason: the repo's proven pattern is a pure core with edge injection ([framework/glimmer/facts.py:1](../../framework/glimmer/facts.py) by design, mirrored by Ticket 11 and by R1b's runner/summary split); scorers must be testable from hand-written rows with no model, no clock and no filesystem beyond the rows passed in. `python -m evals.r2|r3|r4` works via the namespace package the tests already import (`from evals.r3_scenario import apply_ops`, [tests/test_r3_pairs.py:20](../../tests/test_r3_pairs.py)); no `evals/__init__.py` is added.
- **D2, live runs are opt-in by variable, mirroring the existing precedents.** R3 requires `IKIGAI_R3_LIVE=1`, R4 `IKIGAI_R4_LIVE=1`; without it each prints one `disabled` line and exits 0 without touching results. Reason: `IKIGAI_R10_LIVE` ([evals/r10.py:569](../../evals/r10.py)), `IKIGAI_R1B_LIVE` ([evals/r1b.py:1109](../../evals/r1b.py)) and `IKIGAI_PROPOSAL_LIVE` ([tests/test_proposal_live.py:24](../../tests/test_proposal_live.py)) already establish this exact shape; `--summary` never needs the variable. R2 has no live mode and no variable. R3/R4 CLIs use R1b's words where the thing is the same: `--stop-time`, `--limit`, `--results-dir`, `--concurrency` ([evals/r1b.py:971](../../evals/r1b.py)).
- **D3, exit codes are closed and identical for R3/R4 live runs, aligned with R1b where the thing is the same.** `0` = every planned repeat slot is drawn or exhausted; `2` = refusal or bad arguments (D6 refusals, `--repeats != 3`, unknown identity, pairs-hash mismatch); `3` = stopped after three consecutive unavailable repeats (D10) — R1b's unavailable-stop code ([evals/r1b.py:85](../../evals/r1b.py)); `4` = stopped cleanly (quiet window or its drain margin, `--stop-time`, or `--limit` reached) with work remaining; `1` = any other failure. `--summary` exits `0` on success, `2` on unknown identity or unreadable rows. R2 exits `0` whenever the scan completes — including escapes > 0 — and `1` only on harness error (which includes a blind recording under D21's end-to-end control). A canary found in `stored_outbound` and elsewhere stays an escape:

  - *Public repo names* (`github.*.repo` on public-tier rows): the collector tiers GitHub rows `public`. The scanner normalises both canary (full string and distinctive word alone) and corpus by casefolding, collapsing all whitespace runs to one space, percent-decoding (`urllib.parse.unquote`, applied twice), and JSON-string unescaping (`\uXXXX`, `\"`, `\\` via a `json.loads` pass over quoted fragments plus a manual `\u` decode) — a canary found under any normalisation counts once per channel. Positive controls, two kinds: (i) *builder-level* — for **each** channel, a test injects one canary (plain, upper-cased, extra-whitespaced, percent-encoded and `\u`-escaped forms) into that channel's corpus builder and asserts the scanner reports it, so "0 escaped" cannot come from a scan that cannot see; the `stdout_stderr` control writes through the descriptor (`os.write`) inside the capture scope. (ii) *End-to-end* — one **control canary outside N**, planted in one commitment title (which the design prints) in every world: it must be found in the main world's `wonder_prompt`, `meta_body`, `telegram` bytes, `card_stored` and `trace`. Where no natural path exists — `chart_input` (titles never enter chart data), `why_reply` (pieces are statements and fallback lines, never titles) and `stdout_stderr` — the builder-level control is kept and the report says so.

- **D30, the scorer is pure, applies PREREG to the letter, and also computes the literal reading.** `evals/r3_score.py: score_rows(rows) -> Score` takes parsed JSONL dicts (one identity's file) and: selects per slot the first drawn execution, else marks exhausted/missing; computes real picks per arm (pick ≠ null); *most-picked set* = commitments with maximal count among real picks (empty when no real picks). **Invariance** passes iff both arms have ≥1 real pick and every perturbed most-picked commitment is in the base most-picked set; an arm with no picks fails the pair, and the count of such pairs is a printed number ([docs/PREREG.md:57](../PREREG.md)). **Directional `expect_pick`** passes iff perturbed count(expect) ≥ 2 of 3 runs and > base count(expect) ([docs/PREREG.md:58](../PREREG.md)) — counts are over the 3 runs, no-picks included in the denominator reading. **Directional `expect_avoid`** passes iff perturbed real picks ≥ 2 and count(avoid) ≤ 1 and < base count(avoid) ([docs/PREREG.md:59](../PREREG.md)). **Uninformative** (directional only, decided before pass/fail): base count(expect_pick) == 3, or base count(expect_avoid) == 0, or base real picks < 2 ([docs/PREREG.md:60](../PREREG.md)). A missing repeat slot (not drawn, not exhausted — run still incomplete) is reported as missing, the pair scores as failed with the missing count printed, and the whole receipt's prediction verdict is `incomplete` (D32); `--summary` never invents a draw (update D: "It says when a repeat is missing"). **Literal reading:** the scorer also computes a second selection — each slot's **first execution stands**, whatever it was, an unavailable first execution counting as no pick — and re-derives the registered scores (informative set, directional passes, invariance passes, verdicts per D32) under it. This block prints whenever any slot's first execution was unavailable and a later execution exists (equivalently, whenever it could differ), showing what update F's re-run reading changed — usually nothing; it costs nothing because every execution is already on record. Wilson intervals are 95% score intervals (z = 1.959964), computed in the scorer with the standard formula, described in every output as describing these fixed pairs only (Deviation 6). `tests/test_r3_score.py` covers every rule with hand-written rows: tied most-picked in base and in perturbed (subset pass and non-subset fail), an arm of pure fallbacks (and its no-picks pair count), each uninformative arm, boundary counts (2-vs-2 not a move; 2 perturbed avoid picks fail the ≥2-real-picks/≤1 conjunction distinctly), exhausted-unavailable as no pick, missing repeat → `incomplete`, per-profile denominators (D32), prediction per part and combined in all four statuses, literal-vs-rerun selections differing and agreeing, and a by-hand Wilson value.

### R4 — evidence sensitivity (live; `python -m evals.r4`)

Called a sensitivity test everywhere in code and docs, never proof of faithfulness (brief §3, update H). Fact ids never change within a case.

- **D37, cases are built from R3's stored base drafts by a fixed, profile-balanced traversal — nothing is chosen after seeing results.** `evals/r4_scenario.py: build_cases(r3_rows) -> tuple[Case, ...]` is pure. For **each profile separately** it walks that profile's scored R3 base executions in pair-file order (builder: D1–D5, I1, I3, I5, I7, I9; disconnect: D6–D10, I2, I4, I6, I8, I10; repeats 1–3 within a pair, base arm only), parses each first-attempt `raw_text` with the product's `parse_draft` ([framework/proposal/schemas.py:141](../../framework/proposal/schemas.py)) under the same flags `propose` used (facts and metrics present, no parent), and takes the first **5 eligible drafts per profile** under D38/D39 — 10 cases total. (One pooled first-10 traversal would take Builder cases only: D1–D5 are all Builder with 3 repeats each, so Disconnect would never be tested.) Final case order is pair-file order among the selected drafts, case ids `r4-01`…`r4-10` assigned in that order (decision, so ids are stable given the same R3 rows). The base scenario for every case is the R3 base scenario; the profile is that pair's profile. Each case stores its provenance (R3 pair/repeat, base `prompt_hash`, base draft JSON) on its R4 rows, so the base draft never needs re-drawing and cited/control share literally one base draft. If either profile yields fewer than 5 eligible base drafts, R4's live run refuses (exit 2) and says how many per profile were found — it does not lower the bar or borrow from the other profile. Reason: PREREG fixes "10 of each" but not case construction; deriving cases from already-committed R3 draws by a traversal fixed here is the strongest available defence against choosing drafts that flatter the result, and it costs zero extra base calls. The default R3 file is the one R3's own `results_filename` gives for the same model, effort, gate hash, prompt hash and closure — the tree's identity for a live run, the scored rows' identity for `--summary` — selected by name, never by recency, so a newer R3 file for another gate sitting beside the right one cannot win; an R3 file without the closure part keeps today's lookup by the old name. If that file does not exist, a live run refuses (exit 2) and `--summary` still renders, with the noise-floor and discard sections saying no matching R3 rows. `--r3-file` still overrides, and then its model, effort, gate, prompt and pairs hash must all match, or exit 2. A live run also refuses (exit 2, naming how many R3 slots remain) unless every R3 slot is drawn or exhausted under R3's own remaining-slot count — if an R3 slot could still be drawn later, a later draw could change which draft is "first eligible" and the case numbers would shift under rows already written. R4 requires the R3 rows' model, effort, gate identity, prompt identity, closure identity (when the R3 rows carry it) and pairs hash to equal the run's (else the drafts came from a different model, gate or prompt than the regenerations — the file name carries gate, prompt and closure and a changed prompt also makes those base drafts a different draw) — mismatch is exit 2 naming the identities; its rows also copy the source rows' `pairs_sha256` (D5). Assumption (headless review): rebuilding the planned case ids from the R3 rows for the summary's missing-slot count is the same traversal, so the count matches the live run's 20 arm slots.
- **D38, the cited fact is chosen by rule, and a draft that cites nothing usable is discarded and counted.** From a parsed base draft: cited facts = sorted union of `fact_ids` over all claims in `overall_state`, `working`, `not_working` (`since_last` is always empty without a parent). Eligible cited facts = cited facts whose statement maps to a changeable family under D39's table (f1–f5; f6 is changeable but has no matched control, D39, so f6 alone never qualifies a case). The cited fact is the **lowest fact id** among eligible cited facts. A draft with no eligible cited fact (cites no fact at all, or only f6) is discarded, the profile's traversal moves on, and discards are counted by reason (`no_fact_cited`, `only_feed_fact`, `unparseable`, `no_matched_control`) per profile in the summary. Reason: lowest-id is arbitrary in the right way — fixed before any regeneration exists, insensitive to which choice would move the pick.
- **D39, the value change touches statement and metrics together; the control is uncited in both senses.** Every base fact f1–f5 is a three-period statement over `period.{earlier,prior,last}.<family>` with the fixed family table: f1→`pushes`, f2→`screen_hours.Work/Programming`, f3→`screen_hours.Media/Video`, f4→`screen_hours.Comms/Chat`, f5→`tag_hours.iki-family`. The change sets `period.last.<family>` to `0` and rewrites the statement to the PREREG directional phrasing `"<Label> fell from <prior> in prior to 0 in last."` — verbatim the registered D1/D8 statements where they exist ([evals/r3_pairs.json:41](../../evals/r3_pairs.json)), the identical template with the family's label and prior value where they do not (f2, f3, f4). f6's change would be count 6→25 (D4's statement) but is never used (D38). The changed scenario is produced by the same `set_fact`+`set_metric` ops through `apply_ops`, so ids are untouched and statement/metric can never disagree. *Matched control* = the lowest-id fact that is (a) cited in **no** claim's `fact_ids`, **and** (b) its family appears in **no** claim's `metric_refs` — a metric ref belongs to family `<family>` iff it is `period.{earlier,prior,last}.<family>` for some period — of the same template class (period-metric, f1–f5), changed by the identical operation. Both senses are required: a draft can cite `period.last.pushes` as a metric ref without citing f1, and changing f1 then changes a number the draft cites. The cited fact remains a fact id cited by the draft, whatever metric refs it also holds. A hand-draft test pins control selection where the lowest uncited-by-id fact is cited-by-family and must be skipped. If no control qualifies the case is discarded as `no_matched_control`. A test runs every buildable changed scenario (all f1–f5 choices from synthetic hand drafts) through the same gate-as-claims checks [tests/test_r3_pairs.py](../../tests/test_r3_pairs.py) applies to an arm — each fact statement as one claim citing only its own metrics must yield zero violations under `evaluate_briefing` — so an internally contradictory prompt can never be sent. Reason for "last → 0" uniformly: it is the largest unambiguous move available for every family, identical in kind across cited and control, and already the registered direction for two families; tailor-made magnitudes per fact would be exactly the after-the-fact tuning this design forbids.
- **D40, two arms per case, paired on one base draft.** Arm `cited`: base scenario + cited-fact change. Arm `control`: base scenario + matched-fact change. Each arm is regenerated **once, first attempt only** (D41) — 10 cases × 2 arms = 20 calls, i.e. PREREG's "10 of each". - **D41, the first-attempt draft is reached with Ticket 11's real prompt and schema, proven equal to `propose`'s.** R4 builds its request exactly as `propose` does at [framework/proposal/core.py:249](../../framework/proposal/core.py): `metrics_map = offered_metrics(snapshot)`, `prompt = build_prompt(profile_id, profile_name=profile_id.capitalize(), facts in scenario order, metrics_map, deltas=(), eligible commitments (D26 path), hour, policy="")`, `schema = build_response_schema(commitment_ids, fact_ids, snapshot_metric_ids=list(metrics_map), delta_metric_ids=[], has_facts=True, has_metrics=True, has_parent=False)`, then one `TimeoutRetryClient(LocalRetryClient(MuseExecClient(timeout_s=WONDER_TIMEOUT_S))).complete(WonderRequest(prompt, model, effort, schema, forbidden_raw_literals=D26 literals))` — built by the same default factory as R3 (D36) — and `parse_draft(text, has_facts=True, has_metrics=True, has_parent=False)`. - **D42, "changed" is defined on citations and pick, never on text — in three measures fixed here, before any regeneration (update H's two traps).** For a parsed draft: `pick = commitment_id`; *whole claim signature* = the multiset over claims in `overall_state`/`working`/`not_working` of `(section, tuple(sorted(fact_ids)), tuple(sorted(metric_refs)))`, text ignored entirely; *reason signature* = `(tuple(sorted(first_overall.fact_ids)), tuple(sorted(first_overall.metric_refs)))` of the first `overall_state` claim — the claim that carries the reason (`((), ())` if a parsed draft somehow holds none). An arm *changed pick* / *changed whole signature* / *changed reason signature* iff that value differs from the base draft's. The whole signature may well differ between almost any two draws; that expected saturation is why the reason signature exists — both are reported for the prediction (D43) and **neither is chosen afterwards**. None of the three can fire mechanically when a cited value's digits change (same refs, new digits in text ⇒ unchanged) or on rewording (same citations ⇒ unchanged), while a model that actually re-grounds its argument registers. Their known blindness is stated in `docs/r4.md`: a claim that flips direction in words while keeping identical citations counts as unchanged; that is the price of a mechanical, pre-registered reading, and the noise floor (D44) calibrates how often each signature moves on its own. ## Risks

- **I8 is only meaningful at the `propose` seam.** Through `run_proposals` its prompt is base-identical (executed proof, D25), and the product would refuse its UTC slot outright (D26). The plan's reading — I8 tests representation-invariance of the hour string the model reads, via a direct `propose` call the product itself would never make for that stamp — is the only non-vacuous one available without editing `framework/` or the pair, both forbidden. `docs/r3.md`'s method section states the seam plainly so no reader over-claims.
- **R2 may find a real escape.** The sharpest candidates are metric-id paths (tag-shaped canaries, canary feed `source` / screen category keys become snapshot keys and may reach the prompt's metric table — some are D21 by-design lines, some may not be), public repo names reaching the prompt (by-design line, with its token caveat), and any targeted fact that survives the checks carrying planted text. That is the measurement working: the true count ships with the split, the fix is a follow-up ticket, and Step 3 records it without stopping.
- **R2's whole-slot worlds are the heaviest tests in the suite.** Roughly a dozen-plus slots render real charts (Pillow) and run gated proposals against fakes; still seconds each, but they couple `make check` to orchestrator behaviour changes and D18 budgets the total under a minute with a stop-and-report if that fails. That coupling is the point — R2 is a regression receipt for the live path — yet a future orchestrator change can legitimately require an R2 disposition update; the completeness test forces that update to be explicit.
- **Uninformative pairs can shrink R3's denominator hard.** If Wonder's base draw already picks the expected commitment 3/3 on several builder pairs (plausible: the base scenario is symmetric but models have priors), the registered headline rests on few pairs. Nothing may be retuned; Deviation 6's dual reporting (passes/informative *and* informative/10, "not evaluable" at zero) exists precisely so this cannot look like success.
- **R4's whole signature may saturate and all signatures are blind to direction flips with identical citations** (D42); with n=10 per arm, a one-case difference is 10 points. The reason signature, the per-profile noise floor (D44) and exact denominators are the mitigations, all fixed before any regeneration; the doc must not upgrade "sensitivity detected" into a faithfulness claim.
- **Subscription window contention.** R3 at ≈13 points with retries is small against a fresh 5-hour window but not against one already spent by live slots; `--limit` + resume + quiet windows with drain are the controls, and exit 3 makes a hard limit visible instead of degrading into counted fallbacks (update F).

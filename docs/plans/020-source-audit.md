## Approach

### Assumptions (stated because nobody can answer me; approval of this plan accepts each one)

1. **First request means the first URL of that endpoint's walker.** A non-200, invalid JSON, or a rate-limit response (403 or 429) on a first request fails the whole fetch with a closed code and writes no file. The same failure on a later page is not a fetch failure: paging stops, the stop reason is recorded as coverage, and the snapshot is still written. That reading is the only one that makes the brief's "a refused later page recorded as coverage and not as a failure" testable.
2. **Page caps.** Events and pulls: at most 10 pages each (1,000 rows), then stop with reason `page_cap`. Activity: at most 50 pages, then `page_cap`. GitHub's own refusal to paginate further (a 422 on a later page) records `github_pagination_refusal`; no `rel="next"` in the `Link` header records `last_page`, as pinned under Fetch. If a first page is refused, assumption 1 wins and the fetch fails.
3. **Instant text.** Every instant in the snapshot, the export, and stdout is UTC ISO 8601 with a `Z` suffix at second precision, parsed back with `datetime.fromisoformat` after replacing the trailing `Z`. `--tz` (default `Europe/Madrid`) changes only how instants print in the human-readable lines; it never changes a count, a comparison, or the export's instants, which stay UTC. An unknown `--tz` name, a naive `--as-of`, or an `--as-of` without an offset is a usage error (exit 2, closed code).
4. **What `recount --metric` accepts.** One of `prs`, `pushes`, `pushes_plus_prs`, `all` (default `all` where the flag is optional; on `recount` the flag is required by the brief's wording "for a stated instant and timezone", so I make `--metric` required there and `--tz` required there too, matching the brief's flag list for that command exactly). `compare` and `run` take `--metric` with default `all` and `--tz` with default `Europe/Madrid`, as briefed.
5. **`--card` values.** `latest` or an ISO instant. An instant names the delivered card whose `slot` equals that instant compared as instants, never as text. A card already carries both sides, so there is one card per slot: if a slot has more than one delivered row, I take the last by `rowid`. A card instant with no delivered card is `unavailable` at stage 4 with `CARD_NOT_FOUND`, not a usage error.
6. **Closed-code spelling.** Every reason code, status, limit code, and error code in this plan is an exact string the implementation uses verbatim. Adding a code later is a plan amendment, not an implementer choice, because the export's allowlist and the tests pin the set.
7. **The snapshot is one JSON object, written atomically.** `fetch` writes to a temporary sibling file and renames it onto `--out` only after every page and the allowlist self-check pass, so a failed fetch leaves no file at `--out` — including no partial file and no leftover temporary sibling.
8. **`run` folder layout.** `--out` is a folder the command creates if missing. It writes `snapshot.json` and `export.json` inside it, and nothing else. `run` always exports (the brief says "write the snapshot and the export there"), so `run` needs no `--export` flag of its own; passing one is a usage error.
9. **Numbers are integers.** Every count in the recount, the stages, and the export is a Python `int`. A stored snapshot value that is not a number, or that is not integral (for example `8.5`), compares as a mismatch, never rounded. A stored value of `8.0` equals the recount `8`.
10. **Reading JSON columns from the store never executes them.** `cycles.snapshot`, `proposal_results.snapshot`, `briefing_json`, `card_json`, and `chart_json` are parsed with `json.loads` only. Invalid JSON in a needed column is `unavailable` with a closed code for the affected stage, never an exception that reaches the output.

### The fetch and the snapshot: public by construction

`fetch --user <login> --repo <owner/name> --out <path>`. `--repo` is the full `owner/name` form (it names the repo for the pull list and the activity rows, and the `owner` half addresses those two endpoints); a value without exactly one `/` and two non-empty halves is a usage error (`USAGE_BAD_REPO`). A `--user` that fails the login shape is a usage error (`USAGE_BAD_USER`), checked before any request. The HTTP seam is one injectable function with the product's shape in spirit only: `http_get(url, headers) -> (status, headers, body_bytes)`, defaulting to a `urllib.request` implementation with a 15-second timeout. Tests inject a fake; the default is the only code that can touch the network, and no test calls it.

Every request carries exactly two headers: `Accept: application/vnd.github+json` and `User-Agent: ikigai-loop-source-audit`. No `Authorization` header is ever constructed — the code has no line that reads `GITHUB_TOKEN`, so a token in the environment changes nothing. That absence is the guarantee: anything an anonymous caller can read is public, so I need no filter after the fact. This is the deliberate opposite of the product collector, which calls `/users/{user}/events` with an optional token at [framework/collectors/github_events.py:115](../../framework/collectors/github_events.py:115) and :128-135 and can therefore return private events to their owner.

Only these three endpoints, all on `https://api.github.com`, page size 100 (`per_page=100` on the first URL of each walker). All three endpoints use one walker: I send the first URL, then follow the `rel="next"` URL from the `Link` header verbatim until there is none. There is no standalone page parameter anywhere in the plan or the code.

| # | First URL | Rows I read |
|---|---|---|
| E1 | `GET /users/{user}/events/public?per_page=100` | `id` (digit string), `type`, `repo.name`, `actor.login`, `created_at`, `payload` |
| E2 | `GET /repos/{owner}/{repo}/pulls?state=all&sort=created&direction=desc&per_page=100` | `number`, `created_at`, `user.login` |
| E3 | `GET /repos/{owner}/{repo}/activity?per_page=100` | `id`, `timestamp`, `activity_type`, `before`, `after`, `actor.login` |

For E1, `payload` contributes only: on `PushEvent`, `push_id`, `head`, `before`; on `PullRequestEvent`, `action` and `number`. Nothing else in the payload is read into the snapshot. E3 `activity_type` is one of `push`, `force_push`, `branch_creation`, `branch_deletion`, `pr_merge`, `merge_queue_merge`; any other value is kept as its raw string for coverage counting and ignored by the recount (it is an allowlisted field with a shape check, not an enum check — a new GitHub activity type must not break the reader).

I take `fetched_at` before the first request, not at the end. So "fetched at or after the window end" means every row was read after the window closed.

A short page is not the end: filtered rows make pages short, and stopping there could silently lose later pages. The check on a next URL is scheme and host only, never the path, because the real next URLs use another path form from the one requested (Reviewer-stated facts). A next URL whose scheme is not `https` or whose host is not `api.github.com` is never followed: paging stops with `github_pagination_refusal`, because a snapshot built from another host is not a GitHub snapshot.

Paging stop reasons, one closed code per source, recorded in the snapshot's coverage: `last_page` (a response with no `rel="next"`), `empty_page` (a later page with 0 rows; a first page with 0 rows and no `rel="next"` is `last_page`, because an account with no public events is a valid empty snapshot), `github_pagination_refusal` (a non-200 on a later page, including 403/429/422, or a transport failure reaching it), and `page_cap` (assumption 2). A later page whose body is not valid JSON or not a list stops with `github_pagination_refusal` too — I do not get to guess what that page held. Failure on a first page is different and fatal: non-200 → `FETCH_FIRST_PAGE_FAILED`, 403 or 429 on a first page → `FETCH_RATE_LIMITED`, invalid JSON or a non-list body on a first page → `FETCH_INVALID_RESPONSE`. A fatal fetch prints the one code, exits 2, and writes no file (assumption 7).

The snapshot file is one JSON object with exactly these keys, and the reader rejects anything else:

```json
{
  "fetched_at": "<UTC instant>",
  "user": "<login>",
  "repo": "<owner/name>",
  "events": [{"id": "…", "type": "…", "repo": "…", "actor": "…", "created_at": "…",
              "action": "…"|null, "pr_number": 0|null, "push_id": 0|null,
              "head": "…"|null, "before": "…"|null}],
  "pulls": [{"number": 0, "created_at": "…", "author": "…"|null}],
  "activity": [{"id": "…", "timestamp": "…", "activity_type": "…",
                "before": "…"|null, "after": "…"|null, "actor": "…"|null}],
  "coverage": {"events": {"rows": 0, "oldest": "…"|null, "newest": "…"|null, "stop": "…"},
               "pulls": {…}, "activity": {…}}
}
```

Only the kept row kinds appear: `events` holds every row E1 returned, whatever its `type` (coverage counts need all rows, and the per-repo breakdown needs the repo names of rows I do not count). Field rules, enforced by the reader and by the writer's self-check: event `id` is a digit string; `pr_number` and `push_id` are non-negative ints or null; `head`, `before`, `after` are 40-char lowercase hex strings or null; `repo` is `owner/name` with each half matching `[A-Za-z0-9_.-]+`; logins match `[A-Za-z0-9-]+` with an optional trailing `[bot]`; instants parse as aware datetimes. Real logins can end in `[bot]`, and the API allows a null user on a pull and a null actor on an activity row: `author` and activity `actor` may be null, neither shape fails the snapshot, and such rows are kept and count for nobody, since they do not equal the user. The user and repo names compare case-insensitively everywhere. Coverage `rows` counts rows returned by that endpoint before any filtering; `oldest` and `newest` are over all rows returned by that endpoint, not only the kept types, and are null when the endpoint returned nothing. No title, body, branch name, commit message, or raw payload ever goes in — the writer builds each row dict field by field from the allowlist, so a field GitHub adds tomorrow cannot ride along.

The snapshot reader (`snapshot.py`) is strict in the other direction: an unknown key at any level, a missing key, a wrong type, or a value that fails its shape check rejects the whole snapshot with `SNAPSHOT_INVALID` and exit 2 on `recount` and `compare`. A snapshot I cannot trust is an operational error, never a stage verdict, because reporting stage numbers against a malformed recount source would pass off a guess as an audit.

### The recounter: its own definitions, the product's meaning

Written fresh in `recount.py`, from the product's meaning as checked above. Three definitions, mine in wording, the product's in effect:

**Window.** `floor_hour(as_of)`: pin `as_of` to its own fixed offset, convert to UTC, drop minute/second/microsecond, convert back — the same construction as [framework/glimmer/metrics.py:28-40](../../framework/glimmer/metrics.py:28-40), written out here because importing it would break independence. The floor is in UTC and not on the wall clock of a half-hour zone, so at a fixed +05:30 offset the floored instant has UTC minute 0 and local minute 30. `window_bounds(as_of) = (floor_hour(as_of) - 72h, floor_hour(as_of))`. `period_bounds(as_of)` is three half-open 24-hour periods ending at the floor: `earlier = [end-72h, end-48h)`, `prior = [end-48h, end-24h)`, `last = [end-24h, end)`. All arithmetic is on absolute time (aware datetimes), so a DST change inside the window moves no boundary. Items with time in the open hour `[floor_hour(as_of), as_of)` count in no period and no total; the recount reports them separately as `open_hour` per metric. `--tz` only changes how instants print.

**Scope.** The stored metric counts everything in the user's public feed across all repos (the product's collector polls the user feed, and `build_metric_snapshot` counts every winner it is given), so a one-repo recount would mismatch by construction whenever I touch another repo. The source count therefore covers the user's whole public feed, and reports a per-repo breakdown: for each repo name seen in the window, its `prs` and `pushes` counts. `--repo` names the one repo that gets the independent pull list and the activity rows. Other repos come from the feed only, and every report says so with their combined count (`other_repos_feed_only` in the export, plus the fixed sentence keyed `LIMIT_OTHER_REPOS_FEED_ONLY`).

**Opened pull requests (`prs`).** One item per `(repo, pr_number)` pair, never per row and never per event id, with repo names compared case-insensitively. Author is the user (`--user` on fetch; on recount/compare the snapshot's `user`), compared case-insensitively. Time is its creation. `merged`, `closed`, `reopened`, and any other action count nothing — that is `is_opened_pr` at [framework/glimmer/metrics.py:70-82](../../framework/glimmer/metrics.py:70-82) restated: only the `opened` action creates the item. For `--repo`, the pull list (E2) is the source: item time is the pull's `created_at`, author is the pull's `user.login`, which may be null; a null author counts for nobody. For other repos, the feed's `PullRequestEvent` rows with `action == "opened"` are the source, keyed the same way, author from `actor.login`. The two sources for `--repo` are cross-checked at stage 1; they are never merged into one count, because merging would hide exactly the disagreement the stage exists to show. The recount's headline `prs` number for `--repo` is the pull-list count; the feed count for `--repo` is reported beside it.

**Pushes (`pushes`).** One item per push identity: `push_id` when present, else the `head` SHA, never the event id. Actor is the user, compared case-insensitively; repo names compare case-insensitively too. Time is the event's `created_at`. The only public source of `PushEvent` rows is the feed (E1). There is no independent source for this metric, and nothing in the output may imply one: stage 1 for `pushes` is `unavailable` with code `NO_INDEPENDENT_SOURCE` (or `mismatch` on a duplicate, below), and the fixed sentence keyed `LIMIT_PUSHES_FEED_ONLY` prints on every report. An activity row with a null actor is kept and counts for nobody. From the activity rows I report one information-only number per activity type: ref updates in `--repo` in this window, by the user, with no matching `PushEvent`, matched by activity `after` to push `head`. It changes no status, carries code `ACTIVITY_UNMATCHED_INFO`, is labelled information-only wherever it prints, and prints only when the activity list covers the window — activity coverage decides only whether that number prints, never a status. I do not call it a push count, because on the Nov 1 measurement the activity endpoint typed all 8 feed pushes as `pr_merge` and returned no `push` row at all.

**`pushes_plus_prs`.** Per period, `pushes + prs` from the two recounts above, because the card's chart plots that sum (`chart_json` `pushes` series labelled `pushes + PRs` at [framework/cycle/card_build.py:43](../../framework/cycle/card_build.py); the product's own sample chart uses a plain `pushes` series at [framework/telegram/sample.py:45](../../framework/telegram/sample.py:45), which is a sample and not the delivered shape). Its stage 1 status is the worse of the two metrics' stage 1 statuses (`mismatch` worse than `unavailable` worse than `match`), and its numbers are the sums.

**Duplicates.** Two snapshot rows with one identity count once, and the recounter reports them with their public identifiers: a second `opened` feed row for one `(repo, pr_number)` under another event id (both event ids printed), a repeated `number` in the pull list, a repeated push identity (`push_id` or head SHA, with the event ids that carried it). A snapshot holding any duplicate gives stage 1 a `mismatch` with code `DUPLICATE_IN_SNAPSHOT` for every metric that identity belongs to (`pushes_plus_prs` inherits it from either parent). The count stays the deduplicated count — the mismatch is about the snapshot's shape, and reporting the inflated number would repeat the 009d error inside my own audit.

**Coverage.** A window is covered by the feed only when all of these hold: (a) `fetched_at >= window_end`; (b) `window_start >= fetched_at - 30 days`; (c) either the events paging stopped on its own (`last_page` or `empty_page`) with fewer than 300 rows returned, or the oldest events row returned is at or before `window_start`. A pull or activity list covers the window when its paging reached `last_page` or its oldest row is at or before `window_start`, and it was fetched at or after `window_end`. No coverage means `unavailable` with code `COVERAGE_GAP`, never a number passed off as complete — the numbers still print, marked by that code, because a reader needs to see how far off the run was, but no stage that depends on the uncovered source may say `match`. If `fetched_at` is under 6 hours past `window_end`, the recount sets `feed_settled: false` and the report carries the fixed sentence keyed `LIMIT_FEED_MAY_SETTLE`: a feed row that has not appeared yet can turn this run into a mismatch that clears on a later re-run, and the reader is told that in those words, not left to guess why I am not alarmed.

Giving `--card` and no way to name the subject is handled by the subject rule below, not by a flag error.

### Choosing what to audit

In order, first match wins for the cycle; the card choice is separate and then joined to a cycle below.

1. **With `--card`.** The delivered card at that slot, or the latest delivered card. `latest` means the greatest slot instant among delivered cards; if a slot has more than one delivered row, I take the last by `rowid` (on the fallback path, the last `telegram_cards` row for that slot by `rowid`). Stage 4 audits that one card. The cycle comes from joining the card to `proposal_results` (below). `--card latest` with no delivered card is not an error: stage 4 is `unavailable` with `CARD_NOT_FOUND`, and the target falls back to the latest cycle (rule 2). With no cycle either, it is `USAGE_NO_TARGET` (exit 2).
2. **Without `--card`.** Stage 4 is `unavailable` with `CARD_NOT_SELECTED`. The latest cycle for the subject: greatest `as_of`, then run, then id — the same pick as `fetch_latest_cycle` at [framework/store/fact_store.py:316-339](../../framework/store/fact_store.py:316-339), rewritten with plain SQL and instant comparison in Python, because stored `as_of` text under different offsets does not sort as instants.
3. **With `--as-of` and no card.** The cycle stored at that instant if any (a `cycles` row whose `as_of` equals `--as-of` as an instant; if several runs share it, the greatest run). Otherwise no cycle, which is valid: stage 1 and the row diagnostics still run, stages 2-4 that need a cycle or a card are `unavailable`, and the exit code follows the verdict rule (INCOMPLETE → 3 unless stage 1 already failed). Giving both `--as-of` and `--card` is `USAGE_AS_OF_WITH_CARD` (exit 2), never this rule.
4. **No card, no cycle, and no `--as-of`.** Exit 2 with `USAGE_NO_TARGET`. There is nothing to walk a number to. The same code covers `--card latest` with no delivered card and no cycle.
5. **Subject.** If `--subject-id` is given, I use it and never print it. If it is missing, the store must hold exactly one distinct `subject_id` among its GitHub rows (`events` rows with `source = 'github'`); zero or more than one is `USAGE_SUBJECT_AMBIGUOUS` (exit 2). I count distinct subjects in SQL and print only the code.

### A delivered card

Ticket 13's orchestrator is merged and it is what sends real cards, so the Ticket 13 path below is the live one; the fallback path remains for older stores without those tables, and the code checks which one the store in front of it supports. I check for a table before reading it (`SELECT name FROM sqlite_master WHERE type='table' AND name=?`). A missing table is a reason code, never an exception.

- **Ticket 13 path.** Either all three Ticket 13 tables exist or the fallback path applies. When `slot_ledger`, `slot_cards`, and `slot_card_payloads` all exist: a card counts as delivered only when a `slot_ledger` row has `step = 'send'` and `outcome = 'delivered'` for its `card_id`. Each delivered card appears once, for the audited subject only: side rows share a `card_id`, and rows for other subjects are ignored. I read the card body from `slot_card_payloads.card_json` (the `Card` model: `slot` and `statements`, at [framework/telegram/models.py:136-141](../../framework/telegram/models.py:136-141)) and the chart from `slot_card_payloads.chart_json`. `delivery_proven` is true.
- **Fallback path.** When the Ticket 13 tables do not all exist, I read `telegram_cards` from [framework/telegram/ledger.py:10-21](../../framework/telegram/ledger.py:10-21) (`card_id, card_json, created_at`; the `Card` JSON is the same model). `delivery_proven` is false, and stage 4 can be `mismatch` or `unavailable` but never `match`, with code `DELIVERY_NOT_PROVEN` attached to any would-be match. The reason is in the ledger itself: `save_card` at :36-53 writes the card before any send, so a row there proves a card existed, not that it arrived. "Latest" on this path means the greatest `card_json.slot` instant; if a slot has more than one row, I take the last by `rowid`. A fallback card whose slot is unreadable is skipped, and the sort never compares an unreadable slot against an instant.
- **Neither path.** When `telegram_cards` is also missing, stage 4 is `unavailable` with `CARD_TABLE_MISSING`. The rest of the audit still runs.

### Joining card to cycle, and the window guard

The card's `slot` joins `proposal_results.slot`, compared as instants and never as text. The join ignores `noop` rows: a `noop` side is not on the card and may name a placeholder cycle. Only `proposal` and `fallback` rows join, taking the latest row per profile by `rowid` — the same pick as `results_for_slot` at [framework/store/proposal_store.py:426-444](../../framework/store/proposal_store.py:426-444), rewritten in plain SQL — and only those rows take part in the snapshot-agreement check at stage 2. That row gives `cycle_id`, `run`, `snapshot`, and `briefing_json`. If the joined rows at that slot name more than one distinct `(cycle_id, run)`, stage 4 is `unavailable` with `CARD_CYCLE_AMBIGUOUS`, and stages 2 and 3 use the greatest `as_of` among the joined cycles. If no `proposal` or `fallback` row sits at the card's slot, stage 4 is `unavailable` with `CARD_NO_RESULT_ROW` and stages 2-3 fall back to the chosen cycle from the rules above (or `unavailable` when there is none).

**Window guard.** When the chosen cycle has facts (at least one `facts` row for its `(cycle_id, run)`), its stored `facts.window_start` and `facts.window_end` must equal this package's window for `cycles.as_of`, compared as instants. Facts that disagree among themselves on the window hit `WINDOW_RULE_MISMATCH` too. If they differ, I print a plain window-rule mismatch (fixed sentence keyed `WINDOW_RULE_MISMATCH`, with the two window pairs as instants), mark stages 2 to 4 `unavailable` with code `WINDOW_RULE_MISMATCH`, and compare nothing. This catches a cycle made under another rule and it catches this package drifting from the product; both look the same from here and I do not pretend to tell them apart. When there are no facts, I report that the guard could not run (code `WINDOW_GUARD_NO_FACTS` on stages 2-3 as a note; it changes no status by itself). Stages 2 and 3 use the cycle's `as_of`; stage 4 uses the card's `as_of` (below), so the two windows can differ when a cycle is reused, and the output shows both windows when they do.

### The four stages

For each chosen metric, each stage gets exactly one status — `match`, `mismatch`, or `unavailable` — plus numbers per period and a total, and closed reason codes from the table below. A stage line shows that stage's own numbers, or `-` where it has none, so an unavailable stage never looks as if it held a number. The stage 1 line already shows the recount. On a stage 1 coverage gap, stages 2 to 4 are `unavailable` with `COVERAGE_GAP` (inherited, listed after any stage's own code). A pre-floor cycle caught by the window guard overrides that: stages 2-4 carry `WINDOW_RULE_MISMATCH` and nothing else is compared.

**Stage 1, source (the recount itself).**
- `prs`: `match` when coverage holds for both the feed and the pull list, there are no duplicates, and the pull list and the feed's `opened` rows agree on the set of `(repo, pr_number)` for `--repo` in the window (same set, hence same per-period counts — set agreement is checked on the window, and the per-period numbers print from the pull list). `mismatch` when the two sets disagree (code `SOURCE_SET_DISAGREE`, naming the public identifiers in the symmetric difference: repo, PR number, and the event ids on the feed side) or a duplicate exists (`DUPLICATE_IN_SNAPSHOT`). `unavailable` on a coverage gap (`COVERAGE_GAP`).
- `pushes`: always `unavailable` with `NO_INDEPENDENT_SOURCE`, or `mismatch` on a duplicate (`DUPLICATE_IN_SNAPSHOT`). It still shows the feed recount per period. Nothing in the wording may suggest the activity number rescues this stage: stage 1 for pushes carries only `NO_INDEPENDENT_SOURCE`, and `ACTIVITY_UNMATCHED_INFO` belongs on the activity line alone, because it changes no status and is not a finding about that stage.
- `pushes_plus_prs`: the worse of the two stage 1 statuses, with both parents' codes carried.

**Stage 2, stored metric.** From `cycles.snapshot` of the chosen cycle and run, at the cycle's `as_of`: for `prs`, the keys `period.earlier.prs`, `period.prior.prs`, `period.last.prs`, and the total `github.pr.count`; for `pushes`, `period.*.pushes` and `github.push.count`; for `pushes_plus_prs`, the per-period sums of the two stored families against the summed recount, with the total checked as `github.push.count + github.pr.count`, where a missing `github.*.count` key means 0 in the sum as well. Missing-key rules, pinned: a missing `github.*.count` key means 0, because the product drops zero totals at [framework/glimmer/metrics.py:394-406](../../framework/glimmer/metrics.py:394-406). A missing `period.last.*` key is not 0: since Ticket 9e the product withholds it when the family has open-hour activity (the deletion at [framework/glimmer/metrics.py:407-411](../../framework/glimmer/metrics.py:407-411)). That key's check is `unavailable` with `STORED_PERIOD_WITHHELD`, unless the source count for `last` is above 0, which is a `mismatch` with `STORED_PERIOD_MISSING` — the product cannot withhold a key whose floored count is non-zero. A missing `period.earlier.*` or `period.prior.*` key is always a `mismatch` with `STORED_PERIOD_MISSING`, because the product always writes those two families. I state the asymmetry plainly: `last` gets the withheld reading, `earlier` and `prior` do not. A stored value that is present but wrong — including a non-numeric value, NaN, or Infinity — is a `mismatch` with `STORED_NUMBER_WRONG`; `STORED_PERIOD_MISSING` is for a missing key only. A non-integral number such as 8.5 is a `mismatch`, and 8.0 equals 8 (assumption 9). A cycle snapshot that is invalid JSON or not an object, or a joined snapshot that is invalid JSON, makes stage 2 `unavailable` with `STORE_JSON_INVALID`. The cycle's `snapshot` and the `proposal_results.snapshot` of the joined card row (when a card was chosen and joined; only `proposal` and `fallback` rows take part) must agree on these keys; a disagreement is a `mismatch` with `SNAPSHOT_DIVERGES` at stage 2, naming the key (a metric key is a closed-shape string and may print; its values print as integers). No cycle means `unavailable` with `NO_CYCLE`.

**Row diagnostics, part of stage 2.** I read `events` rows with `source = 'github'` for the subject and the window (by stored `time`, compared as instants after parsing) — columns `source_id` (the GitHub event id), `type`, `time`, `collected_at`, and the `counts` object inside `data` JSON. A row whose `data` is not valid JSON is skipped and counted in `rows_unreadable`. Both (a) and (b) use the floored window. I report five numbers: (a) how many stored rows in the window with `collected_at` at or before `as_of` the product would count — `github.pr` rows whose `counts.opened > 0` for `prs`, `github.push` rows for `pushes`, using this package's own restatement of `is_opened_pr`, never the product's function — because that is what the product counts; (b) how many stored rows in the window were collected after `as_of` (`collected_at > as_of`), so a later cycle sees them and this one does not — code `ROWS_COLLECTED_LATE` with the count; (c) how many stored rows have no matching item in the public snapshot, as a count only, with no id, repo, or time, because such a row may not be public — code `ROWS_NOT_IN_SNAPSHOT`; (d) which public items have no stored row, with their public identifiers (repo, PR number or push identity, event id) — code `ITEMS_NOT_STORED`. The item check runs in both directions: open-hour public items are never reported (their stored rows cannot be in the window), pull-list items with no feed row are reported by repo and number without an event, and a public item whose only stored row was collected late is reported as late, not as not stored. These numbers show where a wrong count entered: 8 source items, 8 stored rows, and a metric of 16 points at the metric code; 8 source items and 9 rows points at the rows. The diagnostics never change stage 2's status by themselves; they sit beside it. If the `events` table is missing, the diagnostics are `unavailable` with `EVENTS_TABLE_MISSING` and stage 2 still compares the snapshot keys.

**Stage 3, fact statement.** At the cycle's `as_of`, as stage 2. All `facts` rows of that cycle and run, code and model origin alike (the `origin` column at [framework/store/fact_store.py:151-176](../../framework/store/fact_store.py:151-176); a store whose `facts` table predates that column is read without it, and origin is never printed). My own parser, with its own word lists, in two tiers. I report numbers and ordinals only — the ordinal of the statement among the cycle's facts for that metric (1-based, in `rowid` order), its parsed numbers per period, and its status contribution. Never the sentence, never a fact id. A public identifier or ordinal appears only for a problem: the `statements` list holds only the wrong statements, with each one's ordinal and its expected and found integers.

- *Tier 1, the exact code-fact form.* The two sentence shapes `code_facts` writes at [framework/glimmer/code_facts.py:87-111](../../framework/glimmer/code_facts.py:87-111): `Pull requests rose|fell from <n> in <period> to <n> in <period>.` and `Pushes rose|fell from …`, with the two periods consecutive (`earlier→prior` or `prior→last`, the `_PAIRS` at :31-34) and each number bound to the period named beside it. A tier 1 statement's two numbers compare to the recount for those two periods. The direction word is not audited (it is on the limits list).
- *Parser order, pinned.* First I mask number-and-time-unit pairs, written both as `24 hours` and as `24h`, and only then do I look for other-family words among what is left. So a sentence saying 8 pull requests in the last 24 hours parses as 8 in `last`, while a bare `hours` left over after masking still disqualifies. The word `feed` is different from the others: a statement naming it stays out entirely. It is not a claim for this metric and does not add to the unparsed count, because the product writes feed-topic facts of the form "N feed items about ..." and a topic about push notifications must not make `pushes` unavailable.
- *Tier 2, one family's words only.* A statement that names exactly one metric's words and no other family's word among what is left after masking. My word lists, matched whole (below): `prs` — `pull request`, `pull requests`, `pr`, `prs`; `pushes` — `push`, `pushes`, `pushed`, `pushing`. A statement naming both metrics' words, or `screen`, `calendar`, `cancelled`, `cancel`, `tag` or a bare `hours`, plus a number, is unparsed, for a human. (`pushes_plus_prs` has no tier: see below.) In tier 2, digit tokens and small spelled-out tokens (`zero` to `twenty`, and the tens `thirty` to `ninety`, as single tokens only — `twenty-one` is two tokens under my whole-word rule and I say so) pair by order with period words (`earlier`, `prior`, `last`) when both counts are equal, and each paired number compares to the recount for its period. Or: a single number with no period word compares to the 72-hour total. Any other shape — numbers and period words in unequal counts above one, or several numbers with no period word — adds to the unparsed count.
- *Not count tokens.* Masked number-and-time-unit pairs (`24 hours`, `24h`, and the other units `h`, `hour`, `min`, `minute`, `minutes`, `day`, `days`, `s`, `second`, `seconds`), a clock time (`13:30`, `1:30 pm`), a date (ISO, day-first, or month-name forms), and a number carrying a `%` sign are not count tokens. A decimal count (`2.5` as a count) is unparsed, not rounded. A statement that names a metric and has a number but fits neither tier adds to the unparsed count and never to a match. A statement with no number is not a claim here and is ignored by this stage. A statement naming `feed` is ignored by this stage entirely, with or without a number.
- *Whole words.* Matching is on whole tokens: I split on whitespace and strip surrounding punctuation, and a hyphenated compound is one token, so `push-review` is not a push, and a feed topic about push notifications stays out because `feed` keeps it out entirely. Case is folded. This is deliberately narrower than the product's label binding at [framework/briefing/labels.py:10-12](../../framework/briefing/labels.py:10-12), and the difference is stated: I would rather call a true sentence unparsed than bind a number to the wrong family.
- *Status.* Any wrong number in a parsed statement (either tier) is a `mismatch` (`FACT_NUMBER_WRONG`, with the statement ordinal and the expected and found integers). Otherwise, any unparsed statement that named the metric, or no parsed statement at all for that metric, is `unavailable` (`FACT_UNPARSED` with the unparsed count, or `FACT_NONE_FOUND`). Otherwise `match`. For `pushes_plus_prs`, stage 3 is `unavailable` by design with `FACT_FAMILY_NOT_STATED` — no fact statement states that sum — so its verdict can never be PASS. I say that plainly wherever the metric prints.

**Stage 4, delivered claim.** From the one delivered card at the slot (see "A delivered card"). Stage 4 uses the recount at the card's `as_of` from `slot_cards` when that table exists; stages 2 and 3 use the cycle's `as_of`, so the two can differ when a cycle is reused, and the output shows both windows when they do. On the fallback path, where `slot_cards` does not exist, stage 4 uses the joined cycle's `as_of`, and if there is no joined row it is `unavailable` with `CARD_NO_RESULT_ROW`. With no `--card`, stage 4 is `unavailable` with `CARD_NOT_SELECTED`; with a `--card` that names no delivered card, it is `unavailable` with `CARD_NOT_FOUND`. Per metric, stage 4 is split by design: `pushes_plus_prs` at stage 4 is the chart plus the since line — a claim's refs are never compared to the sum. `prs` and `pushes` at stage 4 are refs and statements, and never the chart. For `prs` and `pushes`: each entry in the card's `statements` is matched by exact text to a claim in that slot's `briefing_json` (the joined `proposal` or `fallback` row's briefing). A claim in the `since_last` section is a delta from the parent card, per [framework/proposal/assembly.py:76-84](../../framework/proposal/assembly.py:76-84), so it adds to a not-audited count with code `CARD_DELTA_NOT_AUDITED` and is never compared to the recount, whether its number equals the recount or not — comparing a delta to a window count would fail every honest card. Other matched claims: each `metric_refs` entry whose metric id belongs to this metric's family (`period.*.prs` and `github.pr.count` for `prs`; the `pushes` pair for `pushes`) compares its `value` to the recount for that period or total, and a claim with refs is settled by them, because the gate bound its text to them — I do not re-parse text the refs already settle. A statement with no refs in its family, or no matching claim at all, goes through the stage 3 parser (both tiers) against the recount at the card's `as_of`. If the card exists but states no number for this metric, stage 4 is `unavailable` with `CARD_NONE_FOUND`. For `pushes_plus_prs`: the chart's `pushes` series (from `chart_json` on the Ticket 13 path) compares per period to the recount at the card's `as_of`; a null series or a missing chart is `unavailable` with `CHART_MISSING`. A card, briefing, or chart whose JSON is invalid makes stage 4 `unavailable` with `STORE_JSON_INVALID`. On the fallback path there is no chart in `telegram_cards`, so the chart check for `pushes_plus_prs` is `unavailable` with `CHART_MISSING`. Same status rule as stage 3 for `prs` and `pushes` (any wrong number → `mismatch` with `CARD_NUMBER_WRONG`; else any unparsed → `unavailable`, and no stated number at all → `unavailable` with `CARD_NONE_FOUND`; else `match`); for `pushes_plus_prs` the chart plus the since line set the status (wrong period → `mismatch` with `CARD_NUMBER_WRONG`; null or missing chart → `unavailable` with `CHART_MISSING`; stated since differs → `mismatch` with `SINCE_LINE_WRONG`; unreadable since → `unavailable` with `SINCE_LINE_UNREADABLE` unless the chart already mismatched; else `match`). `delivery_proven` false blocks `match` in every case: a would-be match becomes `unavailable` with `DELIVERY_NOT_PROVEN`, while a wrong number still says `mismatch`.

**The card's since line, audited at stage 4 of `pushes_plus_prs` (Ticket 13 path only).** One plain count: a row counts when its time is at or after the floor of the previous card's `as_of`, before the floor of this card's `as_of`, and it was collected by this card's raw `as_of`. A first card passes `as_of` minus 24 hours as the previous instant. The previous card is the latest delivered card strictly before this slot, the same rule as `latest_delivered_card_id` at [framework/cycle/slot_ledger.py:401-411](../../framework/cycle/slot_ledger.py). The recount's bounds are the floor of the previous `as_of` to the floor of this `as_of`, half-open. The count is pushes plus opened pull requests by the recounter's own identities and sources. `--card <instant>` finds the previous card from all delivered cards, so `--card latest` and `--card <instant>` give the same bounds. This belongs to `pushes_plus_prs` at stage 4, beside the chart. A stated number that differs from the recount is a `mismatch` with `SINCE_LINE_WRONG`. A since line that exists but fits none of the product's forms makes the stage `unavailable` with `SINCE_LINE_UNREADABLE`, unless something else already mismatched. A card with no since line leaves the chart to decide alone. `parse_since_line` reads `First card, last 24h:` or `Since HH:MM:`, followed by a count piece, or by other pieces with no count piece (0), or by `nothing recorded` or `nothing new recorded` (0). Only the integer ever leaves that function.

### Output and the public export

Output format, pinned for `compare` and `run`. One header with the window in UTC and in `--tz`, `fetched_at`, `feed_settled` and `delivery_proven`; when stage 4's window differs from the cycle's window, the header shows both windows. Then for each metric one key=value line per stage: `metric`, `stage`, `status`, `earlier`, `prior`, `last`, `total`, `codes`, with `-` where a stage has no number. One verdict line per metric. Then the open-hour count per metric and the per-source coverage (rows, oldest, newest, stop), then the row diagnostics and the information-only activity number, then identifiers. `compare` lists identifiers only for problems (a disagreement, a duplicate, an item not stored); `recount` lists all of them. Then the limits sentences — every sentence every run, except `LIMIT_FEED_MAY_SETTLE`, which prints only when `feed_settled` is false.

`--export` writes one JSON object built only from: closed status and reason codes (from the set above, plus metric ids from the closed set `prs|pushes|pushes_plus_prs`), integers, booleans, instants (UTC, assumption 3; null where the run has no window), limits as codes only (`LIMIT_FEED_MAY_SETTLE` rides only when `feed_settled` is false), and public GitHub identifiers from the snapshot — repo names, logins, event ids, pull request numbers, push ids, and SHAs. Beside the stages, verdicts and rows it holds: the per-repo breakdown; open-hour counts per metric; coverage per source (rows, oldest, newest, stop); the card's window when it differs from the cycle's; the not-audited delta count as an integer beside its code; `activity_unmatched` per activity type (an empty list when nothing is unmatched, null only when the activity list does not cover the window); and the full `snapshot_diverges` list. The export holds no sentence at all, so no string in it has whitespace. Shape checks, one per string kind: repo `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`; login `^[A-Za-z0-9-]+(\[bot\])?$`; event id `^[0-9]+$`; SHA `^[0-9a-f]{40}$`; code strings `^[A-Z0-9_]+$` or a status/metric literal; instant parseable and `Z`-suffixed. Any string with whitespace fails every check. A final allowlist pass walks the whole export (every key and every string value, recursively) before writing and refuses to write — exit 2, code `EXPORT_REFUSED`, no file — if any string fails its shape check, so an unexpected value cannot get out by riding a field I forgot. Keys are from a fixed set in the code; an unknown key refuses too. The export holds no subject id, no card id, no cycle id, no fact id, no statement, no title, no calendar or screen value, and no path. Stored rows missing from the public snapshot are a count (stage 2 diagnostic (c)), never a row. Stdout is rendered from the export dict after it has passed the allowlist walk, and from nothing else except the fixed limit sentences from the table in `source_audit/limits.py` keyed by the limits codes below, so "stdout prints only what the export holds" is true by construction. `compare` without `--export` still builds and checks the export and just does not write it. If the walk refuses, nothing prints but the closed code `EXPORT_REFUSED`. On the Ticket 13 path the report carries one since line beside the recount, holding the stated number and the floored recount; a mismatch carries `SINCE_LINE_WRONG` at stage 4 of `pushes_plus_prs`, an unreadable line carries `SINCE_LINE_UNREADABLE` unless something else already mismatched. No exception text reaches stdout, stderr, or the export — only its class name.

Every report closes with the limits, as fixed sentences keyed by codes, printed verbatim from the table in `source_audit/limits.py`. The export carries those limits as codes only:

| Code | Fixed sentence (verbatim) |
|---|---|
| `LIMIT_ONE_FAMILY_ONE_SOURCE` | I audit one number family against one public source. Every other number on the card is unchecked by this run. |
| `LIMIT_FEED_WINDOW` | The public feed holds at most 300 events from the past 30 days, and an event can take up to 6 hours to appear in it. On Nov 1 the feed had already lost pushes inside its own 30 days, so a covered window can still be missing rows the feed never showed. |
| `LIMIT_PUSHES_FEED_ONLY` | Pushes have no independent public source here. For pushes I audit only the path from the feed to the card, not the count against the world. |
| `LIMIT_OTHER_REPOS_FEED_ONLY` | Only the named repo gets the pull list and the activity rows. Every other repo in the count comes from the feed alone. |
| `LIMIT_DELTA_NOT_AUDITED` | Claims that state a change since the parent card are deltas. I count them and do not audit them. |
| `LIMIT_EVIDENCE_AND_DIRECTION` | Fact evidence lists and direction words are not audited. A statement can cite the wrong rows, or say rose for fell, and this run will not catch it. |
| `LIMIT_OTHER_FAMILIES_NOT_TOUCHED` | Screen and calendar numbers are not touched by this run. |
| `LIMIT_UNPARSED_NEEDS_HUMAN` | A paraphrase my parser cannot read is unavailable, not wrong. It needs a human reader. |
| `LIMIT_FEED_MAY_SETTLE` | This snapshot was taken under 6 hours after the window closed. A feed row that has not appeared yet can make this run a mismatch that clears on a later re-run. |

### `--scratch-copy-of` and `--store`

The real store is a live SQLite file in WAL mode with a collector writing to it. `--scratch-copy-of <path>`: I open the source read-only by URI (`file:<path>?mode=ro`, with the path URL-quoted by `urllib.parse.quote`), and take a consistent copy with SQLite's backup API (`sqlite3.Connection.backup`) into a new private temporary folder (`tempfile.mkdtemp`, mode 0700 by default), never a file copy, which would miss what is in the WAL. The copy is audited through a new read-only connection; the folder is removed in every path, including when the backup itself fails. I never write to the source, never create a missing source (a missing source path is `STORE_MISSING`, exit 2, and creates nothing — including no parent folders and no `-wal`/`-shm` sidecars, which the read-only URI already prevents; an existing path that is not a database is `STORE_UNREADABLE`), and never run schema or journal statements on it — no `PRAGMA journal_mode`, no DDL, not even on the copy beyond opening it. I never write to the source, never create a missing source (a missing source path is `STORE_MISSING`, exit 2, and creates nothing — including no parent folders and no `-wal`/`-shm` sidecars, which the read-only URI already prevents), and never run schema or journal statements on it — no `PRAGMA journal_mode`, no DDL, not even on the copy beyond opening it. `--store <path>` opens read-only the same way and is for made-up stores: a missing `--store` path is also `STORE_MISSING`, because silently creating an empty database would audit an empty world and call it a result. Both paths print only what the output rules allow — never the store path itself.

### Negative control

`negative-control` builds made-up stores and a made-up snapshot in a temporary folder with plain SQL using the same table and column names (`events`, `cycles`, `facts` with `origin`, `proposal_results`, `telegram_cards`, and the Ticket 13-shaped `slot_ledger` with `seconds`, `slot_cards`, `slot_card_payloads`), then calls the same comparison code the real run uses (`compare.py`'s stage functions over an opened copy — not a second implementation, or the control proves nothing about the real path). One window, one subject in the SQL (never printed), 8 pull requests in `--repo` all in `last` with an `opened` feed row in the snapshot and the matching pull-list rows. Scenarios:

1. **Clean.** Stored metric 0 in prior, 8 in last (`github.pr.count` 8), a code-form fact statement saying 0 to 8, a delivered claim saying 8 (Ticket 13 tables, delivered row present, chart present for the sum metric with the scenario's own stored numbers). Must PASS for `prs` — so the control cannot pass by always failing.
2. **The historical double count.** The same rows, with the stored metric, the statement and the delivered claim computed by the old rule — counting every `github.pr` row — so the delivered claim also says 16, because the bug would carry through. Must FAIL at stored, fact and delivered, with the source at 8.
3. **Planted duplicate in the store.** One more stored `opened` row for an existing pull request under a new event id, with the stored metric recomputed to 0 in prior, 9 in last. Must FAIL, with the row diagnostics showing one stored row with no public item (`ROWS_NOT_IN_SNAPSHOT` count 1) and the recount at 8, rows counted at 9.
4. **Planted duplicate in the snapshot.** A second `opened` feed row for one pull request under another event id. Must make stage 1 a `mismatch` (`DUPLICATE_IN_SNAPSHOT`) and still count that pull request once (recount 8, not 9).

It prints one line per scenario: `source`, `stored`, `fact` and `delivered` each as earlier/prior/last with `-` for no number, then the verdict, then the expected verdict; the planted snapshot row also prints the duplicate count, and the planted store row the rows-not-in-snapshot count. The final check asserts exact numbers per stage per scenario, not only the verdicts. It exits 0 only when each scenario came out as stated, 1 otherwise. `make audit-control` runs it: `PRE_COMMIT_HOME="$PWD/.git/pre-commit-home" UV_CACHE_DIR="$PWD/.git/uv-cache" uv run python -m source_audit negative-control` (the env prefix applies because it is a `uv` command; the target is defined under Docs below).

Fails if the bounds stop being floored.
- `test_since_line_first_card_and_zero_forms`: a first card bounds the recount 24 hours back floored; the zero forms state 0, bare counts without a header state nothing, and `Since 13:30: code 1.2h.` states 0. Fails if the fallback bound or a form misreads.
- `test_since_line_sentinel_states_nothing_and_leaks_nothing`: a since line holding a sentinel word is unreadable and leaks nothing into lines or export. Fails if a non-form line yields a number or reaches output.
- `test_since_line_fallback_card_reports_nulls`: a fallback-path card reports null for both stated and recounted. Fails if the fallback path invents a number. New: `test_since_line_unreadable_makes_stage_unavailable`, `test_since_line_no_line_leaves_chart_alone`, `test_pick_sorts_on_instant_not_text_across_dst`, and the conformance `test_since_counts_and_line_match_recount_floored` which fails if the bounds stop being floored.
- `test_per_repo_breakdown_and_other_repos`: a stored count that includes a pull request in another repo still matches, and the output names how many rest on the feed alone (`other_repos_feed_only`). Fails if the recount covers `--repo` only or the other-repos count goes.
- `test_stored_fraction_and_float`: stored 8.5 is a `mismatch` and stored 8.0 is a `match`. Fails if a stored value is rounded.
- `test_chart_match_mismatch_null`: the chart comparison in its match, mismatch and null cases for `pushes_plus_prs` at stage 4. Fails if a claim's refs are compared to the sum, or a null chart says anything but `unavailable` with `CHART_MISSING`.
- `test_noop_row_ignored_in_join`: a `noop` row at the slot is ignored in the join and in the snapshot-agreement check; only `proposal` and `fallback` rows join. Fails if a `noop` row joins.
- `test_negative_control_exit_path`: `negative-control` exits 1 when a scenario misbehaves, tested by making the comparison always pass and then always fail, so the control's own exit path is exercised and neither can pass without effect. Fails if the control exits 0 under either forced comparison.

## Known gaps

In my words, so they are on the record and not rediscovered as surprises:

- A wrong number that the feed and the store share in a repo other than `--repo` goes unseen. For those repos the feed is the only source I have, so a feed error and a store error that agree pass stage 1 there; only the per-repo breakdown shows the size of what rests on the feed alone.
- Any push the feed never showed goes unseen. The activity unmatched count can hint at its size in `--repo`, but it is information only and proves nothing about pushes, and in other repos I have not even that.
- A feed row that has not appeared yet can turn a run into a mismatch that clears later. The output tells the reader with `feed_settled: false` and the `LIMIT_FEED_MAY_SETTLE` sentence; it does not, and cannot, tell a late row from a wrong count in the same run. I re-run after the feed settles instead of arguing with the first result.
- The audit reads what the store holds at that moment. A collector writing between my snapshot and my store read can make the two disagree honestly; the row diagnostics (`ROWS_COLLECTED_LATE`) show one direction of that, and a second run is the check on the other.
- Ticket 13's table shapes are checked against the real DDL in `framework/cycle/slot_ledger.py` by the conformance test. The fallback `telegram_cards` path remains for stores without those tables, and stage 4 on it can never say `match`.
- My stage 3 parser reads two tiers and nothing else. Compound spelled-out numbers (`twenty-one`, `eight and a half`), a number buried in a longer sentence with two families' words, and any decimal count all land in the unparsed count. That is the design — a paraphrase I cannot read is `unavailable` and needs a human — but it means a model that writes around the code forms gets less audit, not more, and I should not mistake a run full of `FACT_UNPARSED` for a clean card.
- `pushes` can never PASS, because its stage 1 is `unavailable` by design, and `pushes_plus_prs` can never PASS, because its stage 3 is `unavailable` by design. The sum's chart check at stage 4 is real, but a reader who wants a green verdict has to read `prs`, not the sum's verdict. With `--metric all` the best possible exit is 3; only `--metric prs` can exit 0. I state it here and in the limits so nobody files it as a bug.

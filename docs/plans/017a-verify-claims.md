## Approach

### Key decisions (binding on the implementer; each with its reason)

- **D1, package layout: `framework/verify/` holds `core.py`, `repair.py`, `page_bundle.py`, `__main__.py` and a thin `__init__.py`.** Reason: the CLI needs a `__main__`, the repair loop needs its pinned home, the page bundle builder needs a module runnable as `python -m framework.verify.page_bundle` (D11), and a module named `verify.py` inside a package named `verify` reads badly in tracebacks. Detail: `framework/verify/core.py` defines `MetricRefInput`, `ClaimInput`, `VerifyInput`, `Violation` (this package's own finding type; the name collides with the gate type on purpose, since each package exports its own), `Report`, `LIMITS_NOTE` (D19), the size-cap constants (D2), `VerifyInputError`, `load_input`, `format_report`, `page_render` and `verify_claims`. `framework/verify/__init__.py` re-exports `verify_claims`, `load_input`, `VerifyInput`, `ClaimInput`, `MetricRefInput`, `Violation`, `Report`, `LIMITS_NOTE`, `VerifyInputError`, plus `repair_loop`, `verify_and_repair`, `RepairResult`, `Attempt` from `repair.py`, with `__all__` updated. `framework/verify/__main__.py` defines `main(argv: list[str] | None = None) -> int` and the `if __name__ == "__main__"` guard, so both `python -m framework.verify` and the console script call the same `main`. Nothing else lives in the package.
- **D2, one strict entry for bad input: public types, `VerifyInputError`, `load_input`, exact numbers, blank rules and size caps.** `VerifyInput`, `ClaimInput` and `MetricRefInput` are Pydantic models with `extra="forbid"` at every level, so a typo like `label` for `labels` cannot silently switch a check off. Detail, all binding:
  - **Public error.** New public `VerifyInputError(ValueError)` in `core.py`. `verify_claims` raises it for anything invalid, whichever form it was given (plain `dict`, JSON text, or a `VerifyInput` that fails re-validation). Its message is safe to print and to send back to a model: it never echoes input.
  - **One parser.** New `load_input(raw: str | bytes) -> VerifyInput`, used by `verify_claims` when given text, by the CLI, and by the page (through `page_render`), so all three share one parser. It decodes UTF-8 and accepts a BOM. It parses JSON with `parse_constant` rejecting `NaN`, `Infinity` and `-Infinity`, and with `object_pairs_hook` rejecting duplicate keys. It catches `ValueError` and `RecursionError` and re-raises them as `VerifyInputError`. Reviewer probe, 2026-11-01: `{"a": NaN}` and `{"a": Infinity}` load by default in Python's `json`, `1e999` loads as `inf`, an integer of 5000 digits raises plain `ValueError`, and 200000 opening brackets raise `RecursionError`; each of those must surface as `VerifyInputError`, never as a bare exception or a silent infinity.
  - **Exact numbers.** `MetricRefInput.value` and every `metrics` value are `Annotated[int | float, Field(strict=True)]` plus a finite check. Strings, booleans and null are bad input. Reviewer probe, 2026-11-01: lax pydantic turns `"3"` into `3.0` and `true` into `1.0`, and `float(9007199254740993) == float(9007199254740992)`, so converting to float passes a false number. Ints stay ints, and every comparison stays `Decimal(str(x))`.
  - **Shape rules, each bad input (`VerifyInputError`, CLI exit 2).** Not an object; missing or unknown key at any level; empty `claims` (a pass over nothing is a false pass, and an adapter bug looks exactly like this, so this replaces the earlier "an empty claims list passes" reading); duplicate claim ids (a claim id is the only locator in the report, and the gate rejects duplicate ids too, so this replaces the earlier "caller's problem" reading); blank `id`, `text`, fact id, fact value, metric id, label word, deny term or advice word, where blank means empty after stripping; an empty word list in `labels` (bad input, not "no entry"); a malformed `order` (D7).
  - **Size caps.** Six named constants in `core.py`: `MAX_CLAIM_TEXT_CHARS = 2_000` (per-claim text at most 2,000 characters), `MAX_TOTAL_CLAIM_TEXT_CHARS = 100_000` (total claim text at most 100,000 characters), `MAX_INPUT_BYTES = 10_000_000` (input at most 10,000,000 bytes; the CLI and `load_input` read at most one byte past the cap), `MAX_CLAIMS = 5_000` (at most 5,000 claims), `MAX_REFS_PER_CLAIM = 100` (at most 100 `metric_refs` per claim), `MAX_TERMS = 1_000` (at most 1,000 entries in each of `deny_terms` and `advice_words`, when present). Each breach is bad input with a message naming the limit. The first three caps bound the regex time per claim, but a long list still multiplies the work: the deny-term arm collapses every term on every claim, and `ref_backs_token` runs per number token per ref, so the last three caps bound that multiplication. Reason, with the measured numbers: reviewer probe, 2026-11-01, native Python, worst-case input (`a-a-a-...` through the gate's secret regexes and `aaaa...` through the identifier regexes in `framework/briefing/numbers.py`): 2,000 characters 0.06 s, 4,000 characters 0.25 s, 10,000 characters 1.6 s, 40,000 characters 21 s — quadratic. A single 5 MB token would run for days. Those regexes belong to the gate and this ticket does not change them, so the caps go at the verify boundary. Worst case under these caps is about 3.5 s natively. A 5 MB input whose bulk is long fact strings still passes through to a clean report, because the caps bind claim text and total bytes, not fact-string length beyond the byte cap.
  - **Types.** `ClaimInput` is `id`, `text`, `fact_ids: list` default empty, `metric_refs: list[MetricRefInput]` default empty, with the blank rules above. `MetricRefInput` is `metric_id` plus the strict `value` above. `VerifyInput` is `claims: list[ClaimInput]`, `facts: dict[str, str]`, `metrics: dict[str, int | float]` (strict per value), and optional `labels: dict[str, list[str]] | None = None`, `order: list[list[str]] | None = None` (D7), `deny_terms: list[str] | None = None`, `advice_words: list[str] | None = None`. String fields reject blank-after-strip values; a local non-blank string annotation in `core.py` carries that rule (the reason is not import avoidance — see D3 for the true import picture).
  - **Safe messages.** Validation errors are rendered with `exc.errors(include_input=False, include_url=False, include_context=False)`. In a printed location, keep integers and the schema's own field names; replace any other part with `<key>`, because a dict key is caller content and may be private. Print at most 5 errors, then a count of the rest.
  - **Report.** `Violation` is a frozen dataclass `(code: str, claim_id: str, message: str)`. `Report` is a frozen dataclass `(violations: tuple[Violation, ...], limits: str)` with a `passed` property true exactly when `violations` is empty, mirroring `GateResult.passed` at [framework/briefing/gate.py:222-225](../../framework/briefing/gate.py), and a `feedback()` method (D10). `LIMITS_NOTE` is the D19 constant, pinned so the API, the CLI, the page and the README quote the same words. Violation order is deterministic: claims in input order, and inside one claim the check order in D5, de-duplicated per D5.
- **D3, gate edits are strictly additive; the import picture is stated truly.** No existing function body and no existing call site in `framework/briefing/gate.py` changes, and `framework/briefing/__init__.py` is not touched. `_collapse`, `_contains_token`, `_ref_backs_token`, `text_check_codes` and `_binding_violations` stay exactly as they are. Reason: Ticket 10b is rewriting text rules in `gate.py` and `numbers.py` right now, and the coordinator's instruction is that this ticket only exposes public functions. One block is appended at the end of `gate.py`, after `_finish` ([framework/briefing/gate.py:959-967](../../framework/briefing/gate.py)), holding exactly:
  - `collapse_text(text)` and `contains_token(text, literal)` as thin public wrappers over `_collapse` ([framework/briefing/gate.py:274-275](../../framework/briefing/gate.py)) and `_contains_token` ([framework/briefing/gate.py:278-291](../../framework/briefing/gate.py));
  - `ref_backs_token(value, places, token_abs)` wrapping `_ref_backs_token` ([framework/briefing/gate.py:537-540](../../framework/briefing/gate.py)) and returning `False` on `decimal.InvalidOperation` — reviewer probe, 2026-11-01: `_ref_backs_token(1e30, 0, ...)`, `(1.0, 28, ...)` and `(1e27, 2, ...)` all raise it, so fail closed: no backing means a violation, never a traceback;
  - `word_list_hit(text, words) -> bool` using the same normalisation as the advice arm at [framework/briefing/gate.py:145-148](../../framework/briefing/gate.py) (collapse, curly-apostrophe normalisation, whole-token match);
  - `direction_sides(text, *, exclude_words) -> frozenset[str]` reading `_DIRECTION_TOKEN_RE`, `_UP_WORDS` and `_DOWN_WORDS` as [framework/briefing/gate.py:658-664](../../framework/briefing/gate.py) does, returning a subset of `{"up", "down"}`;
  - `ADVICE_WORDS`, a public tuple of `_ADVICE_SINGLES` plus `_ADVICE_PHRASES` ([framework/briefing/gate.py:55-84](../../framework/briefing/gate.py)), used only by the parity test.
  Import truth, replacing the earlier wrong reasons: importing `framework.schemas.base` runs `framework/schemas/__init__.py`, which imports events and manifest; importing `framework.briefing.numbers` runs `framework/briefing/__init__.py`, which imports commitments and context; importing `framework.verify.repair` runs `framework/verify/__init__.py`. The import closure therefore includes those modules. They do no I/O and read no env at import, and nothing in `framework/verify/` calls them at runtime beyond the pinned checker surface. Two tests pin this: a source-level import test over `framework/verify/*.py` (the package may import only `framework.verify` itself, `framework.briefing.gate`, `framework.briefing.numbers`, `framework.schemas.base`, pydantic and the standard library — test files, which are outside the package, may also import `framework.briefing.labels` and `framework.briefing.gate`'s `evaluate_briefing` for parity; `repair.py` is narrower still, D10), and a subprocess test that imports `framework.verify` fresh and asserts no `sqlite3`, `jinja2`, `inspect_ai`, `icalendar`, `framework.store`, `framework.collectors` or `framework.blocks` in `sys.modules`. `socket` is deliberately not in that assertion: importing the closure loads `socket` transitively through the `email` package chain that pydantic's datetime handling pulls in once `framework/schemas/__init__.py` imports the event schemas, even though no verify code imports it, so asserting its absence would fail on correct code. Checked in this session with the project interpreter: bare `import pydantic` loads neither `socket` nor `sqlite3`; `import framework.schemas.base` loads `socket` and not `sqlite3`, `jinja2`, `inspect_ai` or `icalendar`.
- **D4, text checks: reuse `text_check_codes` as-is for secrets, contact and private terms; advice runs only from the caller's list.** `core.py` calls the already public `text_check_codes(text, private_terms=terms)` ([framework/briefing/gate.py:133-168](../../framework/briefing/gate.py)) and keeps only `L1_SECRET`, `L1_PII` and `L1_PRIVATE_TERM` from its result. No new text helpers are added for those. Rules that later land in `text_check_codes` then reach `verify_claims` with no edit here. `deny_terms`, when present, is passed as `private_terms`; when absent, no private-term check runs beyond what the caller declared (pass `()`). Advice runs only from the caller's `advice_words`, through the appended `word_list_hit`, and emits `L1_ADVICE`; when `advice_words` is absent, no advice check runs at all and the gate's pinned list is never applied to a stranger's text. Reason: my pinned advice list suits my product, not everyone's, and the brief pins default none, so the caller declares the list or the check stays off. The remaining small duplicates (for example the direction scan behind `direction_sides`) are exactly what the parity test (D8) catches; a gate rule change therefore shows up as a parity failure, and the plan says so plainly rather than pretending the split helpers prevent drift.
- **D5, the per-claim check order, code set and de-duplication are pinned.** For each claim, in this order: (1) `L1B_CLAIM_WITHOUT_EVIDENCE` when the claim has no `fact_ids` and no `metric_refs`, matching the gate arm at [framework/briefing/gate.py:732-740](../../framework/briefing/gate.py); (2) `L1B_UNKNOWN_FACT` for each cited fact id absent from `facts`, matching [framework/briefing/gate.py:741-751](../../framework/briefing/gate.py) minus its subject arm, because public facts are plain strings (`"f1": "any string"`) with no subject to compare; (3) `L1B_UNKNOWN_METRIC` for each ref whose `metric_id` is absent from `metrics`, and `L1B_METRIC_VALUE_MISMATCH` for each ref present whose value differs, compared with `Decimal(str(...))` equality like the gate at [framework/briefing/gate.py:768-788](../../framework/briefing/gate.py); (4) `L1B_NUMBER_WITHOUT_METRIC_REF` for each number token from `extract_number_tokens(claim.text, known_ids)` ([framework/briefing/numbers.py:147-191](../../framework/briefing/numbers.py)) that no ref backs, where `known_ids` is the claim's fact ids plus its ref metric ids, matching [framework/briefing/gate.py:752-764](../../framework/briefing/gate.py) and backing by the appended `ref_backs_token` (absolute value, rounded at the token's decimal places, fail-closed on `InvalidOperation` per D3); (5) the binding rule (D6, D7: label, too-many and direction in that order); (6) `text_check_codes` keeping only `L1_SECRET`, `L1_PII`, `L1_PRIVATE_TERM`, then advice via `word_list_hit` emitting `L1_ADVICE` (D4), one violation per claim per code from the text arms. Violations de-duplicate per `(code, claim_id)`, keeping first-seen order, the same rule as `_finish` at [framework/briefing/gate.py:959-967](../../framework/briefing/gate.py) (which de-duplicates per `(code, location)`; here the location is the claim id). Without this, two unknown facts on one claim give a different code multiset from the gate. A claim may collect several codes; the report keeps input claim order. Facts hold any string and are never parsed; a fact string that looks like a number is still just a cited source. Metrics values compare as numbers through `Decimal(str(x))`, so `3` and `3.0` are the same value, while `9007199254740993` as an int stays distinct from `9007199254740992` (D2).
- **D6, one binding rule for labels, mirroring the gate's shape; order is declared on the reference side (with D7).** New optional top-level input field `order: list[list[str]] | None`. Each inner list is one series of metric ids, earliest first, at least 2 ids. An id may appear in at most one series and at most once; a violation of that is bad input (D2). The docs wording is: each inner list is one series, earliest first. `claims` is the agent's output, the thing under test, so order is never taken from `metric_refs`: a model that lists refs in sentence order would make "Deploys fell from 9 to 5" with refs `[deploys.nov=9, deploys.oct=5]` pass when the truth is 5 then 9, while the gate rejects this shape because it derives order from the metric id. For each claim, the bound refs are the refs whose `metric_id` has a `labels` entry or appears in `order`. Then, in this order:
  1. No bound refs: no label or direction check. A generic id with no label entry is not an error.
  2. Two or more bound refs, and they are not all distinct ids inside one `order` series: emit `L1B_TOO_MANY_METRICS` with the message `claim cites several metrics outside one declared series; split the claim or list them in order`, and skip steps 3 and 4 for this claim, the same early return as [framework/briefing/gate.py:615-624](../../framework/briefing/gate.py). Without this, "Pushes reached 5 while the feed held 3" with true refs pushes=3 and feed=5 passes `verify_claims` while the gate rejects it — a swapped-value false pass. Do not use "the refs share a label word" as the eligibility test: `deploys.oct` and `errors.oct` can both list `october`, and the swap gets through.
  3. Label: for each bound ref with a `labels` entry, every listed word must appear in the claim text as a whole word, case-insensitive, through the gate's token match (`contains_token` on collapsed text). The brief says "words that must appear", and any-of was a silent weakening: `tickets.closed: ["closed", "tickets"]` would pass "Opened 12 tickets". One `L1B_METRIC_LABEL_MISSING` per claim (message: `claim does not name the cited metric`). The docs say alternatives can't be expressed, so pick the form the agent writes, and that whole-word matching means `push` does not match `pushes`. A ref whose id has no entry and no `order` entry is not bound and is skipped; a `labels` entry for an id nobody cites is ignored; an empty word list is bad input (D2), not "no entry".
  4. Direction: scan the claim text for the gate's direction words through `direction_sides`, excluding the tokens of every label word of every bound ref, as the gate does at [framework/briefing/gate.py:658-664](../../framework/briefing/gate.py). Words from both sides emit `L1B_DIRECTION_MISMATCH`. One side with exactly one bound ref emits `L1B_DIRECTION_MISMATCH`, the same as [framework/briefing/gate.py:690-698](../../framework/briefing/gate.py); there is no single-ref carve-out. One side with two or more bound refs (which step 2 has already ensured sit inside one `order` series): sort them by their position in the series, compute consecutive differences with `Decimal(str(...))`, and require all positive for up, all negative for down, otherwise `L1B_DIRECTION_MISMATCH`, the same as [framework/briefing/gate.py:700-723](../../framework/briefing/gate.py). No direction word passes.
  `L1B_TOO_MANY_METRICS` joins the public code table (see the table below). The public API still never emits `L1B_METRIC_LABEL_UNKNOWN` or `L1B_PERIOD_WORD_MISSING`. Reason the gate's fail-closed family rule stays Briefing-only: the gate fails closed on an unknown family ([framework/briefing/labels.py:48-59](../../framework/briefing/labels.py) returns `None`, and [framework/briefing/gate.py:563-572](../../framework/briefing/gate.py) emits `L1B_METRIC_LABEL_UNKNOWN`) because my product knows its metric families; a stranger's ids are generic, and the brief states a generic id with no label entry is not an error. The public checker therefore never calls `metric_label_binding` on caller ids at runtime.
- **D7, direction follows the declared `order`, never `metric_refs` order.** This decision is the direction half of D6 step 4, pinned separately because the earlier reading (caller order is `metric_refs` order, single ref exempt) is withdrawn in full. ## Risks

- **The parity claim is narrower than it sounds.** The public shape cannot say sections, actions, windows, parents or raw refs, so D8 parity covers only the pinned expressible subset (18 mutants, 17 known-good) and says so in the test, with every excluded case named with a one-line reason. The risk is a reader hearing "same verdicts" without the qualifier; the README section quotes only the limits note, and the session note states the subset plainly.
- **A false pass through shape, not wording.** The binding rule (D6) is the ticket's core risk and is pinned against the measured shapes: order from `metric_refs` (sentence-order refs), any-of label words, a shared-label-word eligibility test, and a single-ref direction carve-out each let a gate-rejected claim pass. D6 and D7 remove all four; the named order test and the M33/M36 parity cases keep them removed.
- **Caller word lists cut both ways.** Whole-word matching on caller `deny_terms` and `advice_words` inherits the gate's limits: `push` does not match `pushes`, a term inside a longer word will not match for short terms, and wording outside the caller's list passes. That is the caller's list doing what it says, and the examples show a list that works. Alternatives can't be expressed in `labels`, so the docs tell callers to pick the form the agent writes.
- **The stale bundle test will bite other tickets.** Any merge that changes `framework/briefing/`, `framework/schemas/` or `framework/verify/` without rerunning `make verify-page` fails `tests/test_verify_page.py`. That is the intended staleness, but it crosses ticket boundaries while four tickets are merging. Tell the coordinator: whoever merges second reruns `make verify-page` (Steps, rebase checkpoint).
- **The page runs an older pydantic than the CLI.** Reviewer probe, 2026-11-01: Pyodide 0.27.7 carries pydantic 2.10.5; `uv.lock` has pydantic 2.14.1. The implementation must not use pydantic features newer than 2.10, and a page-only validation difference would show up first as a browser-only verdict difference, which only the reviewer browser pass (AT10) can catch.
- **Pyodide load is pinned, not re-probed.** D12 is pinned from the reviewer probe in headless Chrome (reviewer probe, 2026-11-01); the implementation sandbox has no browser. If a later Pyodide or jsDelivr change breaks the pinned load order, the page fails to enable Run and says nothing was sent; the fix is a new reviewer probe and a one-line version bump, not an implementation-time guess.
- **Size caps trade completeness for a bounded worst case.** The caps (D2) are set from the measured quadratic timings (reviewer probe, 2026-11-01). A legitimate claim text over 2,000 characters is bad input, not a slow pass; the message names the limit so the caller can split the claim. Long fact strings are not capped beyond the 10 MB byte cap, so a 5 MB fact-heavy input still reports cleanly.
- **Packaging metadata is new to this repo.** No build backend is pinned today, so the first reviewer `uv build` (AT7) may surface discovery choices. D13 pins hatchling and reports the `uv.lock` diff; if the first build shows hatchling cannot package this tree as configured, the reviewer reports the build output rather than swapping backends silently. No test builds a wheel, so this cannot break `make check` on a fresh cache.
- **Dependency reshaping could break a repo command.** Moving `inspect-ai`, `icalendar`, `recurring_ical-events` and `jinja2` into the `app` group (D20) is safe only while `default-groups = ["dev", "app"]` holds; AT4's `inspect_ai` resolution check and the unchanged `make check`/`make eval` runs are the guard.
- **Ticket 11 timing.** `framework/proposal/` is not on `main` today. If Ticket 11 lands first with its own loop, D10's rule still holds: one loop, re-exported, with this ticket's tests pointed at the surviving definition.
- **Ticket 10b timing.** Ticket 10b is rewriting text rules in `gate.py` and `numbers.py` and adding cases to `evals/briefing_cases.py`. The appended-block rule (D18) and the pinned parity lists (D8) are designed to fail loudly on that merge, not to absorb it silently; the rebase checkpoint (Steps) is where the normalisation hook lands and the parity test reruns.
- **Pages goes live at merge, the README link a few minutes later.** The coordinator enables Pages at merge, and the README (D16) links the page address with no not-live-yet clause, so for the few minutes between merge and first Pages deploy the link does not resolve yet. Accepted, because a conditional clause would go stale the same day.

## Amendments after code review (2026-11-01)

Findings from Claude Code's review of the first build, applied in the fix session. Each overrides the matching text above. Numbers are reviewer probes on 2026-11-01.

- A13, `facts` and `metrics` are required, as D2 already says. The first build gave them empty defaults, and the hostile rows hid that by using empty `claims`.
- A14, a claim can't name a series member it doesn't cite. A differential fuzz over 39,222 generated claims found one class where the gate rejected and `verify_claims` passed: a claim citing one period while naming another, such as "Pushes reached 5 in last and prior". The input shape can say this through `order` and `labels`, so by this plan's rule it must agree. D6 step 3 gains: if a bound ref sits in an `order` series, a word listed for an uncited member of that series, and for no bound ref on the claim, must not appear in the claim; it emits `L1B_METRIC_LABEL_MISSING` with the message `claim names another metric in its series without citing it`. D8's translator declares the whole family series over three periods with labels for every member, so parity covers it. M38 stays excluded, since a metric with no period belongs to no series.
- A15, three more caps: `MAX_LABEL_WORDS = 10`, `MAX_SERIES_IDS = 366`, `MAX_JSON_DEPTH = 64`, plus a series index built once per run and `known_ids` as a set. 5,000 claims against a series of 400,000 ids ran 85 s natively, and 100,000 nested brackets gave a fatal Pyodide error in the browser because the JS stack ran out first.
- A16, every failure is `VerifyInputError`, including a lone surrogate in a `str` input and an int too large to stringify through the dict API. Messages use plain words in place of pydantic type names.
- A17, the CLI treats an unknown flag as a usage error (exit 2), works with a replaced `sys.stdout`, and stays quiet on a closed pipe.
- A18, page: an example button fills the input and runs; the page names the need for your own records and links the field table and the adapter recipe.
- A19, examples: `input-fixed.json` corrects the claim, because changing the records to match the agent is the exact mistake this tool exists to catch. Foreign statements carry `note_refs`, because a fact link no field states could only be guessed. All example JSON is pretty-printed.
- A20, adapter recipe: the first command used a flag that doesn't exist (`--approval never`), and paths that only resolved from the folder it said not to run in. The prompt now says the run is headless, names its input files, keeps the mapping in one table, and returns what it could not confirm under `unconfirmed_mappings`, because a headless run can't ask a person anything. D14's "one function plus its tests and nothing else" becomes one function, the table and the exception.
- A21, D19's list grows: a metric with no `labels` or `order` entry gets no label or direction check, rounding and sign, and a worked example of the reversed sentence.
- A22, the first depth check was quadratic on a string that never closes: 0.4 MB of escaped quotes ran past 25 s. An unclosed string now runs to the end of the text, so nothing restarts.
- A23, lists stop at their first bad item (`fail_fast`), and error lines de-duplicate through a set. 4.9 million bad items at the input cap cost about 4 GB, and 100,000 took 22 s. A stranger fixing a broken file now sees the first bad item in each list, not all of them.
- A24, labels are collapsed once and indexed by series, so a claim walks only its own series. 100,000 series against 5,000 claims ran past 25 s.
- A25, two more caps: `MAX_WORD_CHARS = 100` and `MAX_CLAIM_ID_CHARS = 200`. A 4 MB label word against 5,000 claims ran past 25 s.
- A26, every code from `text_check_codes` reaches the report except advice, which runs on the caller's list. The first build kept a fixed list, so a new gate text rule would have passed here silently.
- A27, the CLI handles closed streams, a directory on stdin and Ctrl-C without a traceback.
- A28, each distinct word is searched once per claim. `contains_token` restarts at each occurrence, so 3,660 sibling word entries of `a` runs against 50 long claims ran 43 s.
- A29, the recipe's command gains `--no-foreign-personal-context`, because without it Muse Code can read a person's rules and skills from other tools and send them to the API.

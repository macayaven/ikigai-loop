## Decisions (binding on both implementation sessions; each with its reason)

### Shared

- **SD1 — Two new packages, no edits to the card path.** Slice A creates `framework/rater/`; Slice B creates `framework/metrics/`. Neither touches `framework/cycle/`, `framework/telegram/`, `framework/voice/`, `framework/proposal/` (except the one optional-argument change in BD3), `framework/briefing/`, or `framework/learner/`. Reason: both slices are read-only consumers of the store; keeping them out of the send path means the live run cannot be broken by reporting code, and Slice A can ship before Slice B is designed in code.
- **SD2 — The store is read only through a backup copy.** Both commands open the real DB with `sqlite3.connect("file:<path>?mode=ro", uri=True)`, copy it with sqlite's backup API into a temp file, work only on the copy, and delete the copy plus its `-wal`/`-shm` afterwards — exactly the dry-run pattern at [framework/cycle/orchestrator.py:766-780](../../framework/cycle/orchestrator.py) and [framework/cycle/orchestrator.py:808-818](../../framework/cycle/orchestrator.py). All store classes are then opened on the copy path. Reason: the live poller and timers write the real file; a reporting run must never take a write lock on it or observe a half-written slot, and the project already trusts this pattern.
- **SD3 — Explicit paths, product env names.** Every command takes `--db <path>` explicitly (no default; a missing file is a refusal, exit 2). The subject id comes from `IKIGAI_SUBJECT_ID` and the commitments file from `IKIGAI_COMMITMENTS_FILE`, read the way `run-slot` reads them: required, no placeholder default ([framework/cycle/__main__.py:628-631](../../framework/cycle/__main__.py) refuses when `IKIGAI_SUBJECT_ID` is empty; commitments load fail-closed at [framework/briefing/commitments.py:45-100](../../framework/briefing/commitments.py)). Reason: a report run against the wrong subject or the synthetic placeholder would silently produce plausible wrong numbers; the brief pins "the same variables the product reads", and the slot path is the strictest reader. (The Telegram poller's placeholder default at [framework/collectors/common.py:90-92](../../framework/collectors/common.py) is deliberately not copied; see Contradictions C6.)
- **SD4 — Refusal means counts and codes only, nothing partial written.** On any refusal (private-term hit, unavailable terms/commitments, bad output path, mismatched key/result), the command prints closed `key=value` counts/codes, writes no page, no key and no export, and exits 1 (data refusal) or 2 (usage/missing env, bad arguments). Reason: a half-written pack that the rater has already seen cannot be un-seen; all-or-nothing keeps the denominator honest.
- **SD5 — Determinism.** Sorting, shuffling and hashing use only pinned inputs (seed, sorted keys, canonical JSON with `sort_keys=True`). No wall clock enters any count except the explicitly recorded `cut`/`as_of` instants. Reason: "every number regenerates from logs with one committed command" ([docs/PREREG.md:28](../PREREG.md)); a hidden clock makes two runs disagree.

### Slice A

- **AD1 — Delivered is a union of three signals; everything else is a named disagreement (A2).** A card id is *delivered* iff any of: (i) a `slot_ledger` row `step='send', outcome='delivered'` names it (slot path, [framework/cycle/orchestrator.py:1935-1941](../../framework/cycle/orchestrator.py)); (ii) a `voice_notes` row has `new_card_id` equal to it (voice path, set only after `send_card` returned a validated message id, [framework/voice/worker.py:1932-1934](../../framework/voice/worker.py)); (iii) a `telegram_card_messages` row names it (written by `send_card` only after Telegram returned an integer `message_id`, [framework/telegram/service.py:155-162](../../framework/telegram/service.py)). The payload tables are **not** delivery signals: `slot_card_payloads` is written at the card step before any send, and `telegram_cards` is written by `send_card` before the photo goes out ([framework/telegram/service.py:140-142](../../framework/telegram/service.py)). The generator cross-checks the signals and prints each of these counts on its own line: `delivery_slot_without_message_row`, `delivery_voice_without_message_row`, `delivery_message_without_send_record`, and `delivery_unknown_cards` (cards present in `slot_card_payloads` or `telegram_cards` with no delivered signal, including `DELIVERY_UNKNOWN`/never-sent cards). A delivery-unknown card is not delivered and its statements never enter the pack. Reason: each signal alone has a hole — the message-row write is swallowed on store error, a slot's `delivered` row can be blocked, the voice row is written in a second step — so the union is the only definition that counts every card that demonstrably reached the phone, and the disagreement lines keep the holes visible instead of silent. This join is a pure function `delivered_cards(copy) -> DeliveredJoin` in `framework/rater/delivery.py`, reused by Slice B (BD2). **Pack scope (Slice A owns this; Slice B reuses it, BD2):** the pack takes only delivered cards at the run's slots. The run's slots are the instants from the first card `2026-11-02T13:30` Europe/Madrid to the last card `2026-11-04T18:00` Europe/Madrid in the Design ([docs/PREREG.md:19](../PREREG.md)) whose Madrid time is in `SLOT_TIMES` ([framework/cycle/orchestrator.py:117-123](../../framework/cycle/orchestrator.py)) — 13 instants. `framework/rater/delivery.py` pins them as `run_slots() -> tuple[datetime, ...]` (built from `SLOT_TIMES`, read-only, plus those two bounds; no Slice B code involved), and the pack keeps only delivered cards whose `slot` is in that tuple. A delivered card at any other slot is counted on its own line (`delivered_cards_outside_run`) and left out of the pack. Reason: Slice A must not depend on Slice B, so the run scope lives where the pack is built; defining it once and reusing it stops the pack and the report from counting different runs.
- **AD2 — Sentences are the claim pieces of `Card.statements`, recovered per card and side (A1, A3).** For each delivered card, load the `Card` from `slot_card_payloads.card_json` (slot path) or `telegram_cards.card_json` (voice-only cards); group `card.statements` under the side header that precedes them: headers are regenerated from the card's own sides as `"<letter> · <display>"` from each side's `letter` and `profile` (the display built at [framework/cycle/card_build.py:59-71](../../framework/cycle/card_build.py), where `display` is `_display_name(profile_id)` at [framework/cycle/card_build.py:388-389](../../framework/cycle/card_build.py)), never by guessing text shape, and each following non-header piece belongs to that side until the next header. A piece before the first recognised header, or a side with no `slot_cards` row to name its profile, is unmatched (AD3). A side with no grouped pieces (a fallback side, which contributes no statements by construction at [framework/cycle/card_build.py:384-405](../../framework/cycle/card_build.py)) contributes nothing and is not counted as unmatched or ambiguous. The `since_line` is not in `statements` ([framework/telegram/models.py:138-140](../../framework/telegram/models.py)) and is never a sentence; commitment titles and times live on `Proposal` sides, not in `statements`, and are never claims ([docs/PREREG.md:146](../PREREG.md)). Reason: `build_statements` is exactly what the person saw via Why?, so it — not the briefing sections — defines the denominator; claims a briefing held beyond the 3-per-side cap never reached a card and are excluded.
- **AD3 — Evidence recovery regenerates each side from every stored proposal result for that slot and profile (A3).** For a delivered card, group its pieces by side (AD2); each side's profile comes from its `slot_cards` row for that card id and letter (slot cards) or, for a corrected card, from its copied/changed `slot_cards` rows saved by the voice worker ([framework/voice/worker.py:1717-1777](../../framework/voice/worker.py)). For that side, consider **every** stored proposal result with `kind='proposal'` for that card's slot and that side's profile — not the latest row — read with the rater's own `SELECT rowid, proposal_key, cycle_id, run, profile_id, briefing_json FROM proposal_results WHERE slot = ? AND profile_id = ? AND kind = 'proposal' ORDER BY rowid` on the copy (`results_for_slot` returns only the latest row per profile at [framework/store/proposal_store.py:426-493](../../framework/store/proposal_store.py), which is the reading that loses the original briefing after a correction re-proposes a side). A row **qualifies** when `build_statements(((letter, display, row.briefing),))` — the one side's letter, its display name from the card's own side, and that row's briefing, at [framework/cycle/card_build.py:59-86](../../framework/cycle/card_build.py) — regenerates exactly that side's pieces: the regenerated header plus claim pieces equal the grouped pieces for that side, in order. The **earliest qualifying row by `rowid`** is the source, and its `proposal_key` and its claims' ids give the identity of AD4; the claims corresponding to the side's pieces (in `build_statements` order) supply the evidence `(fact_ids, metric_refs, section_type)`. If qualifying rows disagree on the evidence `(fact_ids, metric_refs)` of any corresponding claim, the side is **ambiguous**: all its pieces are left out and counted (`statements_ambiguous`). If no row qualifies, the side is **unmatched**: all its pieces are left out and counted (`statements_unmatched`). Fact statements come from `FactStore.fetch_facts(source.cycle_id, source.run)` by fact id ([framework/store/fact_store.py:367-395](../../framework/store/fact_store.py)); a cited fact id missing from that cycle is counted (`facts_missing`) and the claim is left out — never guessed. A delivered card with a payload but no `slot_cards` rows for a side leaves that side unmatched by the same rule. Reason: statements carry no claim ids ([framework/telegram/models.py:136-142](../../framework/telegram/models.py)), so regeneration against every candidate briefing is the only non-invented join that survives a re-proposal; a voice correction re-proposes a side ([framework/voice/worker.py:1058-1138](../../framework/voice/worker.py)) and the corrected card is rebuilt from the newest rows ([framework/voice/worker.py:1263-1367](../../framework/voice/worker.py)), so the latest row for a profile is the new result, not the briefing the original card was built from.
- **AD4 — Source-claim identity is `(proposal_key, claim_id)` of AD3's earliest qualifying row, and dedup falls out of it (A3).** The generator reads the copy with its own `SELECT`s where it needs `proposal_key` (`results_for_slot` discards it at [framework/store/proposal_store.py:447-461](../../framework/store/proposal_store.py), so the rater module selects `rowid, proposal_key, cycle_id, run, profile_id, briefing_json` itself — read-only, on the copy). Because AD3 always picks the earliest qualifying row, the unchanged side of a corrected card and the original card resolve to the same row, so they yield the same `(proposal_key, claim_id)` and the claim is rated once; the key records `delivered_cards_shown` = the number of distinct delivered card ids whose statements contain that source claim. The original card's claims also survive its side being re-proposed: the original side's pieces still qualify against the original (earliest) row even though a newer row exists for that profile. A changed side on the corrected card whose pieces qualify only against its new row is a new source claim under that row's key; if its pieces and evidence also qualify against the earlier row, AD3's earliest rule resolves it to the earlier row and it is likewise rated once. Reason: the brief's "same source claim … counts once" follows from the earliest-qualifying rule without a special corrected-card case, and no delivered card loses its claims because a later row superseded its briefing.
- **AD5 — The split is one pure function with fixed rules, from the prompt's rules, never from real data (A4).** `split_atomic(statement: str) -> SplitOutcome` in `framework/rater/split.py`, pure, no I/O. `SplitOutcome` holds the atomic claims plus closed counters. Rules, applied in this order per statement:
  1. **Sentence split.** Split at sentence boundaries (`.`, `!`, `?` followed by whitespace or end), except a period between two digits is never a boundary (`3.95` stays whole). Terminal punctuation is normalised so each atomic claim ends with exactly one `.`.
  2. **Semicolon split.** Each resulting piece is split at `;` the same way.
  3. **`", so …"` pick clause.** If a piece contains `, so ` (lowercase `so` after a comma, the pinned shape at [framework/proposal/prompt.py:114](../../framework/proposal/prompt.py)), look at the clause after the first `, so `: if it contains **no digit character**, cut it — the prefix is the atomic claim, and `so_clauses_cut` rises by one (the clause names my pick from my list; it is not a factual claim). If it contains a digit, keep the statement whole and count `so_clauses_kept_with_digit` on its own line.
  4. **Series/comparison stays one.** A piece naming two or three of the period words `earlier|prior|last` is one claim however it is joined (a comparison or series of one metric across periods says how one quantity moved; [framework/proposal/prompt.py:122](../../framework/proposal/prompt.py)).
  5. **Possibly-compound `and`.** Every other piece that holds the word `and` and that rule 4 did not keep as a series is left whole and counted on its own line as `possibly_compound`, whatever its numbers. It is still rated — the rater judges the whole sentence — it is never split by guessing. (A fact-only claim holds no digit — the prompt's rule at [framework/proposal/prompt.py:114-129](../../framework/proposal/prompt.py) — so a two-number condition would never count a compound fact-only sentence; the word `and` alone is the trigger.)
  Every atomic claim inherits the full evidence `(fact_ids, metric_refs, section_type)` of its source statement, plus its `atomic_index` within the statement. Tests pin each rule, including a decimal (`3.95`), a two-sentence statement, a `", so"` clause with and without a digit, and a three-period series. Reason: the rules are fixed from the prompt's claim rules and made-up drafts, drafted without reading any real claim (A12 says so in PREREG), they mirror the one-metric-family-per-claim discipline the gate already binds, and every judgement call the splitter cannot make deterministically is surfaced as a count instead of hidden.
- **AD6 — Evidence is rendered in plain words from the bindings, not from claim text (A5).** For each atomic claim the page shows the sentence, then under it: every cited fact's `statement` from the facts table, and every cited metric as one line built as: `<what was counted> · <period phrase> · <value><unit phrase>`. What was counted names the thing in plain words per family (the binding's `family` at [framework/briefing/labels.py:48-94](../../framework/briefing/labels.py)), never the shortest label alone — the shortest label gives `push`, `pr` and `feed`, which a rater can't read: `screen_hours.<category>` → `<category word> screen time` (the category word is the shortest label, ties reverse-alphabetical first as at [framework/proposal/prompt.py:105-107](../../framework/proposal/prompt.py)); `tag_hours.<tag>` → `calendar time tagged <tag word>` (the tag word is the shortest tag label, i.e. the tag without its `iki-` prefix when present, [framework/briefing/labels.py:37-45](../../framework/briefing/labels.py)); `pushes`/`github.push.count` → `pushes`; `prs`/`github.pr.count` → `pull requests`; `calendar.busy_hours` → `busy calendar time`; `feed.item.count[.<source>]` → `feed items`; `cancelled.<tag>` (`requires_cancel=True`, [framework/briefing/labels.py:89-93](../../framework/briefing/labels.py)) → `cancelled blocks tagged <tag word>`. Then the period phrase: `in the earlier/prior/last period` from the binding's `period`, or `across the whole three-day window` when `period` is `None`. Then the value: `display_value(ref.value)` ([framework/proposal/prompt.py:37-47](../../framework/proposal/prompt.py)) — assembly filled it from the data, so showing it shows the data, not the model's words — with its unit: ` hours` when the binding's `family` is `screen_hours.*`, `tag_hours.*` or `calendar.busy_hours` (the ids that count hours, [framework/proposal/prompt.py:114-129](../../framework/proposal/prompt.py)); the count families (`pushes`, `pull requests`, `feed items`, `cancelled blocks …`) carry no further unit word, the counted noun being the unit. A claim whose section is `since_last` renders each ref as: `<what was counted> · <period phrase> · <signed change><unit phrase> since the previous card`, where the signed change is `+<display_value(value)>` on a rise, `-<display_value(abs(value))>` on a fall, and `0` for no change, and the unit phrase is as above (` hours` for the hour families, none for the count families) (assembly filled `since_last` refs from deltas at [framework/proposal/assembly.py:72-85](../../framework/proposal/assembly.py), whose values already carry the sign at [framework/proposal/prompt.py:59-85](../../framework/proposal/prompt.py)); it says what changed and in which period, then the change since the previous card. A metric ref whose `metric_label_binding` is `None` makes the claim unrenderable: it is left out and counted (`metrics_unbound`) — never guessed. The page's start screen explains once, in plain words, that `earlier`, `prior` and `last` are three back-to-back 24-hour periods before the card, `last` being the most recent. Tests pin every family's wording, the period phrase, the unit, and the three signed-change forms. Reason: the rater judges "follows from the data it cites", so the data must be readable without knowing metric ids or terse label words; naming what was counted keeps the page's words tied to the gate's own binding and the prompt's display rendering.
- **AD7 — The page is one file, no network, phone-first (A6).** One self-contained HTML file, inline `<style>` and inline `<script>` only. It carries `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'">`; no external script, stylesheet, font, image or link; no `<form>`; the script uses no `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, or navigation. A committed test scans the generated file for all of these plus any `http://`/`https://` occurrence and fails on any hit. The page shows nothing beyond the atomic claims and their evidence: no card id, slot time, profile, model, fact origin, or commitment title. Flow: a start screen says in plain words what to do, that it takes about 10 minutes, how many sentences there are, and what Yes / No / Can't tell mean; then one sentence at a time with its evidence, a `"<k> of <n>"` counter, three large buttons `Yes`, `No`, `Can't tell` each with a few plain words underneath, and a Back control to change the previous answer. Answers persist on every tap to `localStorage` under a pack-scoped key, restore on load, and the whole flow still works when storage throws (kept in memory only). The end screen offers a result-file download and a copy button, with the identical result JSON also shown as selectable text on the page as a fallback. Nothing is sent anywhere; the person sends the file back. It asks nothing about the rater. Large type, high contrast, buttons at least 56 px tall, works opened straight from `file://` and on a phone. Reason: the rater has no AI background and one short session; any network reference, account, or upload path would be both a privacy hole and a way to lose the session.
- **AD8 — Blinding: seeded order, opaque ids, a private key, pack id + hash everywhere (A7).** Items are ordered by `random.Random(seed).shuffle` over the source claims sorted by their source key, then assigned ids `item-0001, item-0002, …` in that shuffled order. The page and the key both carry `pack_id` and `pack_hash` = SHA-256 hex of the canonical JSON of the ordered item list `[(item_id, atomic_text, [rendered evidence lines in shown order]), …]`, so a page with changed evidence can't pass as the same pack. `pack_id` is a caller-supplied label (`--pack-id`, optional) or, by default, derived from the start of the hash — `pack-<first 12 hex chars of pack_hash>` — so the default pack id must not reveal the seed (the shuffled order already needs the seed; the id on the returned file must not hand it back). The key file (JSON, written next to the page) maps each item id to `{card_id, slot, profile, model, effort, claim_id, proposal_key, atomic_index, delivered_cards_shown}`, plus `{pack_id, pack_hash, seed, cut, generated_from: "copy"}`; `model`/`effort` are `model_requested`/`effort` of the attempt that produced the claim — the highest-numbered attempt row for that `proposal_key` (the attempt whose draft became the result). The result file (produced by the page) is `{pack_id, pack_hash, started_at, ended_at, answers: [{item_id, label, answered_at}, …]}` with `label ∈ {supported, not_supported, cant_tell}` from Yes/No/Can't tell. Reason: the rater must not be able to infer model, effort, or card order from ids or sequence (Deviation 4: "The rater isn't told which model wrote what"), and the hash lets the scorer prove the returned file belongs to this exact page.
- **AD9 — The pack cut, exclusions for later packs, and the scorer's refusals (A9, A10).** The generator takes `--cut <iso>` (default: the generation instant, recorded in the key). **A card enters the pack when its slot instant is at or before the cut** (and its slot is a run slot, AD1 scope, and it is delivered, AD1); a corrected card keeps its slot (the corrected card is built with `slot=old.slot` at [framework/voice/worker.py:1263-1367](../../framework/voice/worker.py), and its `slot_cards` rows copy the old slot at [framework/voice/worker.py:1717-1777](../../framework/voice/worker.py)). No delivery instant is read for the cut: the slot ledger has no wall-clock column — its rows carry only `slot, step, outcome, seconds, card_id, detail` ([framework/cycle/slot_ledger.py:28-36](../../framework/cycle/slot_ledger.py)) — so a card whose only delivery signal is the slot ledger's `delivered` row has no readable delivery instant, and reading one would turn a delivered card into delivery-unknown against AD1. (A `telegram_card_messages.sent_at` exists at [framework/telegram/ledger.py:63-73](../../framework/telegram/ledger.py), but it is not present for every delivered card, so it is not the cut.) `--exclude-key <path>` may repeat: every source claim whose `(proposal_key, claim_id)` appears in an earlier key file is left out, so a second short session covers only what no earlier pack held. The generator prints `statements_total`, `claims_atomic_total`, and — when the atomic count is large — still includes **all** of them (never trims); the printed count is how the reviewer knows the session outgrew 10 minutes. The scorer `score --pair <key> <result> [--pair …] [--db <path>]`: refuses (exit 1, counts/codes only) on pack id or hash mismatch, an unknown item id, a repeated item id, or a label outside the three. It prints, per pair and combined: `claims_in_pack`, `rated`, `supported`, `not_supported`, `cant_tell` (own line), `unanswered` (own line), `support_rate = supported / claims_in_pack` with its `n` (over **every** atomic claim in the pack, per Deviation 4's denominator), and the same rate per `(model, effort)` from the key. With `--db`, it also prints `unlabelled_atomic_claims` on its own line: the atomic claims on delivered run cards (AD1 scope + AD2–AD5 rerun on the copy) that **no supplied key holds** — not cards after a cut — so it also shows anything a pack missed, for any reason. Multiple pairs report together and apart; source claims present in two keys are a refusal (`keys_overlap`), because a claim rated twice would double-count. Reason: the denominator is frozen by Deviation 4, later cards are expected (the run continues after the first pack), and a scorer that quietly accepted a wrong or double file would corrupt the one outside measurement R1 has.
- **AD10 — Privacy is by construction, and refusal prints counts only (A8).** Before anything is written, every string destined for the page (each atomic text, each fact statement, each rendered evidence line) passes `scan_outbound_text` with the terms from `load_private_terms()` (production default — no `allow_missing_for_tests`) and `forbidden_literals_for(copy_store, subject_id, card.as_of)` per card ([framework/cycle/__init__.py:97-107](../../framework/cycle/__init__.py)), and must contain no commitment title from the commitments file as a whole phrase (case-insensitive, whitespace-collapsed — the gate's own matching discipline). Any scan hit, unavailable private terms, or unavailable commitments refuses the whole pack: exit 1, printing only `pack_refused=1`, a closed reason code, and hit counts per check — never a sentence, fact, title, or private path. The output directory must resolve outside the repository work tree (repo root = the checkout containing the running `framework/` package); a path inside it is refused with exit 2 before the store is even copied. The page and key are written `0o600` inside a `0o700` directory. Reason: the page holds real sentences with screen hours, calendar hours and cited facts; the only safe failure is no file at all, and the repo must be unable to receive one by accident.
- **AD11 — Commands and exit codes, Slice A (A11).** `python -m framework.rater pack --db <path> --out-dir <path> --seed <int> [--cut <iso>] [--pack-id <label>] [--exclude-key <path> …]` and `python -m framework.rater score --pair <key> <result> [--pair …] [--db <path>]`. Exit codes: `0` success; `1` data refusal (scan hit, unavailable terms/commitments, scorer mismatch/unknown/repeated/bad label, overlapping keys); `2` usage (bad arguments, missing `IKIGAI_SUBJECT_ID`/`IKIGAI_COMMITMENTS_FILE`, output dir inside the work tree, missing DB file). Stdout is `key=value` counts and codes only. Reason: the reviewer runs these by hand next to a private store; pinned codes are what make a refusal actionable without reading prose.

- **BD4 — Identities derived from `propose` are printed with both sides and gate the exit code (B3).** From the flow of `propose` ([framework/proposal/core.py:198-266](../../framework/proposal/core.py), retry loop at [framework/proposal/core.py:493-494](../../framework/proposal/core.py), unavailable path at [framework/proposal/core.py:524-566](../../framework/proposal/core.py), blocked path at [framework/proposal/core.py:495-523](../../framework/proposal/core.py)) the report computes and prints each identity as `<name> left=<a> right=<b> ok=<0|1>`, exiting non-zero if any fails:
  - `passed_plus_failed_eq_reached`: `first_passed + first_failed == first_drafts` per `(model, effort)` (the SQL's own partition of `reached`).
  - `retries_eq_failed`: `retries == first_failed` per `(model, effort)` — an equality, not an inequality. Checked against `propose` in this plan session and it holds for every recorded result: `repair_loop` retries once after every failed validation and returns only on a pass ([framework/verify/repair.py:53-76](../../framework/verify/repair.py)), so a reached first draft that failed always runs a second generation; and a generator exception on that retry is caught in `propose` as `OutboundBlocked` ([framework/proposal/core.py:495-523](../../framework/proposal/core.py)) or `MetaUnavailableError` ([framework/proposal/core.py:524-566](../../framework/proposal/core.py); its local-start subclass is at [framework/proposal/muse_client.py:82-90](../../framework/proposal/muse_client.py)) and recorded as a blocked or unavailable attempt 2 (`number=len(records)`) on a noop/fallback result, which `record` persists with its result in one transaction ([framework/store/proposal_store.py:266-360](../../framework/store/proposal_store.py)). A generator exception of any other type propagates out of `propose` with no result recorded at all, so it cannot leave a recorded failed first draft without an attempt 2. Unavailable and blocked first attempts return without entering or continuing the loop, so they can never produce attempt 2.
  - `retry_passed_le_retries`: `retry_passed <= retries`.
  - `retry_partition`: `retries == retry_passed + retry_fell_back + retry_unavailable + retry_blocked`, where `retry_unavailable` counts attempt-2 rows carrying `MODEL_UNAVAILABLE` (the case the brief names: a retry that came back unavailable lands as a fallback via [framework/proposal/core.py:524-566](../../framework/proposal/core.py) and is invisible in the SQL's attempt-1 `unavailable` grain, so the metrics module counts it with its own read-only query on the copy), `retry_blocked` counts attempt-2 rows with `blocked=1` (a retry stopped by the outbound scan ends as a noop with a blocked attempt 2 via [framework/proposal/core.py:495-523](../../framework/proposal/core.py), so it is not counted as a fallback), and `retry_fell_back = retries − retry_passed − retry_unavailable − retry_blocked`.
  - `attempts_per_key_le_2`: every `proposal_key` has at most 2 attempt rows (`max_retries=1`).
  - `fallbacks_cover_attemptless`: global `fallbacks` (results grain) `>=` the sum of per-model `model_fallbacks`, with `fallbacks_without_attempt1 = fallbacks − Σ model_fallbacks` printed — a no-evidence fallback is recorded with `attempts=()` ([framework/proposal/core.py:314-330](../../framework/proposal/core.py)) and so has no attempt-1 row to join.
  - `noops_cover_attemptless`: the mirror identity for noops (slot/hour/no-eligible noops carry no attempts, [framework/proposal/core.py:242-247](../../framework/proposal/core.py)).

## Risks

- **Regeneration recovery can still leave a side out, but not because a briefing was superseded.** AD3 tries every stored proposal row for the slot and profile, so a `--fresh` rerun or a re-proposal no longer makes a delivered card's side unmatched merely by being newer. What remains is visible by construction: no qualifying row leaves the side in `statements_unmatched`, and qualifying rows that disagree on a claim's evidence leave it in `statements_ambiguous`; both counts are printed, never silently absorbed. The earliest-qualifying rule also means two different briefings that regenerate the same pieces with the same evidence share the earlier row's identity — stated in AD4, and the reason the unchanged side is rated once.
- **Delivery union can over-count if Telegram accepted but every record failed.** Then no signal exists and the card is `delivery_unknown_cards` — under-counted, stated on its own line, never guessed into the denominator.
- **The `, so` rule is a shape rule.** A factual clause after `, so` with no digit is cut unseen by the rater. That is Deviation 4's registered reading (the clause names the pick), the digit arm keeps numeric cases whole, and `so_clauses_cut` is printed so the size of the cut is known.
- **R7's observed-device rule is strict.** Early run hours will often be `device_unobserved` unknowns. That is the registered rule ([docs/PREREG.md:125](../PREREG.md)); the report shows unknowns against all accepted commitments instead of shrinking the denominator.
- **`proposal_results` has no origin column** (BD2/C4). `reproposal_results` can include a `--fresh` slot-path rerun. The voice count beside it bounds the ambiguity; adding an origin column is a store migration this ticket deliberately does not do.
- **Page size.** All atomic claims in one file, however many, may make a heavy page on a phone. Accepted by the brief (never trim); the start screen states the count so the rater knows the session length up front.

## Brief claims the code contradicts (and the reading this plan pins)

- **C1 — "The voice path … keeps the payload in `telegram_cards`" is true but cannot mean delivered.** `send_card` writes `telegram_cards` **before** the photo is sent ([framework/telegram/service.py:140-147](../../framework/telegram/service.py)), for both paths. AD1 therefore never treats `telegram_cards` (or `slot_card_payloads`) as a delivery signal; only the three post-acceptance signals count.
- **C2 — The slot path's payload is not only in `slot_card_payloads`.** Slot cards also pass through `send_card`, so they are in `telegram_cards` too. AD2 reads slot cards from `slot_card_payloads` (the exact sent bytes) and voice-only cards from `telegram_cards`; no claim rests on the distinction.
- **C3 — "The same source claim on an original and a corrected card counts once" needs an identity the store only half-provides.** Statements carry no claim ids, briefings' claim ids (`c-<section>-<n>`, [framework/proposal/assembly.py:45-50](../../framework/proposal/assembly.py)) repeat across briefings, and `StoredResult` drops `proposal_key`. AD3/AD4 pin identity as `(proposal_key, claim_id)` of the earliest qualifying row, read by the rater's own `SELECT`: the unchanged side and the original resolve to the same row and dedup exactly, the original keeps its claims after a re-proposal, and a re-proposed side that regenerates identical pieces with identical evidence likewise resolves to the earlier row; only a side qualifying solely against its new row is a new source claim.
- **C4 — "Re-proposals made for corrected cards" cannot be isolated exactly.** `proposal_results` has no origin marker, so a `--fresh` rerun at a run slot is indistinguishable from a voice re-proposal in that table. BD2/BD3 pin the countable line by proposal key (earliest row per run slot+profile is the slot path, every other row at a run slot is a re-proposal, and R1 is filtered by those key sets) plus the exact voice count beside it, and name the gap instead of hiding it.
- **C5 — B4's "shown hour" is not in `slot_cards`.** `SlotCardRow` has no hour fields ([framework/cycle/slot_ledger.py:163-177](../../framework/cycle/slot_ledger.py)). BD5 takes the hour from the standing card's stored `Card` proposals ([framework/telegram/models.py:114-120](../../framework/telegram/models.py)).
- **C6 — "The same variables the product reads" has two readings.** The poller defaults the subject to a placeholder ([framework/collectors/common.py:90-92](../../framework/collectors/common.py)); `run-slot` refuses without it. SD3 pins the strict reading (required, no default) for both commands.
- **C7 — "The numbers cut in PREREG" is two instants.** Registered text says Nov 4 18:30 ([docs/PREREG.md:19](../PREREG.md)); the clock Deviation reads fact-layer numbers through the 18:00 whole-hour cut ([docs/PREREG.md:158](../PREREG.md)). BD5/BD6 pin 18:00 for evidence data (Deviation wins, per the brief's own rule), and `--as-of` still right-censors anything later.
- **C8 — Nothing else in the brief disagreed with the code I read.** In particular `build_statements`, `results_for_slot`, `first_draft_report`, `standing_chain_ruling`, `rebuild_state`, `score_report`, `policy_diff` and `recover_table` all exist with the shapes the brief assumes, at the lines cited in Grounding.
